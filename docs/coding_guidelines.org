#+title: taskboard Coding Guidelines
#+options: toc:t

* 1. Code Formatting and Linting

- *Formatting:* Enforce standard Rust formatting rules using =cargo fmt=.
  Never hand-format Rust code; always run =cargo fmt= before committing.
- *Idiomatic Code:* Run =cargo clippy= (workspace lints: =all = "warn"=,
  =pedantic = "warn"=) to catch common mistakes and enforce idiomatic Rust
  constructs. Do not offer a PR that contains clippy warnings — CI runs
  with =-D warnings=, turning them into hard errors.
- *Dependency Auditing:* =cargo-deny= runs in CI as a unified linter for
  =Cargo.lock=: duplicate dependency versions, restrictive software
  licenses, forbidden crate sources, and security vulnerabilities. Run
  =cargo deny check --workspace= locally before pushing.
- *Dependency Versions:* Shared external dependencies are versioned once in
  the root =[workspace.dependencies]=. Member crates must reference them
  with =.workspace = true=, never with a duplicate version pin.

* 2. Architectural Boundaries and Purity

- *The Functional Core:* The =taskboard-domain= crate must remain
  completely pure: zero network, zero UI, zero asynchronous runtime
  dependencies. Design domain logic as pure functions that take inputs and
  return outputs, rather than methods that mutate hidden state.
- *Actor Isolation:* Application state, network IO, and local storage run
  as isolated background tasks on the Tokio runtime. Actors communicate
  exclusively via typed message passing using asynchronous channels
  (=tokio::sync::mpsc=, =tokio::sync::broadcast=, embedded =oneshot=).
- *Dependency Injection:* Rely heavily on DI through Rust traits: define IO
  interfaces (Ports) in the domain crate, implement them (Adapters) in the
  outer crates (see =docs/testing_strategy.org=).
- *unsafe:* Every crate carries =#![forbid(unsafe_code)]= — the sole
  exception is =taskboard-ui-slint=, where Slint's generated rendering code
  requires =unsafe=. Do not relax this without an ADR.

** 2.1 Type-Driven Design Policy (2026-10-24 ruling)

The project's assurance ladder starts at the type system. The rulings
below come out of the type-driven/formal-methods suitability evaluation
(=.artifacts/reports/2026-10-24-type-driven-formal-methods-suitability-report.md=,
grounded in the survey of the same date) and are binding for new code.

- *The house pattern is A1, hand-rolled:* a private-field newtype whose
  non-total constructor (the /mint/) lives at the trust boundary — the
  wire decode, the storage codec, or the config load. Parse, don't
  validate: values are validated once where they enter and thereafter
  carried in the minted type. Existing exemplars: =ReminderOffset=
  (=crates/taskboard-domain/src/reminders.rs=), =DeckColor=
  (=crates/taskboard-sync-nextcloud/src/color.rs=), the =local_id!=/
  =remote_id!= id families (=crates/taskboard-domain/src/ids.rs=).
- *No derive-crate dependencies for this:* do not add =nutype=,
  =bounded-integer=, =refined=, or similar. A dozen hand-rolled lines
  match the house style and cost no proc-macro compile time.
- *Deliberate leniency is legitimate but must be documented at the
  type*, the way =Color= ("lenient by design; validation is the sync
  adapter's job") and =DeckColor= (strict writes, lenient reads) are.
  Leniency without that comment is indistinguishable from a gap.
- *No validate-and-forget:* a value range-checked at one boundary must
  not continue its life as a bare primitive. Config-minted values
  (connector names, UI scale) are to be carried in minted types
  (tracked in the follow-up issue from the suitability report).
- *A2–A4 techniques stay out while the existing means suffice — but the
  ruling is conditional, not permanent.* The default correctness means
  are: typed-id-keyed collections and composite refs (handle
  provenance), enums-with-data plus pure transition functions (state
  machines), and boundary-parsed inert quantities (units). If *new* code
  introduces shapes where those means stop sufficing — arena or
  slot-recycled containers, stateful resources with illegal transitions
  not cleanly expressible as enum data, operation-dense mixed-unit
  arithmetic — then either apply the corresponding technique (branding/
  generational indices, typestate, quantity types) or an equivalent
  compile-time/structural guarantee, and record the choice at the type
  or in an ADR. =PhantomData=-heavy encodings applied where an
  enum-with-data would do are a smell, not a goal.
- *Churn posture:* the workspace API is internal and the sole current
  user is the maintainer; API churn, blame-churn, and wide multi-file
  edits are *not* decision variables. If the change improves the code —
  cleaner, more elegant, more provably correct — make it. API stability
  becomes a criterion only when the maintainer explicitly nominates a
  crate for extraction/reuse, at that time.


* 3. Error Handling

Error handling is structurally split between library crates and the main
executable:

- *Domain & Libraries:* Use =thiserror= in domain and library crates to
  derive static, strongly-typed error enums so callers can programmatically
  match on specific failure modes (e.g., =NetworkTimeout= vs =Unauthorized=).
- *Application Binary:* Use =color-eyre= in =taskboard-app= to catch errors
  and panics with rich backtraces and colorized context.
- *The entry-path reading of the binary rule:* =color-eyre= is for the
  functions that *are* the binary's entry paths, not every line
  physically inside =taskboard-app=. Entry paths are =main.rs= and
  lib-located lifecycle entrypoints whose only callers live in the
  binary's own entry dispatch — e.g. =run_desktop=, the desktop
  lifecycle's =main=-equivalent, whose =color_eyre::Result= is
  formatted by the same top-level =color_eyre::install()=. Everything
  below an entry path returns typed errors (=thiserror=); a
  lib-located function with any caller outside the binary's entry
  dispatch does not qualify. (The 2026-10-16 audit's recorded ruling,
  F8-07.)
- *No =unwrap=/=expect= in non-test library code* unless the invariant is
  proven locally and documented; prefer returning typed errors.

* 4. Logging and Observability

- *Structured Instrumentation:* Use =tracing= for all application logging
  to handle contextual spans across =.await= points in async workflows.
- *Dependency Log Capture:* Always include the =log= compatibility feature
  flag in =tracing= so standard =log= emissions from third-party
  dependencies route into the structured =tracing-subscriber= output.
- *Level contract:* =trace= carries entry identities (ids, timestamps,
  user content); =debug= carries typed decision facts (ids, enums,
  booleans — never prose); =info= carries lifecycle transitions
  (spawn/shutdown/attach) and user-facing deliveries; =warn=/=error=
  carry abnormal-but-survivable and lost-work events. User content
  never appears above =trace=, except on a delivery/notification
  surface, where the logged event is itself the user-facing artifact
  (e.g. the reminder =LogSink= line). Messages are static, greppable
  strings; facts ride as typed fields via the =?x=/=%x= sigils.
- *Log enough to enable debugging:* All project crates should carry
  sufficient logging statements (at appropriate levels) that a user's
  default log output can localise a bug report, and a =debug= or =trace=
  level log can pinpoint the location of most bugs.
- *Async Diagnostics:* Build with =--features tokio-console= (in
  =taskboard-app=) and connect the =tokio-console= CLI to inspect async
  task state, channel occupancy, and lock acquisitions during development.

* 5. State Sharing and Synchronization

- *Lock-Free UI Reads:* Never force the UI to wait on asynchronous
  processes. Expose the application state to the UI layer using
  =arc_swap::ArcSwap<AppState>=: lock-free, zero-contention reads on the UI
  rendering thread.
- *Non-Blocking Logic:* The UI crate must act as a "dumb presentation
  client". It only reads from the =ArcSwap= snapshot, maps fields to
  widgets, and emits non-blocking =mpsc= commands on user interactions.
- *No shared-mutable-state locks across actors:* =Mutex=/=RwLock= are
  reserved for intra-actor internals, never for cross-actor communication.

* 6. Platform Support

- *Multi-platform by default:* Where possible, code is multi-platform
  compatible. Platform-specific code must be gated by the appropriate
  annotations (=#[cfg(...)]=).
- *Target Platforms:* x86_64 Linux is the dev platform; first-class binary
  releases for x86_64 Linux & Windows; second priority 64-bit MacOS, 64-bit
  ARM Linux & Windows.

* 7. Source Code Repository

** Commit Message Format

#+begin_example
<type>(<module/workspace-scope>): <short-desc>

<long-desc>
#+end_example

Types: =feat=, =fix=, =refactor=, =test=, =docs=, =ci=, =chore=.

Example:

#+begin_example
fix(app): config rewrites preserve the operator's file mode (#386)

A rewrite adopts the destination's existing permission bits (masked
to 0o777) instead of re-tightening every rewrite to 0600 — the
file's mode is operator territory. A config the writer creates (no
prior mode) still lands 0600 (F12-01/ADR 0012).
#+end_example

** Feature/Issue Branches

Implement new features and bug fixes on dedicated feature branches that get
merged into =main= once completed.

Branch naming: =<category>/<workspace-scope>-<short-description>= with
categories:

- =feat/=: New user-facing features, new domain functionality, or new UI views.
- =fix/=: Bug fixes across state processing, IO connectors, or UI components.
- =refactor/=: Restructuring or optimization without changing external behavior.
- =test/=: Adding or updating unit tests, insta snapshots, or proptest suites.
- =docs/=: Documentation updates.
- =ci/=: Pipeline tweaks, GitHub Actions updates, cargo-deny configuration.
- =chore/=: Dependency bumps, toolchain updates, repository maintenance.

Examples: =feat/ui-slint-overdue-banner=, =feat/ui-r2-drag-to-move=,
=fix/issue-42-sqlite-cache-deadlock=, =fix/nextcloud-auth-token-refresh=,
=ci/cargo-deny-license-check=, =docs/update-agents-artifact-spec=.

Naming guidelines:
- Keep descriptions concise: 2–4 words after the scope tag.
- Include issue numbers for tracked bugs.
- Avoid personal prefixes; if two people create separate versions of the
  same feature/fix, use a personal suffix instead.

** Merging into main (branch-protected PR flow)

=main= is branch-protected on GitHub: every change enters through a PR
that must pass its required CI checks, and local merges into =main= are
not available — the double-rebase procedure this section used to
describe is no longer performable by anyone.

The flow: commits land on the feature branch (freely; house subject
format above) → push only on explicit instruction → open the PR →
=gh pr checks= green → hand off. /The user performs the merge on
GitHub/ (rebase-merge), so no merge commit ever enters =main= either.

Rebase-merge consequence: commits land on =main= verbatim — every
commit must stand alone (correct build, meaningful subject, no WIP or
leftover noise); corrections are amended or reworded before the PR
opens, never in follow-up commits with duplicate subjects.

Stacked PRs: after an upstream PR merges, descendant branches rebase
onto =origin/main= dropping the already-merged commits and push with
=--force-with-lease=. The exact commands live in =AGENTS.md= §8 — the
normative source; this section is the summary and must not drift from
it.

** Git Usage Policy (for agents)

- Never push to a remote without explicit direction from the user.
- Never merge a feature branch into =main= without explicit user approval.
- Do create feature branches for code changes; do commit freely to them.
- Do not work on or commit to =main=. (Exception: the initial repository
  bootstrap commits.)
- Worktrees for parallel agent work live next to the project root:
  =<project-root>-WT-<branch-name>=.

** Release Versioning

Single global semver in =[workspace.package] version=, inherited by all
crates. Cut releases exclusively with:

#+begin_src sh
./scripts/bump_version.sh <major|minor|patch> [--no-push]
#+end_src

The script (1) aborts on an unclean git tree, (2) cuts
=chore/release-v<X.Y.Z>= off the fetched =origin/main=, (3) increments
the version, (4) refreshes =Cargo.lock= and promotes the =CHANGELOG.md=
release entry, (5) stages & commits all changed files on the release
branch, and (6) unless =--no-push=, pushes the branch and opens the
release PR with =gh=. The tag is never created by the script: =main= is
branch-protected, so after the human merges the PR, tag the merged
=main= commit and push =v<major>.<minor>.<patch>= — that triggers the
Release workflow (the script prints these steps).

Before cutting, sweep the range since the last tag for changelog
misses: a user-visible commit with no =[Unreleased]= entry ships
silently — the promotion step copies the section verbatim and never
invents entries.

#+begin_src sh
LAST="$(git tag --list 'v*' --sort=-v:refname | head -n1)"
git log --oneline "$LAST"..origin/main | grep -E '\b(feat|fix)\('
#+end_src

Check every listed commit against the =[Unreleased]= section by its
=#<issue>= reference; =chore= or =refactor= commits that change
shipped behavior (profile flags, dependency bumps — e.g. the
release-profile overflow-checks) are judged the same way, while
docs-, test-, and CI-only commits are exempt. A miss is fixed by
adding the entry to =[Unreleased]= before running the bump, so
promotion picks it up verbatim.
