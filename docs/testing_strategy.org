#+title: taskboard Testing Strategy
#+options: toc:t

Achieving high testability in an asynchronous, multi-actor system requires
strict boundaries between pure logic and side-effect-heavy IO. The design
decisions below make the test suite fast, deterministic, and free of flaky
network or UI dependencies. The single sanctioned exception is the
Nextcloud sync client, whose real-server testing is strictly tiered (§8):
only the hermetic, secretless docker tier may run in CI — anything
touching a live deployment is a local, opt-in invocation. These rules
are binding for agents and humans alike (see also =AGENTS.md= §5).

* 1. Hexagonal Architecture (Ports and Adapters)

Isolate core logic from Nextcloud and SQLite via Dependency Injection
through Rust traits.

- *Define IO Traits in the Domain:* =taskboard-domain= defines async traits
  for all external operations (e.g., =pub trait TaskRepository=).
- *Inject Dependencies:* The state engine and sync actors receive these
  dependencies via generics (=T: TaskRepository=) or dynamic dispatch
  (=Box<dyn TaskRepository>=).
- *The TDD Benefit:* In production, =taskboard-app= injects the real
  =SqliteRepository=. In tests, an in-memory fake runs database-dependent
  logic in microseconds without touching the disk.

* 2. "Black Box" Actor Testing via Channels

Actors are tested through their public channel interface, without mocking
frameworks.

- *The Pattern:* Treat the actor as a black box. In a =#[tokio::test]=,
  instantiate the actor and hand it the receiving ends of its channels.
- *Execution:* Send an explicit command (e.g., =Command::TaskCompleted(id)=)
  down the =mpsc::Sender=.
- *Assertion:* Await the actor's response on the outgoing channel and
  assert the typed result. This proves the actor processes messages
  correctly without spinning up the Slint UI or a real database.

* 3. Fakes over Mocks for Stateful Components

- *Handwritten Fakes:* Instead of asserting that =save_task()= was called,
  implement the =TaskRepository= trait on a simple =HashMap= wrapped in
  =Arc<Mutex<T>>=. This simulates true data persistence across multiple
  operations — far more robust than pre-programmed mock return values.
- *No mocking crate:* the workspace deliberately wires no mocking
  library (=mockall= appears in no manifest). Async ports are
  hand-rolled =BoxFuture= traits
  (=crates/taskboard-domain/src/persistence.rs=) precisely so a fake
  is just an =impl= of the trait — see
  =taskboard_domain::test_support::InMemoryRepository= for the
  repository fake, and the UI suite's =fake_engine= for a fake at a
  module boundary. Behavior is asserted through the port's typed
  results, never through recorded calls.

* 4. The Functional Core & Property Testing

Keep =taskboard-domain= completely pure: zero network, zero UI, zero async
runtime.

- *Pure Functions:* Domain logic takes inputs and returns outputs, rather
  than mutating hidden state.
- *Property-Based Testing:* Because the domain is pure, =proptest= can
  bombard task sorting rules, recurrence generators, or Kiosk rotation
  schedules with thousands of randomized inputs to catch edge-case panics.

* 5. Snapshot Testing the App State

The UI layer is a "dumb client" that strictly reads from
=arc_swap::ArcSwap<AppState>=, so verifying state logic is straightforward:

- *The Practice:* Use =insta=. Push a series of commands through the state
  engine in a test, extract the final =AppState=, and verify the entire
  state tree with =insta::assert_yaml_snapshot!=. If a logic change alters
  the =AppState= structure, =insta= fails with a clean diff.
- *Do not* test the UI framework's internal state; snapshot the
  =StateEngine= instead.

* 6. Deterministic "Tokio Time"

Task reminders and Kiosk screen rotations depend on time passing. Standard
=tokio::time::sleep= in tests makes suites slow and flaky — /never use it/.

- *Time Manipulation:* In =#[tokio::test]= blocks, call
  =tokio::time::pause()= to freeze the runtime clock, then
  =tokio::time::advance(Duration::from_secs(3600)).await= to fast-forward
  instantly. Strict timeouts, delayed API retries, and task deadlines are
  tested deterministically.

* 7. UI Testing: Tiers & Pins (ADR 0015)

Slint ships no public =slint::testing= API (the design round's
recorded finding); the landed UI test suite is four tiers over what
does exist. Nothing tests the Slint framework's internals — the UI
suite proves *this application's* presentation layer.

- *Tier 1 — Unit (pure Rust).* Everything that needs no Slint
  runtime: keymap parse/merge/validate, resolver proptests (chords,
  prefixes, vi modes, masking), preset coverage + conflict-freeness,
  WCAG contrast pairs over token pairs, presentation helpers
  (time-boundary formatting). No Slint types involved.
- *Tier 2 — Component / journeys.* =i-slint-backend-testing=
  (exact-pinned, workspace) behind the thin journey-driver module
  (=tests/support/driver.rs=), with mock time, element addressing by
  accessible role/label, and generated getters. The engine is faked
  at the forwarder boundary (=support/fake_engine.rs=), so journeys
  assert routing only — engine semantics live in the engine's own
  suites. The ten design journey steps run as one continuous session
  plus a cold-start view-graph walk; the keypress-count guard
  (=support/guard.rs=) encodes the design's per-verb ceilings as
  design contracts (any improvement passes).
- *Tier 3 — Golden visuals.* The board view at scale extremes × each
  breakpoint: software renderer, headless, bundled fonts (rendering
  is deterministic by construction); perceptual-hash tolerance with
  a renderer-presence assertion ahead of any comparison. Golden
  regeneration is an explicit, reviewed step — never CI-blessed.
- *Tier 4 — Harness smoke.* The dev-gated =slint/mcp= feature gets a
  CI job that boots headless-with-renderer, captures one screenshot,
  and asserts it is non-empty and changes after interaction; the
  feature-off assertions in =ci.yml= / =release.yml= (=cargo tree=)
  keep the MCP server out of every release resolution.

House rules carried into this tier: no sleeps (mock time only);
accessible labels are element *addresses* — message/label text is
never matched; journeys assert typed outcomes at stable seams, never
per-widget internals.

*Pin discipline.* =slint = "1.18.1"= (caret) and
=i-slint-backend-testing = "=1.18.1"= (exact) move together on every
bump; =tests/pin_guard.rs= asserts the pin equality in CI. Every
Slint bump follows ADR 0015's upgrade runbook — a per-bump chore,
recorded where the ADR lives.

* 8. Integration Testing: Nextcloud Sync (Deck OCS REST API)

=taskboard-sync-nextcloud= speaks to the Deck app through its OCS REST
API (paths under =/index.php/apps/deck/api/v1.0=, JSON inside the OCS
envelope), authenticating with an /application password/ over HTTP Basic
auth; every request carries the =OCS-APIRequest: true= header. Testing a
real HTTP client is split into four tiers, each answering a different
question. Only the hermetic tiers run by default; CI never sees a
secret, and nothing touches a live deployment except an explicit local
invocation.

- *Tier 0 — recorded fixtures (unit).* Parse and build Deck OCS payloads
  against JSON fixture files recorded from a real server (Tier 2 doubles
  as the fixture-harvesting source; =examples/harvest_deck_fixtures.rs=
  refreshes =tests/fixtures/deck/= against a live tier when the recorded
  payload shapes drift). No network; part of the ordinary CI test job.
- *Tier 1 — contract tests (mock HTTP).* An in-process mock server
  (=wiremock=, dev-dependency) serves canned responses covering the
  error matrix (401/403/404/409/412/5xx). Client behavior is verified
  deterministically here: Basic-auth and =OCS-APIRequest= header
  construction, OCS envelope unwrapping, typed error mapping, and
  retry/backoff — the last frozen via the =RetrySleep= clock seam
  (§6), which is impossible against a real server.
- *Tier 2 — dockerized Nextcloud (CI, secretless).* The official
  =nextcloud:<major>= image (version pinned; a matrix over supported
  majors is a future option) on SQLite, started via
  =docker/nextcloud-test/compose.yaml= both locally and as a CI job step
  (compose rather than a =services:= block, because the Deck app must be
  installed after boot via =occ app:install deck=). Auto-install runs
  from the container env (=NEXTCLOUD_ADMIN_USER=,
  =NEXTCLOUD_ADMIN_PASSWORD=, =SQLITE_DATABASE=,
  =NEXTCLOUD_TRUSTED_DOMAINS=); readiness is polled on =status.php=
  until =installed:true= /with a deadline/ (§9: poll a predicate, never
  sleep). Credentials are throwaway values hardcoded in the
  compose/workflow environment — the instance is localhost-only and
  ephemeral, so there is deliberately /no/ secret management here. A
  test user and its app password are minted after boot (=occ user:add=,
  =occ user:add-app-password= — =app-password:assign= on newer releases)
  so this tier exercises the production auth path. CI runs the tier
  under the =it_nextcloud_docker= test-name filter.
- *Tier 3 — private production server (local, manual only).* Proves the
  full story against the real deployment: its Nextcloud version, reverse
  proxy, and TLS chain. It /never/ runs in CI — no Nextcloud secret of
  any kind exists on GitHub, so the server address cannot leak into the
  repository's public CI logs. Run it locally on demand:

#+begin_src sh
cargo nextest run --run-ignored only -E 'test(it_nextcloud_live)'
#+end_src

*Known-server matrix (check here first when a live tier fails).* When a
tier surfaces a failure, record the server versions and the observed
wire behavior next to them — the Deck API reference (=deck/api/v1.0
docs/API.md=) describes intent, not every deployed reality, and wire
drift is version-specific:

- *Tier 3 live (as of 2026-10-08):* Nextcloud 33.0.9, Deck app 1.17.5
  (=status.php= / =capabilities= =deck.version=). Observed deviations
  from the API reference, all pinned by fixtures/contract tests: card
  PUT requires =owner= as the /bare user id string/ (an object fails
  framework param binding with a bare 400); card reads return =labels=
  as inlined label objects (writes take ids); =reorder= answers with a
  card object, an array of cards, or nothing depending on version, and
  a cross-stack move can lag Deck's cache; =GET /boards/{id}/labels=
  answers 405 (use the board read's =labels=); stack listings omit
  =cards= entirely for empty stacks (other builds send =null=).
- *Tier 2 docker (as of 2026-10-08):* =nextcloud:35= (35.0.1), Deck app
  1.19.0 (=occ app:install deck=). Same wire shapes as Tier 3 except
  where noted above; empty stacks send =cards: null= here. Phase 4
  additions (verified 2026-10-10 by the D-series): the boards
  *listing* carries =labels: []= even for labelled boards (the board
  *detail* payload is authoritative); a soft-deleted board's detail
  read answers *403* while the listing may still list it (=deletedAt=
  stamped, =lastModified= *not* advanced — deletion stamps must come
  from the observation); every read of a dead board (stacks, card
  details) answers 404/403; write endpoints answer sporadic =500=s
  under load (the production client must not retry those — a retried
  create can double-apply — but tier scaffolding retries them).

Hard rules binding the real-server tiers (2 and 3):

- *App password, never the account password.* App passwords are
  individually revocable and auditable in Nextcloud's Security panel,
  and are the only non-interactive option on servers enforcing 2FA. They
  cannot be folder-scoped — the dedicated test account /is/ the scope.
- *Secrets live in one place only.* Tier 3 credentials sit in a
  git-ignored =.env= at the repo root, loaded by the test harness via
  =dotenvy= (dev-dependency); the committed =.env.example= documents the
  names:
  =TASKBOARD_IT_NEXTCLOUD_URL=, =TASKBOARD_IT_NEXTCLOUD_USER=,
  =TASKBOARD_IT_NEXTCLOUD_TOKEN=. CI-only tokens (=CODECOV_TOKEN=,
  =SONAR_TOKEN=, =BENCHER_API_TOKEN=) stay in GitHub Actions secrets —
  a secret never migrates to a place that does not use it.
- *Skip, never fail.* Live tests are =#[ignore]=-marked with an internal
  environment guard; when the variables are unset they skip. The default
  =cargo nextest run --workspace= therefore cannot touch the network,
  and the coverage job stays hermetic by construction.
- *Isolation.* Every run reads and writes only under a unique
  =taskboard-it-<run-id>= prefix, with best-effort teardown.
- *Wall-clock timeouts.* Every live test is wrapped in
  =tokio::time::timeout= so a hung connection fails the test in seconds
  instead of stalling the job.
- *Auth-failure coverage stays in Tiers 1–2* (401 mapping, expired
  tokens): repeated failures against a real server trip its brute-force
  protection and can lock the test account out.

** App-level E2E (binary-driving, tier-2 reuse)

Phase 6 adds a fourth live surface to Tier 2: the =it_nextcloud_docker_cli_*=
journeys (=crates/taskboard-app/tests/it_cli.rs=) drive the *real
binary* — =Command::new(env!("CARGO_BIN_EXE_taskboard"))= — through the
multi-process login → boards select → tasks add → sync choreography
against the dockerized Deck server. They exist to prove only what only
the binary can prove: arg parsing, stdin prompting (the password is
piped into =login=, which is itself the regression proof for the
piped-stdin =rpassword= path), config-file discovery, per-process env
resolution, exit codes, and the durable-then-pushed sequencing across
separate invocations. Everything below that surface is tested
hermetically (O/L/V/K-series via =taskboard_app::commands::= handlers
with wiremock + real sqlite tempdirs + fake stores/prompts) — one
behavior, one test, at the lowest layer that can own it.

Mechanics that make the binary tests safe to run in a shared suite:

- *Config by file, never by env.* Every child gets its config via
  explicit =--config <tempdir>/taskboard.toml=; the =TASKBOARD_CONFIG=
  escape hatch would couple children to the parent test process.
- *Per-child env hygiene.* =tests/common::binary_command()= strips
  every parent =TASKBOARD_*= variable before spawning and re-sets
  exactly what the child needs (=TASKBOARD_APP_PASSWORD= = the tier
  token) — a sibling test's override cannot leak into a journey.
- *The docker-tier serialization covers them.* The =it_nextcloud_docker=
  filter and the =docker-tier= nextest group (=max-threads = 1=)
  include the CLI journeys automatically; the existing
  =nextcloud-integration.yml= invocation needs no workflow change.
- *Coverage note (documented, not solved):* subprocess work is not
  instrumented by =cargo llvm-cov=; the hermetic handler suites carry
  the coverage duty for the command logic, and the journeys prove
  wiring.

** Keyring round trip (local, manual only)

The app-level counterpart to tier 3's live Nextcloud runs:
=it_keyring_local_round_trip=
(=crates/taskboard-app/tests/secrets.rs=) drives the production
=KeyringStore= (ADR 0008) against the /developer's own/ OS credential
store — the only executed proof of the credential store's real OS
I/O. It is manual-only for the same reason tier 3 is: it dirties a
real user keyring by design, and no CI runner sets its gate
(=TASKBOARD_IT_KEYRING= appears in no workflow). The hermetic halves
(password redaction, error mapping, fake-store round trip: S1–S6 in
the same file) run in every CI pass.

- *Prerequisite:* a running OS credential store in your session —
  Linux: a Secret Service such as gnome-keyring on the session D-Bus
  (the app links the =sync-secret-service= backend), macOS: Keychain,
  Windows: Credential Manager. A headless box fails typed
  (=CredentialError::Backend=) — by design; that failure is the signal
  to configure =credential_store = "env"= instead (ADR 0008).
- *Invocation:*

#+begin_src sh
TASKBOARD_IT_KEYRING=1 cargo nextest run -p taskboard-app \
  --run-ignored only -E 'test(it_keyring_local_round_trip)'
#+end_src

- *The vacuous-pass footgun:* the test is =#[ignore]=d /and/
  internally guarded — without =TASKBOARD_IT_KEYRING=1= exported it
  returns early and /passes having done nothing/. A green run without
  the gate proves nothing; always run the command exactly as above.
- *What it writes:* one throwaway entry into your own store — service
  =taskboard=, account =roundtrip@keyring-test.example.com=, value the
  literal =local-secret=. The test deletes the entry /before/
  asserting, so any in-test failure still self-cleans; only a process
  killed between store and delete can leave the entry behind — remove
  it with your desktop's credential manager (e.g. Seahorse on GNOME),
  looking up service =taskboard= / account
  =roundtrip@keyring-test.example.com=.

* 9. Test Suite Discipline (Hard Rules)

From =AGENTS.md= §5, restated because they matter:

- A new test failing can be a bug in production code — evaluate both sides
  before changing anything.
- Never weaken a correct test to make it pass; leave it failing and report
  the bug if the fix is out-of-scope.
- No quality ceilings, no text assertions, one behavior per test at the
  lowest layer, deterministic by construction, no pins of "today's
  behavior".

* 10. Memory Safety: Miri

Unsafe code lives mostly in the third-party dependencies of the stack, so
Miri is applied targetedly:

1. *Enforce* =#![forbid(unsafe_code)]= in all workspace crates (the sole
   exception: =taskboard-ui-slint=).
2. *Scope* =cargo miri= to pure logic, serialization, and state-transition
   tests: =cargo miri test -p taskboard-domain -p taskboard-state=.
3. *Run out-of-band in CI* (weekly scheduled workflow + manual dispatch):
   Miri is 10–100× slower than native builds, so it never runs in the PR
   pipeline. Run it locally when introducing complex serialization
   structures or concurrency primitives.

** The weekly job's contract (measured 2026-10-12 through 2026-10-16)

The job (=.github/workflows/miri.yml=) splits the sweep into four
parallel jobs — domain core, domain =pipeline::= tests, domain
=remote::=/=state::= properties, and the state crate — so each family
owns the 120-minute timeout and no single slow family starves the rest.
Every reduction below is an *interpreter-only environment/speed gate*:
the native suite is unchanged (256-case proptest default, failure
persistence, and the checked-in seed replay all stay exactly as they
are outside these jobs), and no assertion is weakened or skipped.

- *Environment forwarding*: under Miri's default isolation the
  interpreted process sees *no host environment variables*, so
  =PROPTEST_*= settings must be forwarded explicitly with
  =MIRIFLAGS=-Zmiri-env-forward=<VAR>=. Isolation itself stays on —
  =-Zmiri-disable-isolation= is deliberately not used.

- *Failure persistence is env-off under the interpreter*
  (=PROPTEST_DISABLE_FAILURE_PERSISTENCE=1=): proptest's persistence
  opens/canonicalizes the regressions file at every property start,
  which is unsupported under isolation. Only the raw
  =Config::with_cases= proptest blocks need this; the rest go through
  =test_support::proptest_config=, which disables persistence under
  =cfg!(miri)= in code. Nothing is lost semantically — persistence only
  remembers shrinking seeds between runs, and native runs keep
  replaying them, including the checked-in seed file.

- *Per-job case caps* (=PROPTEST_CASES=): domain core 16, domain
  =pipeline::= 2, domain remote/state properties 16, state 128. The
  =pipeline::= family does carry properties —
  =apply_push_report_equals_the_pipeline_push_phase= (the family's
  cost dominator, ≈ 15 min per interpreted case by subtraction from
  the measured walls) and =equal_replicas_converge= — so its cap of 2
  is a measured budget statement for those two, not an empty-family
  guard. Measured job walls at the kept caps, all judged against the
  ≈ 90-minute headroom bar (25% margin under the timeout):

  | job (cap)                 | 2026-10-12 run 38312493624 | 2026-10-15 run 38786976628 | probe run 38814917035 | run 38846463650 | run 38853294730 | run 38862752532 |
  |---------------------------+----------------------------+----------------------------+-----------------------+-----------------+-----------------+-----------------|
  | domain core (16)          | 55 min                     | 81 min                     | 82 min                | 66 min          | 46 min          | 82 min          |
  | domain =pipeline::= (1→2) | 24 min                     | 72 min                     | 105 min               | 55 min          | 102 min         | 91 min          |
  | remote/state props (16)   | 21 min                     | 18 min                     | 15 min                | 16 min          | 14 min          | 18 min          |
  | state (16 → 128)          | 8 min                      | 13 min                     | 71 min                | 71 min          | 93 min          | 77 min          |

  The 2026-10-15/16 probe (workflow_dispatch ladder on
  =ci/miri-cap-probe=) raised state 16 → 128 and pipeline 1 → 2, both
  kept on the green in-budget run 38846463650 (pipeline 55 min,
  state 71 min, core 66 min, props 16 min — all four ≤ 90 in the same
  run). Intermediate evidence, kept honest in the record: state 64
  has a single sample — 39 min (day window, run 38804930006); state
  128 measured 71/71/77/91/93 min across five windows (runs
  38814917035, 38846463650, 38862752532, 38826477952, 38853294730) —
  so no same-window pair exists for the two caps and the 39-vs-71 gap
  is not a per-case slope. What the record does show: window
  variance, not case count, sets this job's wall (the unchanged-cap
  control jobs swung 46 ↔ 82 min core and 14 ↔ 18 min props within
  the probe's own windows), and 128 was kept because doubling
  interpreted coverage costs a worst-observed wall (93 min) that
  still holds ≈ 22% margin under the 120-minute timeout. Pipeline
  cap 2's walls across seven dispatches ({55, 59, 91, 102, 105, 106,
  111} min) overlap cap 1's own pre-probe walls ({24, 72} min) once
  window variance is accounted for — cap 2 adds ≈ one dominator case
  (≈ 15–30 min) in a like-for-like window. In the observed slow
  windows it is the raised caps that cross the 90-minute bar
  (pipeline 102–111, state 91/93) while the unchanged caps stay under
  it (core ≤ 82, props ≤ 18, cap 1's own slow window 72): reverting
  to cap 1 would have restored the soft bar, but the raise was kept
  because the bar is a 25%-margin heuristic under the 120-minute
  kill, cap 2's worst observed wall (111 min) still clears the kill
  with ≈ 7% margin, and the night-curve follow-up below owns the
  residual risk. Caps exist to fit the budget; they are never a
  coverage statement, and moving one requires a measured budget
  justification recorded in the PR that moves it.

- *Do not read libtest's =finished in= figure as wall time*: under
  isolation Miri emulates the monotonic clock from interpreted work
  (≈ executed operations), so a job can print =finished in 4222s=
  with a wall time of ≈ 57 min. Budget compliance is judged from the
  job's wall time, never from this figure.

- *Doctests are outside the interpreter scope* (invocations use
  =--lib --tests=): the state crate's usage doctest boots the tokio
  engine, which reads the realtime clock and cannot run under
  isolation. Doctests stay compiled and executed natively in the PR
  pipeline.

- *Realtime-clock tests carry scoped =#[cfg_attr(miri, ignore)]=
  gates* (isolation provides no =clock_gettime(REALTIME)=). Fixture
  builders must not read the clock: they stamp fixed, distinct,
  strictly increasing timestamps (the repository contract harness's
  =ts()= block) so ordering semantics stay exercised while the tests
  run interpreted — the former fixture gates (PendingOp roundtrip,
  read-port contract, repository contract harness) moved to fixed
  stamps on 2026-10-15 and now run interpreted. The remaining domain
  gates are inherent — production code itself reads the clock:
  =clock.rs= (SystemClock) and =idgen.rs= (production
  =UuidV7Generator=). Each gated test runs natively unchanged;
  existing gates follow the same pattern (insta S-series socketpair,
  =sqlite_smoke= tempdir+FFI, P4/P5 live-engine properties).

- *Same-config walls drift window-to-window on the rolling nightly*,
  and the drift swamps the caps themselves: pipeline 24 → 72 min at
  cap 1, then 59 → 105 → 106 → 111 → 55 → 102 → 91 min across seven
  cap-2 dispatches in two days; core 55 → 81 → 82 → 66 → 46 → 82 min
  at the unchanged cap 16; and state 64's only sample (39 min, run
  38804930006) landed in the probe's fastest window — the two caps
  share no comparable window. The slow
  windows matter because the weekly cron fires Monday 03:00 UTC,
  inside one. Consequences: a single in-budget measurement is weak
  evidence of weekly repeatability; the ≥ 25% headroom preference
  applies to the worst-observed wall, not the best (state's worst
  observed is 93 min ≈ 22% margin under the timeout; pipeline's is
  111 min ≈ 7%); a drift-driven weekly red is re-triaged on the next
  nightly; and a cap that proves chronically over budget is lowered
  in a recorded follow-up, never quietly. At the 2026-10-15/16 night
  curve core and pipeline measure up to 82 and 111 min against the
  120-minute kill — if that curve persists on Mondays, re-sizing
  those budgets (or the 90-minute bar itself) is a recorded
  follow-up, not a quiet cap cut.

- *Why the job split exists*: interpreter cost is wildly
  non-uniform — the plain =pipeline::= tests dominate (the slowest,
  =apply_push_report_equals_the_pipeline_push_phase=, is ≈ 28 s
  natively but ≈ 25 min interpreted), while whole =remote::=/=state::=
  property passes cost ≈ 15 s per case. A single combined invocation
  cannot order around such outliers; parallel per-family jobs keep
  every family's wall time inside the headroom bar.

- *Local-run recipe*:
  =PROPTEST_DISABLE_FAILURE_PERSISTENCE=1 cargo +nightly miri test -p taskboard-domain -p taskboard-state=.
  A bare =cargo miri test= without the env aborts on the raw
  =Config::with_cases= proptest blocks (entities, state, remote,
  messages, ids, merge); migrating those to
  =test_support::proptest_config= is follow-up material (§9 backlog).

* 11. Fuzzing: cargo-fuzz

Deferred. With high-level, heavily-fuzzed ecosystem crates (=serde_json=,
=sqlx=, =tokio=, =chrono=) doing the low-level parsing, =proptest= +
=insta= provide ~95% of the value at a fraction of the setup cost.

*When to add =cargo-fuzz=:* only when a custom binary format parser,
string tokenizer, or low-level protocol decoder appears. (The Deck OCS
API is JSON handled by =serde_json=, so =taskboard-sync-nextcloud= is
not expected to grow such a parser.) Then fuzz out-of-band on a
dedicated service (OSS-Fuzz) rather than in the PR pipeline.

* 12. Sanitizers (ASan)

Deferred. Rely on =#![forbid(unsafe_code)]=, =clippy=, =cargo-deny=, and
Miri for now. Once the Slint UI and SQLite integrations are fully wired in
=taskboard-app=, add a scheduled nightly CI job running ASan against the
C-FFI boundary:

#+begin_src sh
RUSTFLAGS="-Zsanitizer=address" cargo +nightly test \
  -p taskboard-storage-sqlite -p taskboard-ui-slint \
  --target x86_64-unknown-linux-gnu
#+end_src

* 13. Coverage & Mutation Testing

- *Coverage:* =cargo-llvm-cov --all-features --workspace --nextest= in CI;
  review diff coverage before merging.
- *Mutation Testing:* =cargo-mutants= runs weekly (and on demand) against
  =taskboard-domain= and =taskboard-state=. Surviving mutants are recorded
  as =.artifacts/reports/YYYY-MM-DD-mutation-testing-report.md=.
- *Benchmarks:* =criterion= tracks hot paths (SQLite caching actor, task
  sorting) in the =benchmark.yml= lane — every =main= push plus a weekly
  Thursday 04:00 UTC run and manual dispatch (off the PR lane since
  2026-10-21: a 14–19 min job whose per-PR results were discarded; PRs
  keep =clippy --all-targets= compiling the bench targets). Uploads feed
  the Bencher =main= trend (=BENCHER_API_TOKEN= secret via the CLI's
  =BENCHER_API_KEY= env); no thresholds are configured — trends, not alerts.

* 14. Performance Smoke Harnesses (local, manual only)

Two scripts measure the *process-shaped* budget rows on the dev
machine (audit theme perf-budgets, sketches S1/S3; wave plan KDF-7
rows 1+4). They are smoke references, never gates: nothing in CI runs
them, no test asserts their numbers, and the exit code never encodes
a budget comparison — the kiosk bring-up spike owns the device-class
verdicts. Both build a fresh deterministic fixture (the hot-path
bench builder at N = 10 000) into a scratch directory and drive the
real release binary against it; a first run may spend minutes in
=cargo build --release=.

** RSS steady state (S1 — budget row 1: App RSS ≤ 200 MB)

- *Prerequisite:* Linux (reads =/proc/<pid>/status=); the release
  binary (built on demand). No display needed.
- *Invocation:*

#+begin_src sh
scripts/process_smoke.py rss            # --help for every flag
#+end_src

- *What it does:* spawns =taskboard daemon= standalone (no network —
  no =[nextcloud]= config) on the fixture DB, polls =taskboard status
  --json= until =daemon = true= (deadline-bounded; never a fixed
  sleep), soaks /proc VmRSS until a bounded plateau, reports
  steady/peak kB against the 200 MB reference, then shuts the daemon
  down over IPC (=daemon stop=).
- *Reading the number:* dev-machine reference under a desktop's load
  profile — direction only for the 1 GB kiosk device; record it in
  the PR/report, never in an assertion.

** Cold start to first frame (S3 — budget row 4: ≤ 5 s)

- *Prerequisite:* a graphical session — =WAYLAND_DISPLAY= or
  =DISPLAY= set non-empty (empty counts as absent); Linux; the
  release binary. Headless runs fail typed before spawning (slint
  1.18.1 panics at backend init without a display).
- *Invocation:*

#+begin_src sh
scripts/process_smoke.py cold-start     # --help for every flag
#+end_src

- *What it does:* spawns =taskboard gui= on the fixture DB and times
  spawn → the =moment = "first-frame"= structured tracing event
  (=TASKBOARD_LOG_FORMAT=json= is set for the child; the field, not
  the message text, is selected). The moment is the mount seam's
  first refresh (models ready) — the show→presented delta has no
  public slint 1.18.1 API and is unmeasured; receipt-side timing
  adds ≤ 1 ms bias.
- *Reading the number:* valid only within one backend —
  =SLINT_BACKEND= / =SLINT_SCALE_FACTOR= pass through to the child
  and move the number; the default backend of the shipped build is
  what the reference means. Device verdicts belong to the spike.

Both harnesses are honest about failure: a readiness deadline, a
non-plateauing soak, or a missing first-frame event is a nonzero
exit with the captured child logs printed — never a silent skip.

The =TASKBOARD_LOG_FORMAT=json= knob (one-line JSON log events on
stderr, default output unchanged when unset) exists for this
harness; it is a log-format switch, unrelated to the CLI =--json=
payload flag.
