#+title: Agent Dispatch Discipline — orchestrating multi-agent chunks

#+options: toc:t

This is the standing law for orchestrating work through the three-stage
dispatch protocol (planning → implementation → review; the protocol
itself: =.artifacts/templates/dispatch-plan.md=). It was formalized
2026-11-16 from the UX journey planning framework's rollout
(2026-11-13 → 11-16: six phases, six remediation chunks, ~20 staged
agent runs), where every failure mode below was observed and every rule
earned by a recovered incident. The full narrative:
=.artifacts/plans/2026-11-15-ux-remediation-dispatch-plan.md= §1
(long-command discipline amendment) and the rollout's dispatch plans.

* 1. The harness facts these rules answer

- *Inactivity cutoff*: a dispatched subagent is killed after ~600s
  without observable activity. Long silent commands kill agents that
  are otherwise working correctly.
- *Quota limits*: a subagent can stop mid-run with a quota error. Its
  context survives; it can be resumed.
- *Both are cheap if committed*: in every observed stall, the agent's
  landed commits were intact — only verification and reporting were
  lost. Work that is committed before any wait cannot be lost.

* 2. The long-command discipline (non-negotiable)

- *The coverage trio never runs inside a subagent.*
  =cargo llvm-cov nextest= + quarantine + report runs 10–14 minutes of
  silent compile+test — structurally longer than the inactivity
  cutoff. A stage-2/stage-3 agent's gate is: the pre-commit hooks
  (fmt + clippy + slint lint, automatic on every commit) plus
  =scripts/run-quality-gates.sh cargo nextest run --workspace= (the
  wrapper's flock-safe arbitrary-command mode, ~4–6 min warm).
- *The dispatcher owns the full suite*: it runs the complete AGENTS §10
  sequence in its own session (background + poll, which survives)
  between stage 2's landing and stage 3's ship — and CI's Code
  Coverage check runs it authoritatively on the PR regardless.
- *The dispatcher owns the CI watch and teardown*: a stage-3 agent's
  scope ENDS at PR-open. =gh pr checks --watch= is 7–16 minutes of
  silence — even backgrounded, an agent that runs out of other duties
  goes quiet and is killed at PR-green's worst moment. The dispatcher
  watches checks, performs teardown, and does at-merge issue closures.
- *The concurrency cap counts every live chunk-affiliated agent
  session* (#1288-adjacent incident, 2026-11-23 20:00 — the
  systemd-oomd kill): "≤3 concurrent chunks" means ≤3 LIVE agent
  sessions affiliated with chunks — stage-2 implementations, stage-3
  reviews, and mid-chunk continuations (quota/resume/dedup) alike.
  The dispatcher's failure mode was counting stage-2 implementations
  against the cap while letting reviews and a post-ship dedup
  continuation stack on top: five live sessions, each emitting cargo
  invocations, drove the whole ZCode cgroup to 19.8G with 36% Avg10
  memory pressure, and =systemd-oomd= killed the entire =app.scope=
  unit — every agent died at once. oomd reacts to PRESSURE (task
  stalls / swap thrash), not to the MemAvailable floor the memory
  gate samples at entry; five gate entries that each passed the floor
  check at time T still aggregate past the box's budget at T+minutes.
- *Every cargo invocation routes through =scripts/memory-gate.sh=* —
  not only the >1-minute ones. Single-target =cargo test -p= /
  =cargo build= calls were the un-gated class in the same incident:
  each looks cheap alone, five agents emit them concurrently, and the
  gate's exclusive flock never sees them. The gate is usually
  uncontended, so routing everything costs little and makes the
  box's heavy-command concurrency exactly 1.
- *Any subagent command expected over ~5 minutes runs backgrounded*,
  with short interleaved polls and useful work between polls — and the
  agent commits all landed work BEFORE beginning any wait.
- *Flock deferral (never block on the gate lock)*: when the
  =run-quality-gates.sh= flock is contended *and no other useful work
  remains*, the agent never blocks waiting for the lock — it commits
  all landed work, reports "gate deferred: lock held by <holder>",
  and ends its stage cleanly; the dispatcher runs the gate. A silent
  wait for a held lock is indistinguishable from a stall and dies at
  the inactivity cutoff (observed four times before this rule; #879).
- *Real builds route through the memory gate*: any agent command
  expected to be a real build (>~1 min — =cargo build=, =cargo test=
  subsets, clippy re-runs) and the pre-commit hook's clippy step run
  under =scripts/memory-gate.sh=: an exclusive cross-worktree flock
  serializes build-vs-build memory peaks, and a =MemAvailable= floor
  (=MEMORY_GATE_MIN_AVAIL_MIB=, default 8192) is polled before the
  command starts — bounded wait (=MEMORY_GATE_TIMEOUT=, default 3600s),
  then a nonzero exit. =--status= reports the lock state and the
  current reading. The full §10 suite keeps =run-quality-gates.sh=
  (its own, distinct lock). Evidence: the 2026-11-17 global OOM —
  7 concurrent cold per-worktree clippy builds + 1 llvm-cov build
  drove a 30G box under (a measured clippy re-check peaks at
  ~3.9 GiB; floor = peak + ~2 GiB desktop headroom + margin)
  (.artifacts/reports/2026-11-17-oom-incident-concurrency-learning-report.md).
  - *Two-mode routing*: *short/heavy builds* (clippy, =cargo check=,
    one-shot test builds — anything real but bounded by its own
    completion) run *gated-hold* (the default mode; lock held for the
    command). *Long self-capped runs* (cargo-mutants =--jobs N= under
    =timeout=, miri batches — any run with *both* its own job cap and a
    wall-clock cap) run *gated-preflight only*:
    =scripts/memory-gate.sh --preflight= floor-checks once, prints the
    reading, and never acquires the lock. The law sentence: holding the
    gate lock across a multi-hour run is an availability collapse
    (every other agent's gated pre-commit clippy queues behind it —
    observed live 2026-11-17 ~21:20, dispatcher-verified), not a safety
    measure; the self-caps are the protection. Evidence: the #923
    two-mode corollary and the mutants stage-2 report §4
    (.artifacts/reports/2026-11-17-cargo-mutants-taskboard-app-report.md).
  - *Gate-lock liveness is detection-only (#1110)*: both gate locks
    release on holder *death* (flock is kernel-owned) but a holder
    that hangs while *alive* blinds every queued waiter —
    =scripts/gate-lock-liveness.sh= (sourced by both gates)
    classifies the holder from the record the gates already write:
    =alive= (CPU time advanced across the poll window), =likely-hung=
    (zero CPU-time delta across 3 consecutive polls), =gone= (pid
    vanished; the kernel releases the lock). The constraint, binding
    on every gate and every agent: **no gate may kill, signal, or
    steal a lock from a live holder regardless of its CPU profile** —
    a legitimate long holder is indistinguishable from a wedged one by
    CPU time alone; triage is the dispatcher's job, and the safe
    release path remains flock-on-kill. The =likely-hung= wait line
    ("no CPU time in ~90s — triage that lane") is the #894
    flock-deferral rule's triage trigger: a waiting agent that sees it
    reports "gate deferred: lock held by a likely-hung pid <pid>" and
    ends the stage instead of blocking.
- *Resource law (the concurrency cap)*: at most **3 concurrent
  work-performing agents per box**, with **staggered starts ≥3
  minutes apart** (cold pre-commit build peaks must not align), and
  the **dispatcher's full §10 suite counts as ONE slot toward the ≤3
  cap** (agents + suite runs ≤ 3 total; `run-quality-gates.sh`'s
  flock still serializes suites; the memory gate still guards every
  agent build) — the suite is the heaviest single slot on the box, so
  stagger it ≥3 minutes from any agent start like any other slot. The
  strict **zero-agent free window is reserved for when
  `memory-gate.sh --status` shows pressure** (MemAvailable below the
  floor — the always-on free-window framing was the 2026-11-17 OOM
  report's belt-and-braces rule, demoted to pressure-triggered by
  #1063). Docs-only
  stages count toward the cap (their commits trigger hook builds —
  the incident's main memory source). The memory gate protects
  memory; this cap protects latency and the inactivity cutoffs.
  Evidence: the 2026-11-17 OOM (same report); 2–3 staggered agents
  is operator-validated practice on this box. This bullet supersedes
  the interim rule in that report's §5.
- *Scratch never lands on host tmpfs (#1043)*: host `/tmp` is tmpfs
  (RAM-backed) — scratch written there consumes `MemAvailable`
  directly and is a shared, unbounded resource (the 2026-11-19 ENOSPC
  incident: a foreign agent's 5.8G scratch dir on a 6G tmpfs killed
  three bench runs instantly). Large agent scratch (bench batteries,
  bisects, mutants shards, multi-hundred-MB logs) routes through
  `scripts/memory-gate.sh`'s TMPDIR redirection (both modes already
  redirect an unset-or-`/tmp` TMPDIR to `/var/tmp`) or creates its
  scratch under `/var/tmp` explicitly; nothing writes unbounded
  scratch under `/tmp`. Evidence:
  `.artifacts/reports/2026-11-19-build-cache-evaluation-report.md` §3.
- *Measurement/bench worktrees live outside the standard layout
  (#1042)*: bench worktrees whose only purpose is keeping a warm
  `target/` for an in-flight battery **live outside the
  `taskboard-WT-*` glob** (e.g. `/var/tmp/taskboard-bench-<arm>`,
  created with plain `git worktree add` / `git clone`), never under
  the standard worktree layout — the worktree-doctor sweep cannot
  distinguish them from disposable worktrees of record (the
  2026-11-19 incident: `taskboard-WT-bench-bench-b` swept
  mid-battery, invalidating its paired-load design;
  `.artifacts/reports/2026-11-19-build-cache-evaluation-report.md`).
  They are ephemeral the same way: the agent that finishes the
  battery removes them.

* 3. Stage-exit verification (the dispatcher never trusts reports)

Before dispatching stage N+1, the dispatcher verifies stage N's landed
state directly in the worktree: commits present (=git log
origin/main..HEAD=), tree clean, gate evidence re-runnable. A stalled
or quota-cut stage is *completed by the dispatcher from the worktree
state*, never re-dispatched blind — resumption from landed commits
cost minutes; blind re-dispatch costs hours and can duplicate or
contradict landed work.

* 4. Resume over redo

A stopped agent that retains context (inactivity, quota) is resumed
with a state-check message ("commit X is landed; continue from Y"),
not replaced: the replacement re-reads everything and re-derives
decisions the original already recorded. If resumption is impossible
(quota exhausted), the fallback is a fresh agent seeded with the
landed-state summary, not a from-scratch prompt.

* 5. Prompt organisation (what a dispatch plan must carry)

- *Verbatim prompts*: every stage prompt is complete and paste-ready;
  a reader who has never seen the origin can dispatch from the
  document alone (the house bar, dispatch-plan template).
- *Chunk-specific traps, not generic advice*: each stage-3 prompt names
  the invariants that could silently break, from the origin's facts
  (the round-7 precedent: "the exact files, the tests that must not
  have been weakened, the diff-shape rules").
- *The discipline carried verbatim*: the long-command rules and the
  scope split are restated in full at the top of every stage prompt —
  an agent that must read them from another file will not.
- *Cross-cutting constraints bind all stages and are restated per
  prompt*: blind-authoring constraints (phase-2 pilot), retrofit
  posture ("describe what exists, never fix"), epistemic rules
  ("record reality, never invent rulings") — a constraint stated only
  in the plan preamble was observed to be missed by stage agents that
  never re-read the preamble.
- *Coverage-gate steady states are stated per phase kind*: retrofit
  plans expect FOUND on every row (MISSING = plan-vs-code defect);
  remediation plans expect new rows FOUND with pre-existing debt
  excluded — bounded by the *byte-identical-baseline* check (the
  MISSING set must equal the pre-chunk baseline; run the gate against
  the pre-amendment plan blobs to prove it). Never let "gate green"
  be demanded where the honest steady state is "gate unchanged".
- *Beware shell exit codes in evidence loops*: =cmd | tail -n= reports
  tail's exit. Capture =cmd; echo exit=$?= without pipes (observed
  false-green in the phase-3 verification).

* 6. Worktree & environment hygiene

- *Start point law (#1185, 2026-11-23)*: a standard-layout worktree is
  created with an explicit fetched start point —
  =git worktree add -b <branch> <path> origin/main= — never the bare
  =-b <branch> <path>= spelling, which branches off the *local* =main=
  ref; mid-round, local =main= lags the fetched tip and the fresh,
  zero-commit worktree then sits strictly below =origin/main=, exactly
  the shape the worktree-doctor's containment removal targets (the
  grace window in =scripts/worktree-doctor.sh= is the backstop, not
  the rule).
- The house AGENTS §8 worktree rules all apply; additionally, from the
  rollout's one environment incident: after ANY unexpected worktree
  anomaly (a foreign stash surfacing, a checkout of an unexpected
  commit), verify the branch's commits contain no foreign content
  (diff the commit list against the ledger, check for unfamiliar
  files) before proceeding, and report the incident honestly. The
  phase-5 chunk-6 stash incident was resolved with =git reset --hard
  HEAD= after confirming all local commits were landed.
- Teardown anchors to the main checkout with an absolute path and is
  confirmed via =git worktree list= (AGENTS §8) — the dispatcher does
  this, not the stage-3 agent (see §2).
- *Measurement hygiene (#1160, 2026-11-22)*: wall-clock numbers from
  this box are only meaningful with load context, and an idle box is
  the *only* recording condition. A timing captured while another
  suite, build, or coverage run holds the box (check the flock
  holder and MemAvailable first) is discarded, not recorded with a
  caveat. Where measurements are recorded: runtime/benchmark reports
  under =.artifacts/reports/= (each carries the box-load context of
  its run: what else was running, MemAvailable, gate state); the
  dispatch law's own timing claims (the L-chunk durations in §7, the
  suite floors quoted in incident reports) cite those reports rather
  than quoting raw numbers inline. A number whose run context cannot
  be stated does not get written down.

* 7. Chunk sizing & compression

- Default: the full three-stage protocol per chunk. *Tiny docs-only
  chunks* (a wording flip, a status-line move — one coherent edit
  across ≤4 files) may be run *compressed*: the dispatcher acts as
  planner and implementer directly — a plan committed first, the
  edits, the full gate suite, then the PR — stating the compression
  choice in the plan. Three subagent sessions for a wording flip is
  ceremony, not discipline. Phase 6 of the framework rollout was run
  this way.
- Feature chunks (any code) always get the full protocol.
- L-sized chunks run 90–210 minutes of stage-2 work without stalling
  under this discipline (observed: chunk 3's resume at rung 2 of 6,
  chunk 5's single-pass completion) — size is not the stall risk;
  silent waits are.

* 8. Failure-mode playbook (observed, with resolutions)

| Incident | Signal | Resolution |
|---|---|---|
| Stage-2 stall on coverage run | agent dead, commits landed | dispatcher verified worktree, ran the full suite itself, proceeded to stage 3 |
| Stage-3 stall on CI watch | agent dead, PR already open | dispatcher watched checks, tore down; report reconstructed from the PR |
| Quota cut mid-ladder | quota error, rung k of n landed | SendMessage resume with state check; agent finished all rungs |
| Review stall before push | agent dead post-fix commits | dispatcher verified fixes, pushed, opened PR |
| CI flake on docs-only PR | one test fails, passes on re-run | comment on the flaky-test family issue, =gh run rerun --failed=, re-watch |
| Foreign stash in worktree | unexpected conflict during baseline check | reset --hard after verifying commits landed; incident reported; foreign content verified absent from diffs |
| Agent died waiting on the gate flock | agent dead while the lock was held by another session | landed work intact — the dispatcher re-runs the gate itself and proceeds (the pre-#879 shape of the stall-on-coverage row; now prevented by the §2 flock-deferral rule) |
