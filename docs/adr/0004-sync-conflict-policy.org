#+title: ADR 0004: Sync Conflict Policy
#+options: toc:nil

- *Date:* 2026-10-08
- *Status:* Accepted
- *Deciders:* Viktoria Pogrzebacz

* Context

The offline-first sync model allows local edits while disconnected; a
later sync must reconcile them against remote Deck changes. Deck
constrains the design space:

- No write-side preconditions (=If-Match=), so optimistic concurrency on
  the wire is impossible.
- =lastModified= / =deletedAt= are entity-level, seconds-resolution epoch
  integers; cards have *no* =deletedAt= (deletion is observable only as
  absence from listings or a 404). Boards and stacks are soft-deleted with
  a real =deletedAt=.
- Card PUT is a full round-trip; sparse PUTs reset omitted fields, so
  every write is full-send anyway.
- Remote ids are only unique per board; local ids are client-side
  UUIDv7 generated before any remote binding exists.

* Decision

** Per-field last-writer-wins, local clocks vs entity-granular remote

Every editable field of a domain entity carries a =DateTime<Utc>= write
clock (=TaskClocks= etc.). Local edits stamp only the touched fields;
adopting a remote version stamps every field with the remote
=lastModified=. Per field:

#+begin_quote
the remote value wins ⟺ =remote.last_modified > field_clock= (strictly);
ties and older remotes keep local.
#+end_quote

The tie-break is deterministic (local bias): Deck's second-resolution
timestamps naturally lose to sub-second local edits made in the same
second. This boundary is pinned by property tests (and kills the
strict-vs-inclusive comparison mutants in =merge.rs=).

Documented limitation — *granularity data loss*: because the remote side
is entity-granular, a remote entity-touch newer than a local field edit
reverts that field even when the remote change touched a different field
(e.g. a remote description edit at 10:06 overwrites a local title edit
from 10:05 with the server's unchanged title). This is inherent to Deck's
timestamps; a Phase 4 docker-tier scenario pins the behavior so it stays
intentional and observable. Alternatives (single entity-level mtime
locally; OR-set labels) were rejected as materially worse or premature
(see backlog).

** Composite and set-valued fields

- *Position* (=stack= + =order=) shares one clock: a move is one user
  intent, so concurrent move+reorder resolve as a unit — never a
  stack-from-A-order-from-B chimera. Interleaving of two devices'
  orderings is a documented limitation.
- *Labels* merge as one field (whole-set LWW). Add-wins OR-set merging is
  backlogged.

** Deletion

- Boards/stacks/labels: the remote =deletedAt= is a timestamped fact and
  LWWs against the local side's latest activity exactly like any field.
- Cards: no remote delete timestamp exists, so an *observed remote
  absence always beats concurrent local edits* (delete-wins tombstone,
  stamped with the observation time). Automatic resurrection would create
  zombie tasks reappearing after every sync. Resurrect-as-new-card is
  backlogged.
- Local card tombstones participate in the normal LWW: a strictly newer
  remote edit resurrects the task (and drops the pending delete op); an
  older remote edit leaves the tombstone standing, and the pending delete
  re-pushes over the remote change. Deck's cache lag cannot resurrect a
  pushed delete: the tombstone clock is at least as new as any stale
  listing entry.

** Push echoes are adopted unconditionally

After a create/update push, the server echo is adopted as-is (not LWW)
with clocks advanced to =max(local, echo.last_modified)=. The server
normalizes what we just wrote (trims, reformats, truncates timestamps to
whole seconds); LWW against a seconds-resolution echo would let the local
sub-second values win forever and the normalization would never land. A
=reorder= push returns no usable echo — the op completes and the next
pull reconciles.

** The engine executes the merge

The sync actor only fetches, pushes, maps DTOs into domain-owned remote
views, and reports raw observations plus push outcomes
(=SyncReport=). The state engine runs the pure policy
(=apply_sync_report=) against its authoritative current state, so user
edits landing during a sync run cannot be lost to a stale-state race —
and 100% of the policy stays inside =taskboard-domain=. Merge functions
never read clocks or generate ids: time and ids are injected data.

** Processing order (normative)

Push outcomes first (they establish new baselines), then board → stacks
→ labels → tasks (remote entity adoption precedes task label-set
resolution), then presence reconciliation for bound-but-absent entities,
then the sync-status transition. Re-applying an unchanged snapshot emits
no persistence actions (idempotence is a property-tested invariant).

** Absence correctness rests on a snapshot-completeness contract

The =RemoteBoardSnapshot= in =SyncReport::Completed= must be the sync
actor's complete view of the board at sync time — absence from it means
absence on the server. Enforced in Phase 4 actor tests; a partial
snapshot would silently tombstone live tasks.

* Consequences

- *Positive:* Deterministic, total, clock-free policy (Miri- and
  mutants-friendly); disjoint field edits survive; deletion semantics
  are well-defined in both timestamped and absence-only worlds.
- *Negative:* Clock skew (all comparisons are cross-machine wall clock;
  no NTP assumed) can misorder near-simultaneous edits — the
  strict-comparison with tie-to-local bias is the documented behavior,
  not a fix.
  Entity-granular remote timestamps cause the documented field losses
  above. Both are backlogged for revisit if real-server use shows
  revert-on-sync symptoms.
- *Enforcement:* Property tests in =crates/taskboard-domain/src/merge.rs=
  (the per-entity algebra) and
  =crates/taskboard-domain/src/pipeline.rs= (the fixed-order composition:
  idempotence, processing order, convergence, rule outcomes); mutation
  testing targets both with zero expected survivors.

* Amendment 2026-10-11 — field-wise board title (WI-3)

Boards move from adoption-only to *field-wise title merging* as part of
the =boards rename= CLI verb (WI-3, M1-exit report §4 B). The
whole-entity freshness gate and every field of =adopt_board_if_newer=
stay exactly as they were — archived, color, tombstone still adopt
whenever the remote entity stamp is strictly newer than =remote_seen=
(boards have no local color/archive verbs, so there is nothing local to
defend there). Only the *title* becomes field-wise:

- =Board= grows =BoardClocks { title }= (room for the color/deleted
  clocks their verbs will need). =CreateBoard= stamps creation; the
  adoption constructors stamp =last_modified=.
- =merge_board= wraps the adoption result: when the remote entity stamp
  is *not* strictly newer than =local.clocks.title= (the =merge_stack=
  rule for one field), the local title and its clock survive.
- Storage migration =0002= adds =boards.ck_title= with the *epoch
  default* — "never locally written" — so every pre-WI row keeps
  today's remote-wins behavior bit-for-bit (pinned by an upgrade test).
- Post-read intent protection: a queued =RenameBoard= op keeps the
  local title against the same-cycle pull (=pending_board_intent= /
  =keep_board_title=, the stack pair).
- Push: =RenameBoard= is a full-send =update_board= PUT (like every
  Deck write), the echo lands via =adopt_board_after_push= (title from
  the echo, =remote_seen=/=clocks.title= advanced to the echo stamp),
  and board writes group *before* stacks in the push planner.

The remaining granularity class is unchanged: a remote title change
landing between our read and our push wins after the op drains — the
same whole-entity remote-wins every other board field already accepts
(the "field-level merge refinement" backlog entry owns the general
refinement).

* Amendment 2026-10-18 — boards complete the per-field merge (chunk 15)

The 2026-10-11 title amendment generalizes to *all four board fields*:
=BoardClocks = { title, color, archived, deleted }= (#132/#177), and
=merge_board= keeps the local value per field while
=remote.last_modified <= field_clock= — remote wins strictly, per
field, exactly like stacks and labels. Details:

- The four local verbs stamp only their own clock: =SetBoardColor= →
  =clocks.color=, =SetBoardArchived= → =clocks.archived=,
  =DeleteBoard= → =clocks.deleted=; the edit verbs converge on one
  full-send op, =LocalOp::UpdateBoard= (renamed from =RenameBoard= to
  tell the full-send truth; the storage tag backfills =rename_board=
  → =update_board= in migration 0005 — one representation, no alias).
  =MaterializedOp::UpdateBoard= keeps the bound+live gate;
  =MaterializedOp::DeleteBoard= is delete-dominant like stacks and
  subsumes the board's other queued ops.
- *Tombstone defense:* =deleted= merges field-wise like the others,
  and the tombstone never clears without an explicit restore verb
  (none exists): a pulled live board does *not* resurrect a
  locally-deleted board whose =clocks.deleted >= remote.last_modified=.
  A remote edit strictly newer than our tombstone adopts the remote
  *fields* but the board stays deleted until restore lands.
- Echo: =adopt_board_after_push= advances every clock to
  =max(local, echo.last_modified)=. Delete pushes finalize through a
  separate helper, =adopt_board_after_delete_push=: the tombstone is
  kept (=deleted: true=, deleted clock advanced), the binding is
  cleared, =remote_seen= moves to the echo stamp. The non-delete
  helper hard-codes =deleted: false= and must not be reused for
  deletes.
- *Reset is local-only.* =ResetBoard= clears a board's content,
  outbox, reminder facts, and — mandatorily — its *sync validators*:
  with warm validators the next conditional pull could answer 304 and
  the reset would silently not re-materialize. Clearing the validators
  forces an unconditional refetch; a bound board re-adopts from the
  next pull under fresh local ids. Nothing about a reset is pushed —
  pushing tombstones would destroy remote content, which is
  =DeleteBoard='s job.
- Board deletes cascade locally at command time (stacks, tasks,
  labels, per-task reminder rules) and cancel — never push — the
  children's pending ops (Deck cascades server-side; per-child pushes
  would chase 404s). Binding survives on the tombstone until the push
  confirms.
- The entity-granularity hazard is unchanged and now wider: a
  full-send =UpdateBoard= PUT can overwrite a concurrent remote edit
  to a *different* field that lands inside our pull→push window, for
  any of the four fields. Same documented Deck limitation as before —
  the "field-level merge refinement" backlog entry owns it.
