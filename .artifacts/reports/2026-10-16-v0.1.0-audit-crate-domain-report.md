## 4. Axis F — data-model fit (against D1–D4, deck-roundtrip vocabulary)

### 4.1 Merge-policy field granularity vs D1 — the native family is per-field

Shapes quoted verbatim (plan D5 requirement):

- `TaskClocks` (`entities.rs:49-66`): eight per-field
  `DateTime<Utc>` clocks — `title`, `description`, `duedate`, `done`,
  `position` (composite `stack`+`order`), `labels` (whole-set),
  `archived`, `deleted`. `StackClocks` (`:70-77`) and `LabelClocks`
  (`:81-88`) analogous; `BoardClocks` (`:94-97`) title-only with an
  epoch constant (`:99-107`).
- `merge_task(local: &Task, remote: &RemoteTask, ctx: &RemoteIndex) -> Task`
  (`merge.rs:170`): each field's verdict is
  `remote_wins(ts_r, local.clocks.X)` (`merge.rs:70-73`, strict `>`),
  stamping only the touched clock — per-field LWW exactly as the
  deck-roundtrip §5 describes.
- `LocalOp` (`outbox.rs:22-51`) is id-scoped and field-less (14
  variants); `PendingOp` (`:55-62`) = `op_id` + `op` + `queued_at` —
  matching the deck-roundtrip §5 push-side note ("TaskClocks already
  knows which fields changed").
- Identity map:
  `task_by_board_card: HashMap<(RemoteBoardId, RemoteCardId), TaskId>`
  (`pipeline.rs:394`) — the same `(board, remote card id)` keys the D1
  document uses.
- The self-clobber guard is bool-per-field:
  `PendingTaskIntent` (`pipeline.rs:90-101`, 8 bools) derived by
  `pending_task_intents` (`:104-151`, protection keyed on
  `queued_at > read_at`) and re-applied value+clock by
  `keep_task_intent` (`:157-205`).

**Verdict: the D1 sidecar fits the existing algebra** — document-embedded
per-key clocks mirror `TaskClocks`; a `merge_task` sibling folding
document entries *after* the native merge and *after*
`keep_task_intent` slots into the fixed order without reshaping
anything. The friction is the **extension seam**, finding **F3-05**:
three parallel structures (entity fields, `TaskChanges` changeset,
intent-guard flags) must grow the app-only field family in lockstep,
and nothing today marks where.

### 4.2 `SyncStatus` vs multi-board (D2) — finding F3-04

`AppState` is deliberately map-shaped ("the map shape keeps multi-board
support additive instead of a rewrite", `state.rs:25-27`), but the sync
summaries are global single slots: `sync: SyncStatus` (`state.rs:39`)
and `last_updated` (`state.rs:42`); `SyncStatus.pending_ops: u32`
(`state.rs:47-54`) counts the whole outbox; and the domain outbox types
carry no board scope (`outbox.rs:22-62`). Today the single-binding
invariant makes the global slot truthful; D2 will need per-board status
(or an explicit accepted simplification) and op→board routing — the
storage layer's `board_id` outbox column (future-directions §4 D2) is
the prepared seam.

### 4.3 Task identity/timestamps vs recurrence (D3) and undo (D4) — accepted facts

- No recurrence slot exists on `Task` (`entities.rs:156-184`) — D3 adds
  it; the `TaskClocks` per-field pattern makes that additive, and the
  D1 vehicle carries the parameters meanwhile (deck-roundtrip §6 row
  "Recurrence parameters").
- `ReminderOffset` is due-anchored by construction (inner `TimeDelta`
  ≤ 0, sole non-zero constructor `before`, `reminders.rs:19-30`) —
  recurrence rule objects will be new shapes, not contortions of this
  one.
- Tombstone finality does **not** conflict with undo: `deleted` is an
  ordinary clocked field — a later local write resurrects (R5,
  `merge.rs:227-234`) — and `finalize_pushed_task_delete`
  (`merge.rs:337-344`) clears the remote binding but keeps the clocked
  field semantics. Undo-as-new-edit is naturally supported; a command
  journal (D4's leading option) would replay `plan_command`, which is
  total and pure (`command.rs:240`). Friction: low. No finding; the D4
  round decides.
