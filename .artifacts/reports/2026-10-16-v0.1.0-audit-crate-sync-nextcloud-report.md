## Axis E — crate & module factoring, boundaries

**Boundary verdict (AGENTS §2)**: clean. The one judgement call the
plan flagged — `lib.rs:10`'s "This crate is pure IO: it holds no
application state of its own" vs `PullCache`/`LoopState`
(`actor.rs:136-160`) — resolves as: the claim **holds in the
architectural sense**. `PullCache` holds wire-DTO copies used solely to
fill `304`s (`fill`, `actor.rs:776-794`), is declared "a rebuildable
optimization" in the module doc (`actor.rs:10`) and bounded by the
cold-cache rule there — one unconditional refetch, never a partial
snapshot (`actor.rs:133-135`) — is cleared on `SetBoard`
(`actor.rs:199`), and a cold cache degrades to one unconditional
refetch, never a partial snapshot (`actor.rs:787-791`). `LoopState` is
loop control state (target/streak/offline/floor). No *application* data
lives here — every durable fact arrives via `read_state`. The doc line
is defensible; one clarifying clause would prevent misreading (F6-11).

Cross-crate seam facts (contract recorded, behavior not adjudicated):
engine ↔ actor = `SyncStateReader` in, `SyncReport`s out on an mpsc,
`SystemEvent`s on a broadcast the actor **publishes** network events on
and **consumes only `Shutdown`** from (`actor.rs:225-245` — the actor
is the network authority by construction); `SetBoard`/`SyncNow`/`Detach`
in on the command mpsc. The single `select!` (`actor.rs:190`, biased,
three arms + post-cycle nudge absorber `actor.rs:250-266`) — contract
recorded; cancellation-safety audit is **chunk 9's**.

Secondary factoring questions (pro/con feeds the split evaluation,
plan §3):

- **`push_exec.rs` weight** — 2 678 lines, the crate's largest file,
  mixing one `impl PushExecutor` block (production 917 lines: overlay +
  group dispatch + create/update/move/delete arms) with the crate's
  largest test suite (1 761 lines). The production half has three
  identifiable strata: `BindingOverlay` (binding math), `execute`'s
  per-`MaterializedOp` decision table, and outcome-assembly helpers
  (`primary_outcome`/`all_applied`/`classify`, `push_exec.rs:843-906`).
  A `push_exec/` module tree (`mod overlay; mod execute; mod outcomes;`
  with the per-kind arms grouped) is mechanical and needs no API change
  — recorded as **O3** in the evaluation (F6-10).
- **`poll.rs` vs `backoff.rs`** — two backoff homes, deliberately
  separate concepts (client retry budget vs cycle failure cadence), each
  documented as such (`poll.rs:2-8` names the distinction). But the
  doubling-and-saturating kernel is written twice (`delay_at`,
  `backoff.rs:56-67`; the loop inside `poll_backoff`, `poll.rs:22-27`)
  and `poll_backoff` adds the floor concept the client budget lacks.
  Verdict: keep two policies, share nothing for now — the kernel is 10
  lines and the two have different edge semantics (floor, saturating
  return path). Feeds the split evaluation's criterion (e) (plan §3): a
  split would carry these
  apart naturally (retry budget → client crate; poll cadence → actor
  crate).
- **`mapping.rs` placement** — everything in it is actor-side
  *semantics* (domain `Remote*` views, push classification,
  fetch-before-write body building) that happens to produce/consume
  client types. Nothing in the client half imports it. Under a client
  extraction it stays with the actor crate — the placement question
  dissolves rather than needs answering.
- **`color.rs`/`ocs.rs` folds** — verdict: keep. `color.rs` is a
  self-contained validated-newtype concern (strict writes, lenient
  reads) with its own visitor; `ocs.rs` is the envelope schema. Folding
  either into `model.rs`/`client.rs` blurs the one-concern-per-module
  grain for ~200 saved lines.

### Axis E headline — the Deck-client vs sync-actor split evaluation

**1. Coupling-point inventory** (beyond the plain pub API — the
"not vibes" evidence):

| # | Coupling point | Where | Nature |
|---|---|---|---|
| 1 | `Fetch<T>` shape | `fill()` matches `fetched.data`/`.validators` (`actor.rs:776-794`) | structural (type shape) |

| 4 | `NewCard`/`BoardChanges`/`StackChanges`/`LabelChanges` | mapping builds them from domain shapes (`mapping.rs:212-261`) | type flow actor→client |

Every coupling point crosses the seam **through declared types**; there
is no hidden state, no `pub(crate)` backchannel from client to actor
(the one `pub(crate)` item in the client half, `decode_envelope`

client-internal). Test-file dependencies confirm the seam:
`tests/contract.rs` + the `model`/`color`/`ocs`/`backoff`/`client`
in-file suites need **only the client half**; `actor_wiremock`/
`e2e_hermetic`/`it_docker`/`it_live` need both; `push_exec`'s in-file
suite needs the client half through the executor only.

**2. Options evaluated** (fixed criteria a–f, plan §3 item 4):

- **O0 — status quo** (module boundary as the seam). (a) no compile
  firewall, but the workspace builds one binary and CI builds all
  crates every run, so firewall value is incremental-build latency and
  concept only; (b) test tiers already split cleanly by file; the
  one-off mutant box covered both roles in one run — a convenience, not
  a property; (c) zero friction for any named wave — the D1 sidecar
  Wave-1 surface **already landed** in-place (§Axis F); (d) AGENTS §2's
  one-line rule stays as-is (with its "WebDAV" wording problem,
  F6-12); (e) zero cost; (f) zero kiosk impact. *Con*: the crate
  description says one role ("API actor") while the crate is two; every
  future Deck wire change keeps touching the sync-actor crate's churn
  budget.
- **O1 — extract `taskboard-deck-client`** (client, model, color, ocs,
  backoff, error ± `tests/contract.rs` + `tests/fixtures/deck/`;
  mapping/actor/push_exec/poll remain). (a) the firewall localizes the
  crate's *most-churned* code: of the crate's top-30 churn entries
  (`§churn`), the client half + its contract tier hold client.rs 13 +
  contract.rs 13 + lib.rs 12 + model.rs 9 + common/mod.rs 11 ≥ 58
  touches vs the actor half's actor.rs 11 (+ push_exec/poll below the
  top-30 cut, <9 each) — wire-format discovery is where the change
  traffic is; (b) contract tier + tier-0 fixtures become the client
  crate's own suite; mutant boxes can target roles separately (the 44
  survivors split 8 client-half / 36 actor-half); (c) Wave-1 sidecar
  work would land in a client crate (surface already present — §Axis
  F); a second connector sees exactly which parts are Deck-specific
  (ADR 0010's vocabulary made physical); the kiosk/IPC wave is
  untouched either way; (d) AGENTS §2 gains one sharp row and sheds the
  "WebDAV" ambiguity (the client crate is a Deck REST client, plainly);
  (e) real but bounded cost: `DeckClient`/`DeckColor`/`DeckError`
  imports move in `taskboard-app` (`bootstrap.rs:68,107,548`,
  `commands/boards.rs:21`, `config.rs` doc refs, `secrets.rs` doc refs)
  — a transition `pub use` in `taskboard-sync-nextcloud` defers that
  rewrite; +1 workspace crate against the project's boundary
  discipline; (f) no kiosk impact — the workspace ships one binary;
  crate partition does not change the linked result (verified
  reasoning: no feature gates, no dylib targets; `taskboard-app` is the
  only bin).
- **O2 — trait seam only** (port trait between actor and client). The
  engine-side connector blindness ADR 0010 asks for **already exists**
  at the engine boundary (`SyncStateReader`/`SyncReport`; no
  production `taskboard-state` dep — verified). Between actor and
  client a trait would isolate the HTTP surface while the actor's
  *semantics* stay Deck-shaped (dead-board 404/403 dialect,
  fetch-before-write wire contracts, `RateLimited` floor) — an
  abstraction with one implementation and no second one on the horizon
  whose shape it could be validated against (the file-sync connector
  report's own stance: the engine stays connector-blind, the connector
  is a translator — no port between translator and its HTTP client is
  named there). *Verdict*: premature; adds indirection now, would be
  *re-derived* anyway if a second Deck-like consumer ever appears.
- **O3 — further split of the actor half** (`push_exec` module tree or
  crate). As a module tree it is a no-regret readability step inside
  the crate (F6-10); as a crate it buys nothing — push_exec is
  meaningless without both mapping and client, and its test suite is
  the crate's strongest mutant catcher. *Verdict*: keep O3 as the
  in-crate valve, not a crate.

**3. Recommendation (exactly one): O1 — extract
`taskboard-deck-client`.**

The two roles are today separated only by a module convention that
nothing enforces, the crate's change traffic concentrates on the client
half (≥58 of the visible top-30 touches, `§churn`), the hermetic
contract tier is already a self-contained client-only suite, and the
role-split removes the naming debt (a "sync actor" crate that is 45%
Deck HTTP client by line count) in the same motion. O2 is rejected as
premature; O0 is viable but leaves the highest-traffic half unshielded
and the description drift in place; O3 is adopted as an in-crate
companion step regardless (F6-10).

- **Consequences for the kiosk/IPC wave**: none on codegen or memory
  (single shipped binary; crate partition does not change the linked
  result), none on the IPC surface (this crate is behind the engine),
  and none on the sync-cycle budgets (chunk 13's row 5 facts are
  partition-independent). The wave the split actually serves is the D1
  sidecar Wave-1 (client-surface extension) and any future second
  consumer of the Deck API — not kiosk/IPC.
- **First concrete step if accepted** (recommendation sketch, not a
  migration plan, origin §6): create `crates/taskboard-deck-client`
  moving `client.rs, model.rs, color.rs, ocs.rs, backoff.rs, error.rs`
  plus `tests/contract.rs` and `tests/fixtures/deck/`;
  `taskboard-sync-nextcloud` keeps `mapping.rs, actor.rs, push_exec.rs,
  poll.rs` + the actor/e2e/it tiers, depends on the new crate, and
  re-exports `DeckClient`/`DeckError`/`DeckColor` for one transition
  so `taskboard-app` imports move in a later, separate commit.
