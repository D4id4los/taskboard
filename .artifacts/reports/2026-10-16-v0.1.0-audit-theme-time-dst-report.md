### The frozen grep set (plan §3.1, D2) and what it actually matched

The plan froze five greps (W1–W5) with the pathspec
`'crates/*/src/**/*.rs'`. Executed verbatim at the tag, that pathspec
**structurally excludes every file directly under `src/`** — in git
pathspec semantics `**/` requires at least one directory level between
`src/` and the file, so `clock.rs`, `reminders.rs`, `actor.rs`,
`merge.rs`, `repo.rs`, `lib.rs`, `presentation.rs` (precisely the
files that hold the time architecture) are invisible to it. Verified
empirically:

```sh
# verbatim W2 run at the tag: matches ONLY domain/src/test_support/*.rs (17 hits)
git grep -n -E 'timestamp_opt|...|TimeZone' v0.1.0 -- 'crates/*/src/**/*.rs'
# same pattern, one component added: finds the production sites it missed
git grep -c 'parse_from_rfc3339' v0.1.0 -- 'crates/*/src/*.rs' 'crates/*/src/**/*.rs'
#   → crates/taskboard-app/src/cli.rs:1, crates/taskboard-domain/src/reminders.rs:1
```

Verbatim-run hit counts (recorded so stage 3 can reproduce both runs):
**W1 = 9, W2 = 17, W3 = 8, W4 = 0, W5 = 4** — all confined to files in
subdirectories of `src/` (W4's seam patterns match no subdirectory file
at the tag — every `SystemClock`/`dyn Clock` hit lives directly under
`src/`, which is exactly why the verbatim pathspec blinds W4).

Per D2 ("any extra pattern added during execution is recorded in the
report's method section with rationale; census exhaustiveness disputes
resolve against the recorded command set"), execution used the
**corrected pathspec union** — `'crates/*/src/*.rs' 'crates/*/src/**/*.rs'`

### Seam-vs-direct rubric (D3, applied verbatim)

`SEAM` / `DIRECT-JUSTIFIED` (triggers (i) presentation-only *and* (iii)
no injectable seam in the component) / `DIRECT-FINDING` (trigger (a)
persists-or-compares, (b) seam-exists, or (c) second time authority) /
`MONOTONIC-OK` (finding only on wall↔mono mixing) / `CONVERSION`
(DST semantics judged in §scenarios).

### Hop-7 verdict — the display second authority

The CLI and UI read the wall clock outside the engine's seam, but both
use it **only to classify state for rendering** (`overdue_tasks` /
`due_soon` set membership — the domain's own pure functions), never to
mutate, persist, or compare against stored instants. The engine's
reminder judgment (hop 4) and the display judgment can therefore
disagree for at most the read-interval gap: the UI re-derives at ≤100
ms cadence plus signal-driven refreshes; the engine fires on its 30 s
tick. Concretely: a task can render `overdue` in the banner up to one
tick (~30 s) before the reminder actually fires — and this split is
the *documented* product semantics ("board truth, not nagging
policy", reminders.rs:411-418; mute applies to firings, not the
banner). No ordering anomaly can persist or compound: both sides
re-derive from the same `ArcSwap` state. **Holds; no finding.**

### Round-trip fidelity verdict (hop 5, plan §3.2 question)

**Resolved: byte/parse-identical through every v0.1.0 surface; the
double-fire hazard is API-only (F11-03, P3).**

- The evaluator's recomputed occurrence after a restart is
  `duedate + offset` over values reloaded from storage. The duedate
  round-trips losslessly (`to_rfc3339` writes, `FromStr` decodes —
  nanosecond-preserving both ways; pinned by
  `persisted_state_roundtrips_through_sqlite`, green at the tag).
- The delivery proof's occurrence key is the evaluator's own instant,
  written `to_rfc3339` and PK-matched on reload — exact-equality
  (`reminders.rs:231-234`) holds.
- **Hazard (i) — offset truncation**: `offset_seconds INTEGER` is
  `rule.offset.as_duration().num_seconds()` (truncates toward zero,
  repo.rs:983-989), and reload rebuilds via
  `TimeDelta::try_seconds` → `ReminderOffset::before` (repo.rs:358-362).
  A sub-second in-memory offset (constructible only through the public
  API `ReminderOffset::before(TimeDelta::milliseconds(-500))`) would
  persist as `0`, shift the recomputed occurrence by 500 ms on reload,
  miss the exact-equality proof, and re-fire. **Reachability: not
  constructible through any v0.1.0 product surface** — the CLI flag
  and config both go through `parse_before`'s whole-second grammar, and
  `set_on` negates it (commands/reminders.rs:112-115). F11-03 records
  it as the library-API hazard it is.
- **Hazard (ii) — rfc3339 sub-second round trip**: lossless. Chrono's
  `to_rfc3339` emits sub-second digits when present and
  `parse_from_rfc3339`/`FromStr` restore the exact instant; the snooze
  key (reminders.rs:160-183) and both storage columns share this
  codec. No truncation exists on the reminder path (the only seconds
  truncations are the Deck push wire — compensated by echo
  normalization — and the offset column above).

## §scenarios — DST & timezone verdicts (template per plan §3.3)

### S1 — spring-forward gap (occurrence inside a nonexistent local hour)

- **Precondition**: a task due (or a reminder occurrence falling) at a
  wall time that a host zone skips (e.g. 02:30 local on a
  spring-forward night).
- **Transition event**: the zone transitions; the stored instant's
  local rendering would land inside the gap.
- **Code path walked**: the *entire* scheduling path is
  instant-typed: storage of `duedate` (`Option<DateTime<Utc>>`,
  entities.rs:166; its write-clock field `DateTime<Utc>` :55),
  occurrence arithmetic `checked_add_signed` (reminders.rs:315),
  predicate `effective <= now` over `T<U>` (reminders.rs:398-402),
  tick read `clock.now() -> T<U>` (actor.rs:787).
- **Representation at each step**: instant everywhere. A local wall
  time is *never constructed* on any scheduling path — the W2 negative
  grep shows zero `and_local`/`from_local`/`FixedOffset`/`LocalResult`
  uses, and the only `Naive` construction in the workspace is the CLI
  bare-date parse, which immediately becomes UTC midnight
  (cli.rs:249-254) with no zone input at all.
- **Outcome**: **holds by representation.** A nonexistent local hour
  is unrepresentable in the system's data model; the occurrence is the
  UTC instant whose local rendering happens to fall in the gap, and it
  fires exactly once, on time, regardless. (D4: proven from the
  negative grep + the end-to-end `T<U>` typing, not chrono's docs; the
  gap is unobservable to the code.)

### S2 — fall-back overlap (ambiguous local wall time)

- **Precondition/transition**: a local wall time that occurs twice
  when the zone falls back.
- **Code path walked**: identical to S1 — and additionally there is no
  wall→instant *resolution step anywhere* that could pick the wrong
  side of the overlap.
- **Representation**: instant everywhere; the ambiguity is created
  only when *rendering* an instant into a local zone (which the
  v0.1.0 product never does — display is UTC, S4c).
- **Outcome**: **holds by representation** — same proof shape as S1:
  nothing in the tag's code can observe the ambiguity.

### S3 — timezone change while a reminder is scheduled (incl. catch-up)

- **Precondition**: rule/default reminder stored against a task's due
  instant; host zone then changes (travel, config change).
- **Transition event**: `TZ`/zoneinfo changes under a running or
  restarted daemon.
- **Code path walked**: firing instants are `duedate + offset` in
  `T<U>` (reminders.rs:314-318) — UTC-anchored, **unchanged by the
  zone change**; evaluation compares against `clock.now()` (also
  `T<U>`). Catch-up: the first tick is immediate on boot
  (`next_tick = Instant::now()`, actor.rs:343, armed iff
  `reminder_cfg.enabled`), and `due_firings` has **no "too stale to
  fire" cutoff** — the predicate is purely `effective <= now &&
  !delivered` (reminders.rs:398-402) — so occurrences that passed
  while the daemon was down fire on the first post-boot tick.
  Re-anchoring ("9:00 in the *new* zone") has no code path: there is
  no local-time representation to re-anchor.
- **Representation**: instant at every hop.
- **Outcome**: **holds**; product fact recorded: a "9:00 local" intent
  stays the *old* zone's 9:00 forever (see S4 for why that intent
  cannot even be expressed today). Catch-up is verified from code, and
  exercised by the state suite (`r2_settled_occurrence_never_refires`
  et al., green at the tag).

### S4 — wall-clock vs instant storage (the product-semantics scenario)

- **(a) Bare date** → midnight **UTC** (cli.rs:253,
  empirically confirmed): a user at UTC+2 typing
  `tasks edit t --due 2026-10-24` stores `2026-10-24T00:00:00Z` —
  the task is due at 02:00 their time. Intent ("on the 24th") is
  preserved day-wise only for UTC users.
- **(b) RFC-3339 without offset** → **rejected** with a usage error,
  exit 2 (cli.rs:246 + :255-256; empirically confirmed — the value
  never reaches the core). No silent local-zone assumption exists.
- **(c) Display zone**: enumerated every renderer — CLI
  `TaskRow.duedate` serializes the `T<U>` (serde rfc3339, `+00:00`/`Z`
  form; output.rs:99/:102, built by task_row :527-545), CLI due markers are set-membership booleans
  (no time text), the notification log prints `to_rfc3339()` UTC
  (notifications.rs:58), the UI renders *deltas* only
  (`due_phrase` = `duedate - now`, presentation.rs:115-125) and never
  formats a wall date. **Every rendered time is UTC or a delta; no
  local zone rendering exists.**
- **Outcome / decision-grade verdict**: this is an **intended
  UTC-only product, and it should be documented as one** — the
  machinery is consistent and instant-correct end to end (nothing
  breaks); what is missing is the *user-facing statement*. Options:
  (1) document UTC-only semantics in help text/config guide
  (recommended — S effort, zero risk, matches v0.1.0's kiosk/offline
  scope); (2) add a `[ui] display_timezone` config rendering offsets
  display-only (M effort, touches every renderer, invites
  wall-semantics confusion the current model avoids); (3) full
  local-wall due semantics (L, a product decision re-opening D-series
  questions — out of scope for v0.1.x). **Recommendation: (1)**;
  recorded as F11-05 (P3).

### S5 — host clock step vs monotonic tick (the composed pair)

- **Precondition**: reminder engine enabled (production default), a
  delivered proof on disk, NTP steps the host clock.
- **Transition event**: backward step (clock jumps earlier) /
  forward step (clock jumps later).
- **Code path walked**: the tick arm schedules on **monotonic** time
  only (`sleep_until(next_tick)`, re-arm
  `tokio::time::Instant::now() + tick` — actor.rs:463/:473): a wall
  step does not wake or delay the cadence. The *evaluation* inside the
  tick reads the **wall** clock once (`clock.now()`, actor.rs:787) and
  compares instants (reminders.rs:398-402). Delivery proofs key on
  `(reminder, occurrence)` — never on tick time
  (reminders.rs:231-234, repo.rs:1028-1036).
  - *Backward step*: occurrences whose effective instant now lies in
    the "future" (shifted) simply wait until wall time re-passes them
    — firing is late by at most the step size; already-delivered
    occurrences cannot re-fire (their proof is keyed on the occurrence
    instant, which did not move). No wall value is derived from the
    monotonic base or vice versa anywhere in the arm (checked at rows
    18–20/28).
  - *Forward step*: catch-up fires on the next tick (≤ tick period +
    loop delay later; the immediate-first-tick design bounds boot
    catch-up the same way, S3).
- **Representation**: the one place two time authorities are
  *composed*: monotonic for cadence, wall for judgment. The composition
  is clean — each authority's output stays in its own lane (cadence
  never produces a timestamp; timestamps never set cadence).
- **Outcome**: **holds.** Max firing lateness bound: one tick period
  (default 30 s) + loop delay under normal operation; + step size
  under a backward step. No re-fire, no loss (durable-then-notify,
  hop 5).

### Interleavings (concrete misorderings)

- **(i) Echo shadow** — the backlog entry's motivating case, now
  *half-obsolete*: local edit at real time T, local stamp `T_l`
  (engine clock); push; echo returns `lm = T + δ_s` (server seconds).
  The *value* cannot revert (R9 adopts the echo unconditionally — and
  the echo is what we just pushed); only the field *clock* may jump to
  `max(T_l, T+δ_s)`, i.e. up to δ into the local future. The residual
  hazard: a **second local edit** at `T_l + ε` (before `T + δ_s`) is
  then beats-able by any remote change whose server stamp exceeds the
  echo's — within the skew window, a remote edit that *precedes* the
  second local edit in real time wins the merge. Window = local clock
  error relative to the server (typically ≤ NTP discipline, sub-second
  to seconds; unbounded if the host is wrong).
- **(ii) Resurrect flip** — local delete observed at real `T_d`
  (tombstone clock `= engine now`, C3); a remote card write that
  *preceded* the delete in reality (`T_w < T_d`) carries
  `T_w + δ_s > T_d` under skew → `merge_task` R5 **resurrects** the
  deleted card and drops the pending delete re-push. The same flip in
  the other direction (local clock behind) makes a *fresh* remote
  change lose to a stale local tombstone — the "tombstone could never
  be adopted" hazard the sync actor's now-stamps (C5) were written to
  prevent for boards.
- **(iii) Seconds-resolution tie** — local stamps carry sub-second
  precision (engine `Utc::now()`); Deck stamps are whole seconds. A
  local edit at `T.4` vs remote `T`: `remote_wins(T, T.4)` is false →
  **ties keep local**, and half-second-skewed remote writes lose.
  Direction: consistently local-favoring — safe-leaning, but it means
  a genuinely-newer remote write within the same second after a local
  edit is silently dropped (R4 never sees it as newer). The C5
  now-stamps come from `Utc::now()` with the sub-second fraction
  preserved, which C4's seconds-resolution note (merge.rs:287-290)
  explicitly compensates for the *echo* case.
