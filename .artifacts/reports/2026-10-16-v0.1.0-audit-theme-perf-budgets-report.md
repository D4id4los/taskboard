### 3.7 C2 — the 100 ms repaint cadence vs the row-3 budget (interaction note)

An audit fact recorded, not adjudicated here: the repaint driver is a
100 ms repeating poll (`adapter.rs:35`, `lib.rs:176–221`), so any
input→visible-update latency is bounded below by up to one cadence
period (~100–150 ms composed) *regardless of draw cost* — row 3's
≤ 50 ms full-frame figure is a draw-cost budget, not the latency the
user experiences. The tick also performs a `chrono::Utc::now()` read
every 100 ms even when nothing is dirty (`lib.rs:211`), making it the
process's dominant idle wake (census item 1). Whether the cadence
composition is acceptable on-device, and whether an event-driven
redraw (render-on-demand) fits the D1 design better, is kiosk-spike
material — carried as F13-09 (P3) with that exact action.

## 5. §bencher — graduation evaluation + the F1-04 judgment

### 5.1 Bencher continuous tracking (decision reserved for the user session)

**Wiring facts at the tag.** The `benchmark` job runs on every PR and
main push (no job-level `if:`, ci.yml:279–301) and runs the benches
via `cargo bench --workspace` (:301). On main pushes *only*, the
Bencher step (:303–315) re-runs the full bench suite inside `bencher
run` with the `rust_criterion` adapter (`--project taskboard --branch
main --testbed ubuntu-latest`), gated by `BENCHER_API_TOKEN` and
wrapped in `continue-on-error: true` with the comment *"TODO: remove
once the first criterion benches exist"* (:306). Criterion benches
have existed since 2026-10-15 (`benches/hot_path.rs`), so the TODO's
condition is met and stale; the backlog entry
(`taskboard-potential-improvements-backlog.md:247–266`) is marked
✅ DONE (implemented 2026-10-07/08, "tolerant until first `[[bench]]`
targets exist") — the DONE status and the still-suppressed step tell
contradictory stories, and the entry's own "proposed approach" (add
`bencherdev/bencher-action`) differs from what was actually
implemented (raw `bencher run`). Two facts are **not verifiable from
the repo** and are recorded as unknowns, not assumed: whether the
`BENCHER_API_TOKEN` secret exists, and whether Bencher has ever
successfully recorded a run. One measurable cost fact: on every main
push the benches currently execute **twice** (:301 and inside `bencher
run` :315) — at §4's observed wall times that is several minutes of
duplicated runner time per push.

**Value.** Bencher would track the one storage bench today; after
S2/S4/S6 land it would cover the budget-critical CPU paths (refresh,
mapping, engine). Tracking is a *proxy*: benches run on shared
`ubuntu-latest` runners, not the 1 GB in-order device — relative
regressions still predict the device-class direction (same code, same
relative hot spots), which is exactly what a between-PR tripwire
needs. Noise on shared runners is real but modest for wall-clock
Criterion with fixed budgets; thresholds should be tolerant (e.g.
flag only sustained shifts, not single-run noise).

**Cost.** An external-service dependency (Bencher cloud) with a token
to maintain; alert triage burden for a one-maintainer project; and
the current double-run cost until the wiring is fixed. With one bench
the value is narrow; with three or four it is genuine.

**Options.**

1. *Retire the `continue-on-error` TODO now* — cheapest; but if the
   token is absent every main push silently no-ops anyway, and the
   tracking value at one bench is thin.
2. *Graduate when the first gap bench lands (S2/S4/S6)* — ties
   activation to real regression-catching value, and the same
   remediation commit fixes the stale TODO and the double-run.
3. *Drop Bencher for artifact-based tracking* (criterion estimates as
   job artifacts + a diff script) — no external dependency, but no
   cross-run storage, dashboards, or alerting for free.

**Recommendation: option 2** — promote the Bencher entry into the
remediation plan *conditionally*: wire it (and remove
`continue-on-error` :306, fixing the stale TODO) in the same
remediation chunk that lands the first gap bench; until then leave
the step as-is (it is swallowed and harmless) and do not activate
tracking on a single storage bench. If the token turns out to be
absent, that is a hard prerequisite discovered at remediation time,
not a reason to pre-build artifact infrastructure now. The graduation
decision itself lands in the user session (audit plan §2 J; this
chunk delivers the recommendation only — no CI edits, origin §6).

### 5.2 F1-04 judgment — the six `hot_path` entries in the default test lane

**Mechanism verified.** The CI test job runs `cargo nextest run
--workspace --all-targets` (ci.yml:166); `--all-targets` includes the
`harness = false` bench target, and nextest surfaces each Criterion
benchmark as its own entry — baseline `§timing` rows 2–5 and 7–8 show
the six `hot_path` entries burning ≈ 62 s of the 195 s test CPU in
the default lane. In that lane they produce **no recorded trend
data** — they are execution smoke, not measurement (§4's numbers come
from the benchmark job's `cargo bench`, not the test lane). Meanwhile
the benchmark job already runs `cargo bench --workspace` on **every
PR** (ci.yml:279–301, no job-level gate) — so the test-lane copies
are redundant rot-protection: a bench that stops compiling or
panics fails the benchmark job anyway.

**Options.** (a) Keep as-is — preserves a bench smoke in every local
`cargo nextest run` at the cost of ~62 s CPU (roughly doubling the
61.3 s suite) on every lane run, for information the benchmark job
also produces. (b) Filter bench targets out of the default lane via a
committed nextest default-filter (or the CI lane's `-E` expression)
excluding the `hot_path` bench binary — `tests/bench_fixtures.rs`
(the fixture-contract test, a regular test) **stays**; benches remain
exercised on every PR by the benchmark job. (c) Move benches to the
benchmark job only — that is today's de-facto redundancy made
explicit by deleting the bench target from the test lane's view;
option (b) achieves the same with a filter instead of a file move.

**Recommendation: (b)** — one line of nextest configuration keeps the
fast lane fast (~62 s CPU saved per run, the suite back near its
61.3 s wall), loses nothing the benchmark job doesn't already
verify on every PR, and keeps `bench_fixtures.rs` guarding the
fixture contract in the test lane. Trade-off: a developer running a
bare local `cargo nextest run` no longer smoke-runs the benches —
acceptable, since `cargo bench -p taskboard-storage-sqlite` remains
the explicit way to do that and the benchmark job covers CI.
Recorded as **F13-07 (P1)**; no workflow edit in this chunk
(read-only, origin §6). Chunk 14 consumes this verdict.
