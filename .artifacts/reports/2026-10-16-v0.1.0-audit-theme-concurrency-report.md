Per hub × subscriber, the `Lagged` behavior and the

|---|---|---|---|---|

| SYN (SYS, sync/actor.rs:242-244) | warn, keeps listening | same producers; SYN's own events are the bulk of the hub load | yes (same theory) | `stop_actor` sends `Detach` (channel-based, not broadcast) + bounded join (bootstrap.rs:459-466) — shutdown never depends on the broadcast |
| SYSLOG (SYS, bootstrap.rs:664-667) | warn + **exits** | needs 64 events between two recv iterations of a tight log loop — practically unreachable | n/a (logger, not a control listener) | none — daemon loses system-event logging for the rest of uptime → **F9-06** (P3: observability-only) |
| UI (SIG, lib.rs:183-194; SYS, :196-209) | `Lagged → dirty=true` + break | needs >64 signals within a 100 ms timer tick (SIGNAL_BUFFER 64) | missed `StateUpdated` is caught by the dirty flag; render reads the *current* `ArcSwap` snapshot on refresh — staleness window ≤ 1 tick (100 ms), self-healing | next tick's refresh; wall-minute check independent (:211-215) |

**Verdict**: lag handling is correct-by-construction everywhere; the
only lasting damage a `Lagged` can do is SYSLOG's log gap (F9-06).

100 ms cadence?) — the only >64-events-per-tick source would be a
command storm at ≫640 StateUpdated/s; each command = one storage apply,
so this is unreachable on the target hardware class. Render
*performance* is chunk 13's (plan D12); correctness here is clean.

## 6. Pass E — select!-safety rubric (I.1)

Verdict vocabulary per plan §2.5: `clean` requires a because.

### 6.1 Full rubric — the six select sites

**ENG — state engine, `state/actor.rs:354-475`**

- **Q1 arms**: `commands.recv()` (guard `commands_open`, :357),
  `sync_reports.recv()` (guard `reports_open`, :403),
  `system.recv()` (guard `system_open`, :428),
  `sleep_until(next_tick)` (guard `timer_armed`, :463). `biased;`
  order commands → reports → system → timer (:355).
- **Q2 head cancellation**: all four heads are documented cancel-safe
  primitives (`mpsc::Receiver::recv`, `broadcast::Receiver::recv`,
  `tokio::time::sleep_until`) — a losing poll leaves no side effect.
  **clean-because**.
- **Q3 body-abort exposure**: arm bodies await `repo.apply` (storage
  round-trip) in `execute_command`/`ingest_sync_report`/`go_offline`/
  `reminder_tick`, and `send_notifications` (`send().await`, :830-835).
  The engine task is aborted only by `join_bounded` at the shutdown
  budget (bootstrap.rs:372) — i.e. after the drain completed or the
  engine wedged. A mid-`apply` abort leaves: storage committed or not
  (sqlite-atomic, chunk 10 cross-ref), memory not advanced (interpret
  runs only after apply success, :547-558), any reply oneshot dropped
  → the waiting verb gets `EngineGone` typed (actor.rs:132). A
  mid-notification abort = the documented at-most-once marker/permit
  design (§4.2 item 2). **clean-because** (bounded, typed, and
  documented semantics).
- **Q4 re-arming**: timer re-arms at fixed cadence after every tick
  (:473); first tick immediate (:343); `timer_armed=false` on drain
  (:440) and reminders-disabled configs never construct the sleep
  (:340-344); guards flip on `None`/`Closed` (:400, :424, :457). A
  tick body's wall time delays the *next* tick to now+cadence (no
  catch-up burst). **clean-because**.
- **Q5 starvation**: biased commands-first. A sustained command flood
  delays reports/system/timer by ≤ 256 commands × per-apply wall time
  (ms each) — seconds worst case against a minute-scale reminder
  cadence; the inbox is capped at 256 and UI sends are fire-and-forget,
  so the flood self-bounds. `Shutdown` via SYS could in theory starve
  behind a flood — see §3's fallback (bounded join). **clean-because**
  (bounded by inbox cap + apply latency; shutdown bounded independently).
- **Q6 body-await drain delay**: the tick body can park the whole
  engine on `send_notifications` if E-20 backs up (NTF is a log sink
  today — no parking; a future slow sink would be an engine-wide
  latency coupling, noted for the NotificationSink port design round,
  notifications.rs:14-17 already scopes it). `execute_command`'s apply
  is the only other body await and *is* the durability barrier.
  **clean-because** (current sink cannot block; coupling documented).

**SYN — sync actor, `sync-nextcloud/actor.rs:190-246`**

- **Q1 arms**: `commands.recv()` (unguarded; `None`/`Detach` → return,
  :207-217), `sleep_until(deadline)` (:220), `sys_rx.recv()` (guard
  `sys_open`, :225). `biased;`.
- **Q2 heads**: all documented cancel-safe (`recv`, `sleep_until`,
  broadcast `recv`). **clean-because**.
- **Q3 body-abort exposure**: arms 1–2 bodies run the full HTTP
  `cycle(...)` (`read_state` oneshot → push executor → three-plus
  pulls → `send_report`), plus `reschedule`. The task is aborted by
  `stop_actor` at the detach/shutdown budget (bootstrap.rs:465). A
  mid-cycle abort: un-landed pushes remain in the outbox (receipts
  arrive only via reports ingest — retry next attach/cycle); a
  create-landed-but-unrecorded window is **chunk 10's** (D13
  cross-ref); the `reports` sender drops with the task (engine
  continues without sync, state/actor.rs:419-423). The oneshot of a
  mid-`read_state` abort → engine replies to a dropped receiver (`let
  _`, tolerated). **clean-because** (all leftovers land in
  retry-by-construction or chunk 10's enumerated window).
- **Q4 re-arming**: `deadline = reschedule(&st, &cfg)` after every
  command/timer arm (:201, :205, :222); reschedule is a fresh Instant
  from now (backoff state machine, :276-288) — no missed/dup-fire; the
  nudge absorber (:249-270) collapses accumulation into one immediate
  rerun (`deadline = now`, :267-270) — duplicate `SyncNow`s cannot
  stack cycles.
- **Q5 starvation**: commands beat the poll timer by bias; sustained
  nudges are bounded twice — the engine's `try_send` coalesces at E-06
  cap 32 (state/actor.rs:593-597) and the absorber collapses whatever
  accumulated during a cycle into one rerun — so the system arm (the
  only other armed arm) polls between cycles. `Shutdown` starvation
  has the channel-based `Detach` fallback (§3). **clean-because**.
- **Q6 body-await drain delay**: a cycle's full HTTP wall time
  (including retries/backoff inside the client) delays shutdown until
  `stop_actor`'s budget aborts it — shutdown latency is bounded by
  `shutdown_timeout_secs` **by design** (bootstrap.rs:456-466 doc).
  **clean-because** (bounded by the join budget).

**IPCA — accept loop, `ipc/server.rs:275-291`**

- **Q1 arms**: `listener.accept()` vs `wait_stopped(&mut stop_rx)`;
  `biased` accept-first so a connection racing the stop is still
  served (:271-274).
- **Q2 heads**: `TcpListener`-class accept and `watch::Receiver` are
  documented cancel-safe. **clean-because**.
- **Q3 body-abort exposure**: spawned connection tasks live in the
  accept loop's `JoinSet` (server.rs:269). On the stop path they are
  drained via `join_next` (server.rs:291), bounded by `join`'s outer
  budget; at the budget `join` aborts accept + dispatcher
  (server.rs:118-119), and aborting the accept task drops its future —
  including the `JoinSet` — and a dropped `JoinSet` aborts every task
  still in it, so the in-flight connection tasks are aborted with it
  (tokio's documented `JoinSet` drop semantics). A connection aborted
  mid-`write_frame` = the client's read fails — typed client-side.
  Connection tasks hold only `in_tx` (never `App`; server.rs:308), so
  no abort debris can touch the F9-01 refcount invariant. The normal
  drain path additionally cannot strand one: a connection awaiting the
  reply oneshot dies typed when the dispatcher goes (:342-344).
  **clean-because** (abort debris self-cleans; no App refcount leaks).
- **Q4 re-arming**: the loop re-selects each iteration; `wait_stopped`
  re-borrows the receiver; stop → `None → break` → drain
  (`join_next` loop :291). **clean-because**.
- **Q5 starvation**: N/A (two arms, accept-first is the documented
  preference). Clean.
- **Q6 body-await drain delay**: the post-stop drain waits for *all*
  accepted connections — bounded by `join`'s drain budget
  (server.rs:116-127) with the polled-handle panic guarded
  (`is_finished` checks, :121-127). **clean-because**.

**daemon lifecycle — `main.rs:306-313`**: `wait_for_signal()` vs

**daemon force-exit — `main.rs:323-329`**: drain vs signal; signal
