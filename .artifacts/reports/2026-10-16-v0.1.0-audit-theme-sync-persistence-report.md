## Crash windows

All windows use the plan §3.1 template. Crash classes (D6): **AC** =
app crash (process dies; committed WAL transactions survive — C05-06);
**OS** = OS crash/power loss (newest commits may drop).

### W1 — Card duplicate-create (the backlog entry's window)

1. **Interleaving**:
   1. User creates a task → command batch (entity + `EnqueueOp`) commits durably, then ack (`state/actor.rs:547-558,573-575`). Outbox now durably holds `CreateTask`.
   2. Sync cycle reads state (`sync/actor.rs:310-321`); planner materializes `CreateTask` from the current row (`push.rs:546-551`); executor POSTs the card — **the POST lands server-side** (`push_exec.rs:384-404`); the echo binding is inserted into the in-memory overlay only (`:405-411`).
   3. **← crash point (AC)**: anywhere between the POST response and the durable landing of the outcome. The outcome currently lives in: the executor's outcome vec → the cycle's `pushes` → the report sent over the bounded mpsc (`actor.rs:447-455`; capacity 32, `bootstrap.rs:82`) → the engine's ingest → `repo.apply` committing `CompleteOp` + the echo-adopted binding (`state/actor.rs:663`, `pipeline.rs:826-833,950-972`).
   4. Crash ⇒ none of that happened durably. On reboot, `load()` returns the pre-cycle state: the task exists, `remote: None`, the `CreateTask` op still queued (`repo.rs:474-482,573-576`).
2. **Crash class**: AC. (OS class widens nothing here — the op row itself is older and durable; only the same tail-loss class as W3 applies to the landing batch.)
3. **Post-crash durable state**: task unbound + queued create op (as before the cycle).
4. **Next-cycle behavior**: the planner re-materializes the create (row present, `push.rs:546-551`), the executor re-POSTs to the bound stack (`push_exec.rs:381-404`) → **duplicate card server-side**. The echo then binds the task to the *new* card; the crashed POST's card was never bound, so presence reconciliation can never tombstone it — it survives until a human deletes it. Same class one level up: a create for a task in a *new* stack can duplicate the **stack** (the stack create re-POSTs first).
5. **Verdict**: wrong outcome (server-side duplicate = data pollution, not loss) — but exactly the ADR-documented residual (`0007:154-157`), human-recoverable, one duplicate per crashed create. Severity verified for chunk 17: **P2** (see the note below).

### W2 — Board-publish orphan (ADR 0010's safe-but-messy)

1. **Interleaving**: `boards publish` → `create_board` POST lands server-side (`boards.rs:233-236`) → **← crash point (AC)** before `BindBoard`'s batch commits (`:238-250` → `state/actor.rs:547`).
2. **Crash class**: AC (OS class: the create POST is inherently non-durable client-side — nothing recorded).
3. **Post-crash durable state**: local board `remote: None` (unchanged); remote board exists, unowned.
4. **Next-cycle behavior**: no sync cycle touches the orphan (never bound — same absence-blindness as W1). A retry of `boards publish` passes its guards (live local-only board: `boards.rs:214-221`) and creates a **second** remote board.
5. **Verdict**: wrong outcome (server-side orphan), but **explicitly documented as accepted** (`0010:115-121`, runbook: delete the orphan in the Nextcloud UI). No finding; recorded as accepted-risk.

### W3 — OS-crash outbox-tail loss (the accepted durability stance)

1. **Interleaving**: any user command commits (WAL write, no fsync under `synchronous=NORMAL`, `connect.rs:27`) → ack sent (`state/actor.rs:573-575`) → **← crash point (OS: power loss)** → the newest not-yet-checkpointed WAL frames are lost on reboot.
2. **Crash class**: OS only. Under AC the window is empty (W4).
3. **Post-crash durable state**: the state as of some earlier commit; the last acknowledged edit/outbox row (or several) gone.
4. **Next-cycle behavior**: nothing re-derives the lost edit (its source — the user's intent — is gone); the outbox loses exactly the newest enqueues with it, so sync state stays consistent with the entity rows (one batch atomicity, C05-09).
5. **Verdict**: exactly the ADR's documented acceptance (`0005:46-50`: "an OS crash / power loss may drop the newest commits, an accepted kiosk trade-off"). What *can* vanish is a whole acknowledged local edit — worth knowing at the kiosk decision session, but it is accepted-risk, not a finding. Revisit trigger already named in the ADR (power-loss field reports).

### W4 — Tombstone-loss on local delete (seeded; window is structurally empty)

Seed hypothesis: "local delete applies in engine memory, crash before the storage batch commits → reboot loads pre-delete state; the delete intent silently gone."

1. **Interleaving**: `DeleteTask` command → `plan_command` builds the tombstone + `EnqueueOp` (`command.rs:343` + outbox) → `repo.apply` commits the batch **first** (`state/actor.rs:547`) → only then `core.interpret` advances memory (`:558`) and the ack is sent (`:573-575`; comment `:548-549`: "Memory never advanced (interpret runs only after a successful apply)").
2. **Crash class**: AC — **there is no memory-leads-disk span**: a crash before the commit returns leaves both memory and disk at the pre-delete state, and the caller never saw success; a crash after it leaves the tombstone + op durable.
3. **Post-crash durable state**: either pre-delete (command unacked) or deleted (command was acked) — never a silently dropped acked delete.
4. **Next-cycle behavior**: in the pre-delete case the user re-issues the delete; in the other case the op pushes normally.
5. **Verdict**: **benign — the seeded window does not exist**; the engine is write-through (same ordering guards the sync path: `state/actor.rs:663-670`, failed batch ⇒ "report discarded", the next cycle re-delivers the same server truth). Chunk 9 owns the channel-semantics side of this ordering (D9).

### W5 — Tombstone-loss on remote observation

1. **Interleaving**: cycle reports `Completed` with a card absent → engine ingests (`state/actor.rs:611-660`) → `repo.apply` commits the tombstone batch (`:663`) → **← crash point (AC)** before commit.
2. **Crash class**: AC.
3. **Post-crash durable state**: pre-tombstone state (the batch never committed); the report itself is lost with the process.
4. **Next-cycle behavior**: the next cycle re-pulls; the card is still absent server-side; absence is re-observed and the tombstone re-synthesized from the snapshot (`pipeline.rs:572-608`, stamped with the *new* observation time — `merge.rs:272` never moves a tombstone clock backwards). Idempotent recovery.
5. **Verdict**: **benign** (self-healing; the observation is re-derivable by construction). If the crash instead lands after commit, the tombstone is simply durable.

### W6 — Delete re-push after the DELETE landed

1. **Interleaving**: pending `DeleteTask` op → executor DELETEs the card (`push_exec.rs:811-839`) → server deletes → **← crash point (AC)** before the outcome is recorded durably (same landing path as W1).
2. **Crash class**: AC.
3. **Post-crash durable state**: local tombstone intact (committed when the delete was commanded, W4); op still queued; card already gone server-side.
4. **Next-cycle behavior**: re-DELETE → Deck answers 404 → `classify_push` with `delete: true` → `RemoteMissing` (`mapping.rs:155-161`; `push_exec.rs:830-837`) → the pipeline finalizes: re-tombstone (clock-`max`, idempotent — `merge.rs:272`, test `:876`), op completes, sibling task ops cancelled (`pipeline.rs:1046-1073`). No resurrection, no mis-tombstone: a 404 on a delete op is *only* produced by an already-absent card, which is precisely the final state the op wanted.
5. **Verdict**: **benign** — the `RemoteMissing`-finalizes path is the correct terminal for this interleaving (and the one place the F10-02 classification cannot misfire: `delete: true` on a genuine delete intent).

### W7 — Migration crash + re-run

1. **Interleaving**: boot on a v0.1.0-older DB → `open()` → `MIGRATOR.run` (`connect.rs:56`) → sqlx applies each pending migration inside **one transaction per migration, bookkeeping row included** (`sqlx-sqlite-0.9.0/src/migrate.rs:166-186` — `begin` → `execute_migration` (SQL + `_sqlx_migrations` INSERT, `:249-273`) → `commit`; none of the four files is `no_tx`) → **← crash point (AC or OS)** mid-migration.
2. **Crash class**: AC and OS alike — both roll the open transaction back (AC: process death aborts it; OS: the WAL's committed-prefix rule discards uncommitted frames).
3. **Post-crash durable state**: the migration + its bookkeeping row are both absent (atomic pair) — `_sqlx_migrations` shows the last fully applied version only.
4. **Next-cycle behavior**: next boot re-runs the same migration from scratch. The shipped migrations are re-runnable by construction: `0002` is a single `ADD COLUMN … DEFAULT` (idempotent only via the bookkeeping — which is exactly why the atomic pair matters), `0003`'s backfill `UPDATE` is guarded by its bookkeeping row, `0004` is `CREATE TABLE IF NOT EXISTS`-shaped. A checksum mismatch (edited-after-release) aborts loudly with `VersionMismatch` (`sqlx-core-0.9.0/migrator.rs:275`) — never silently re-applied.
5. **Verdict**: **benign** — idempotent recovery by construction of the pinned sqlx version (verified from source, not memory — plan §D7). The upgrade tests (`connect.rs:134-183` (0002/epoch), `:186-290` (0003/backfill), `:292+` (0004)) pin the fresh-vs-upgraded behaviors; the reopen test (`:113-131`) pins zero re-application.

### W8 — Echo-adoption gap on update (crash before the echo lands)

1. **Interleaving**: executor fetches the card, PUTs the desired shape (`push_exec.rs:533-616`) → server applies → **← crash point (AC)** before the `Applied { echo }` outcome is durable (W1's landing path).
2. **Crash class**: AC.
3. **Post-crash durable state**: the `UpdateTask` op still queued; the *edit itself* is durable (the commanding batch committed before ack, W4) — the local row carries the edited fields.
4. **Next-cycle behavior**: the planner re-materializes the PUT from the current local row (`push.rs:569-587`) — a full-send of the same values; the executor's fetch-before-write re-derives the body from the server card (`push_exec.rs:601`), so the re-PUT converges to the same end state (idempotent write; `lastModified` advances again, harmlessly). The self-clobber guard cannot misfire: after reboot the op's `queued_at ≤` the new cycle's `read_at`, so its fields are *unprotected* — the snapshot's post-push values are adopted, which is correct (they are the op's own effect).
5. **Verdict**: **benign** — re-PUT converges; no self-clobber regression; no duplicate (updates are idempotent, unlike creates — the asymmetry that makes W1 special).

**Additional windows considered and rejected**: (a) remote stack move
meeting a queued edit — a wrong-outcome interleaving without any crash;
recorded as F10-02, not a crash window; (b) queued ops against a
confirmed-dead board (drain liveness) — recorded as F10-05; (c)
reminder-delivery crash windows — outside axis M (reminders persistence
is chunk 4/14 material; the delivery-proof set-union is already
documented at `persistence.rs:200-207`).

## Backlog-severity note for chunk 17

**Entry**: `[2026-10-10] Duplicate-create crash window reconciliation`,
`.artifacts/taskboard-potential-improvements-backlog.md` **at the tag**
(read via `git show v0.1.0:…`; the file grew post-tag and is untouched
by this chunk — conv 7). Category `Architecture`/`Reliability`;
targets `crates/taskboard-sync-nextcloud/`,
`crates/taskboard-domain/src/pipeline.rs`.

**Claim-by-claim verification** (entry facts vs the W1 analysis):

1. *"Deck has no idempotency keys"* — **verified** (ADR 0007 context `0007:22-24`; executor abort comments `push_exec.rs:455-459`).
2. *"a crash after a create POST but before the outcome reaches the engine re-POSTs next cycle, producing a duplicate card"* — **mechanism verified** (W1). One precision: the true durability boundary is the **storage commit** of the landing batch (`state/actor.rs:663`), not "reaches the engine" — a crash after the engine received the report but before `repo.apply` committed loses the outcome just the same (the report is consumed, non-durable). Both sub-windows are covered by the entry's proposed fix.
3. *"evidence-then-verdict reporting narrows the window to one oneshot hop"* — **mis-sized on two counts**: the report channel is a bounded **mpsc** (capacity 32, `bootstrap.rs:82`), not a oneshot; and the window spans POST-complete → storage-commit, which includes the entire pull phase (3 conditional reads + per-card detail refreshes) plus the engine ingest — "one cycle's remainder, two channel hops" is the accurate shape. (The same "one oneshot hop wide" phrasing is in ADR 0007 `0007:156` — chunk 15's to correct in the ADR text.) The narrowing claim itself is right: without evidence-then-verdict, *every* mid-push transport failure would re-POST, not just crashes.
4. *"it cannot be closed without reconciliation"* — **verified**: Deck offers no client-supplied card ids or idempotency keys, so the duplicate can only be detected after the fact; the entry's own detection idea (same-title cards within the window) is the only available shape. Note the detection key is fuzzy (title+timestamp) — the fix should trigger only on an observed duplicate, which the entry already says.
5. **Scope**: the entry's text is card-scoped ("duplicate card", "adopt one binding"). W1 shows the same crash window duplicates **stacks** (a create whose stack create was also in-flight), and W2 shows the publish ceremony has its own orphan window that ADR 0010 says this entry "owns the general problem" for (`0010:118-120`) — the entry text nowhere mentions boards/stacks. **Chunk 17 should extend the entry's scope line to cover stack duplication and cross-reference the W2 publish-orphan** (or split it), and correct the window-size wording.

**Verified severity: P2.** Reasoning on the origin §3 ladder: the
outcome is data *pollution* (a duplicate card/stack server-side), not
data loss — nothing is deleted or overwritten (P0's "data loss" does
not apply); it does not make the next feature wave (D1–D6, reminders
polish, multi-board) measurably harder (P1's bar); it requires a
process crash intersecting a create push (rare, but *more* likely on
the kiosk class — power loss), is human-recoverable in the Deck UI,
and is bounded (one duplicate per crashed create, self-limiting once
the echo binds). It is already documented as a known residual in ADR
0007 with a proposed remediation — textbook P2 known debt.
