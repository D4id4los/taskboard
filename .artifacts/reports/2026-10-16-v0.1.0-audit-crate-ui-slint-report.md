### 2.2 Where the generated unsafe actually is (mechanism-level characterization)

Generated code is upstream's (i-slint 1.18.1), out of line-by-line
census scope per plan D1; the experiments characterize it precisely:

- The generated expansion (`target/debug/build/taskboard-ui-slint-*/out/app-window.rs`,
  18 594 lines at the tag's `.slint` sources) greps **0** `unsafe` in
  its *text* — text grep alone would under-report.
- The **forbid experiment** (§1 item 2) surfaces what text grep cannot:
  inserting `#![forbid(unsafe_code)]` fails with **36 × E0453**
  (`allow(unsafe_code) incompatible with previous forbid`), every one
  originating in the `ItemTreeVTable_static!` proc-macro
  (`i-slint-core-macros 1.18.1`) expanded inside the generated file —
  one site per generated inner component (`InnerComponent_rectangle_3`
  … `InnerAppWindow`). So the generated code carries **36
  macro-expanded `unsafe` + local `allow(unsafe_code)` sites** —
  vtable statics for the component item tree.
- Per the D3 rubric, all 36 sites are verdict **Slint-generated-bound**
  (upstream-authored, inside the `include_modules!` expansion; no
  hand-written action possible). Hand-written hits to adjudicate: none.
  Avoidable-with-sketch: none. The exemption rationale ("Slint's
  generated rendering code requires `unsafe`", lib.rs:10–11) is
  **literally true**: a crate-level `forbid` is structurally
  incompatible with the generated code's internal allows at the pinned
  Slint 1.18.1.

### 2.3 The guarantee-form gap and the proposal (finding F7-01)

Today **nothing machine-checks** that hand-written `unsafe` stays at
zero — the zero is convention (AGENTS §6 exempts only this crate). The
plan's D3 sketch (deny + an `#[allow(unsafe_code)] mod generated`
seam) anticipated feasibility risk; the experiments settle it, and the
seam module is **unnecessary**:

| Experiment | Result | Meaning |
|---|---|---|
| `#![forbid(unsafe_code)]` + `cargo check -p taskboard-ui-slint` | **fails**: 36 × E0453, all in the `ItemTreeVTable_static!` expansion | `forbid` can never work here: inner `allow`s may not overrule it |
| `#![deny(unsafe_code)]` + `cargo check -p taskboard-ui-slint` | **clean** (4.1 s) | the generated code's *internal* `allow(unsafe_code)` legally overrules a `deny` — Slint 1.18.1 coexists with a crate-level deny, no seam module needed |
| `#![deny(unsafe_code)]` + hand-written `unsafe` probe | **denied**: `error: usage of an unsafe block` (unsafe_code, cite line 1) | the deny fires exactly on the hand-written code the guarantee targets |

**F7-01 · P2 · axis O · evidence `/tmp/taskboard-ui-audit/*.log`
(reproducible via §1 item 2–3; census table §2.1; generated-site
analysis §2.2) · proposed action: add `#![deny(unsafe_code)]` as the
first line of `crates/taskboard-ui-slint/src/lib.rs` and update the
NOTE (lib.rs:9–12) to say *deny, not forbid, because the Slint-generated
code carries internal `allow(unsafe_code)` scopes that a `forbid`
would overrule (E0453)* — a future hand-written `unsafe` then fails
the build unless a local, grep-visible `#[allow(unsafe_code)]` is
added at the site · effort S.** This chunk implements nothing
(read-only discipline); the change is one line + a doc-comment edit,
verifiable with `cargo clippy --workspace --all-targets -- -D warnings`
and `cargo nextest run -p taskboard-ui-slint`. Optional belt-and-braces
(not the recommendation): a CI grep step asserting the D1 census
pattern stays comment-only.

### 3.2 Config surface and ban/allow tables

One config file per boundary, e.g. `.config/deny/deny-domain.toml` and
`.config/deny/deny-ui-slint.toml` (a dedicated directory keeps the
existing root `deny.toml` / `cargo deny check` step untouched; the

License/advisory sections in the boundary configs copy the root
policy; only `[bans]` differ (plus the `[graph]` header). Both configs
start with

```toml
[graph]
exclude-dev = true   # dev-deps (serde_json, png, insta, …) stay unjudged
```

about the **shipped dependency** direction. Two scoping facts
re-verified on 0.20.2 (this tool has **no `--edges` CLI flag** — that

mechanism, and `check bans --edges normal` fails with a CLI error):
`exclude-dev = true` excludes true dev-deps (banning `serde_json`

### 3.3 CI wiring (proposal)

Two steps after `.github/workflows/ci.yml:137` in the existing `deny`
job:

```yaml
      - run: cargo deny --config .config/deny/deny-domain.toml --manifest-path crates/taskboard-domain/Cargo.toml check bans
      - run: cargo deny --config .config/deny/deny-ui-slint.toml --manifest-path crates/taskboard-ui-slint/Cargo.toml check bans
```

Cost: seconds per step (graph walk only, no compilation; the probes
ran < 2 s warm, first run pays `cargo metadata` once). Failure mode:
a PR that adds a banned edge fails **its own** CI with a graph that
names the offending path — the fix or the policy change lands in the
same PR, visibly. Pin consideration: CI installs cargo-deny unversioned
(`taiki-e/install-action`, ci.yml:135); the probes were verified on
0.20.2 — pin the tool (or record the tested minimum ≥ 0.20) in the
same remediation PR.

### 5.2 D9 extraction evaluation (actions/keymap/presentation core)

- **Option A — keep in place (recommended).** No second consumer
  exists at v0.1.0; extraction is pure churn until one does. The
  modules already document the seam (e.g. `src/presentation.rs:4–8`
  "a second Rust consumer lifts this module into its own crate
  unchanged"; `src/actions.rs:13–14` "must stay liftable"), and the
  discipline is *tested*: nothing in the pure half imports slint
  (verified by import scan), so the lift stays mechanical.
- **Option B — extract `taskboard-ui-core`** (actions, keymap, menu,
  presentation, resolver, responsive, router, shell, view_state ≈
  2.6k production lines). Pros: enforces the purity with a crate
  boundary; lets a future Rust second frontend (web dashboard, kiosk
  IPC client) reuse it. Cons: +1 crate and workspace ceremony; the
  boundary is already machine-checkable more cheaply (F7-02's
  cargo-deny boundary or even a `slint` ban on a ui-core member);
  domain does not belong in it, so it would be a *fourth* pure crate
  to keep scored/covered.
- **Option C — fold into `taskboard-domain`.** Rejected: domain's
  purity rule is stronger (no UI concepts at all); `DueKind`,
  `MenuEntry`, `Breakpoint` are presentation vocabulary and would
  pollute it.
- **Consequence/trigger**: revisit B the day a second Rust consumer
  is actually scheduled (origin §1 web-dashboard idea or a Rust kiosk
  client). Cost then: ~S–M (move + re-export shim).
