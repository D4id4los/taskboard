### 2.3 Axis F — data-model fit vs D1–D6

Friction walkthrough against the future-goals decisions (report friction
only, never choose — origin §6):

- **D1 field-carrying**: schema has per-field `ck_*` clocks, but writes
  are whole-row upserts of all 21 task columns (repo.rs:800–847) —
  would a field-carrying strategy need statement-level granularity the
  current `execute_batch` partition loop makes awkward?
- **D2 multi-board**: `sync_status` is a singleton row (`WHERE id = 1`,
  seeded in 0001; CHECK (id = 1)) and `SyncStatus` is one global struct
  — what breaks when N boards sync independently? (Facts here; the
  engine-side `SyncStatus` fit is chunk 4's.)
- **D4/D5 etc.**: tombstones retained forever (ADR 0005; `deleted` flags
  + no GC) — growth facts for a 1 GB kiosk recorded; adjudication of
  retention is chunk 10's.
- Edge-behavior facts to verify and classify (each is a potential P2/P3):
  `pending_ops` saturation `u32::try_from(…).unwrap_or(u32::MAX)`
  (repo.rs:623); `remote_col` u64→i64 saturation at `i64::MAX`
  (codec.rs:317–322); reminder `offset_seconds` whole-second truncation
  toward zero (repo.rs:980–983); timestamps are rfc3339 TEXT with a
  documented *never ORDER BY timestamps* rule (0001 header) — check
  every `ORDER BY` in repo.rs obeys it.

## 7. Mutant-evidence status & survivor triage (B)

**Status: the optional one-off RAN (baseline `§mutants` (b))** — state
this verbatim in the report with the scope (60-min box, completed,
153/107/3/43/0). The dispatch's risk-map fallback ("if no one-off ran,
reason from the risk map instead") is therefore **dormant** — recorded
here so stage 2 doesn't invent one, and so chunk 17 can see the branch
was considered.

Triage the 3 survivors against the risk map (conflict policy, outbox
crash-safety, reminder firing, IPC protocol, config precedence — the
storage-relevant ones being outbox crash-safety and any decode-integrity
class):

- `codec.rs:199:22` / `:200:22` — guard `last_error.is_none()` → `true`
  for `idle`/`syncing`: a stored row `{phase: idle, last_error: …}`
  would decode instead of `Corrupted`. Note the existing rejection test
  covers exactly one dangling combination (`"idle", Some("network")`,
  codec.rs:447–451) — the sibling phases are untested. Assess severity:
  the dangling combination can only arise from a corrupted/hand-edited
  DB (the write path clears `last_error` for non-failed phases,
  repo.rs:946–951), so this is defense-in-depth weakness, likely P2/P3.
- `connect.rs:36:5` — `pool_options` → `Default::default()`: drops the
  memory-pool pinning (`min_connections(1)`, no idle/lifetime expiry)
  and the file-pool `max_connections(1)`. `pool_is_single_connection`
  (connect.rs:372–376) survives it because lazy opening leaves size at 1
  — i.e. the single-writer stance is untested *under load*. Assess
  against the kiosk envelope (a second connection on a file DB breaks
  the WAL single-writer assumption) — candidate P2 with a proposed
  test (assert `max_connections == 1` via `SqlitePoolOptions`? not
  directly observable — sketch honestly, maybe via options accessors or
  a concurrency probe).
