## 4. Per-surface audit procedure (stage 2 executes)

All evidence is `file:line` in the worktree (= tag tree). Scratch
output goes to `/tmp/`; the repo diff stays exactly plan + report
(conv 8). Read-only discipline absolute (origin §5): a needed fix is a
finding, never a diff.

### 4.1 S1 — log/format paths

1. **Subscriber config**: verify `main.rs:38-55` facts (stderr writer,
   default filter, RUST_LOG override) and that nothing else installs a
   subscriber; confirm stdout carries no log output (the claim the
   `--json` surface leans on).
2. **Site census**: enumerate every `tracing::(error|warn|info|debug|
   trace|event!|span!)` site in non-test `src/` of all five library
   crates (app ~most of the 207 + sync; spot-check state/storage/
   domain/ui-slint for completeness). Classify mechanically: sites
   formatting only static strings are trivially clean; sites
   formatting values (`?err`, `%err`, structs, payloads) get
   hand-review of *what type* is formatted and whether it can reach K1/
   K2/K4/K5 (e.g. reqwest `Error` `Display` embeds the request URL —
   can that URL ever carry userinfo or a token-bearing query?).
3. **Fmt-impl inventory**: `Debug`/`Display` impls (manual *and*
   derived) of every type in the K1/K2/K4 carrier closure:
   `AppPassword`, `DeckClient`, `CredentialError`, `DeckError`,
   `CommandError`, IPC codec/protocol error types, `SyncError*`,
   config structs — derived `Debug` on any struct transitively holding
   a secret-bearing field is the classic leak; verify none exists.
4. **Leak-floor tests**: locate every existing redaction/leak test
   (seeds: `secrets.rs:225`, `tests/secrets.rs:17`; grep
   `redact|leak` repo-wide), run them read-only
   (`cargo nextest run -E` filtered) — allowed as an axis question
   under conv 6; a secret-carrier *without* a leak-floor test is a
   finding (missing regression guard), not a patch.
5. **tokio-console** (decision D2): verify the `TASKBOARD_CONSOLE`
   gate, and from the *pinned* version in `Cargo.lock` at the tag the
   console-subscriber's default bind (expect `127.0.0.1:6669`,
   unauthenticated): judge what span fields (URLs, error values)
   would be exposed and to whom; opt-in status weighs severity, it
   does not waive the check.

### 4.2 S2 — keyring + ceremonies

1. Walk `secrets.rs` against ADR 0008's claims: service/account
   scheme, `set`/`load`/`delete` behavior, error taxonomy content
   (`map_keyring_error` — does any error variant embed secret-bearing
   values?), the no-silent-fallback rule (typed `Backend` error whose
   Display names the env alternative — and nothing more).
2. Walk every `expose()` production call site (the four in §2.1) and
   the connect/logout/attach/detach ceremonies: the secret is read
   once, crosses into `DeckClient::new`/keyring only, never into
   config, state, logs, or receipts; detach identity carries only K4.
3. Piped-stdin password path (`connect.rs:133`): record the scripting
   exposure honestly (secret visible to a shoulder-surfer of the pipe
   source / shell history *outside* the app is out of scope; the
   in-app behavior — echoed or not, logged or not — is in scope).
4. Verify "the secret never enters `AppConfig`" from the serde layer
   (deny_unknown_fields per table; the normative test at
   `config.rs:1069+`) — config-side evidence for S4.

### 4.3 S3 — IPC surface vs ADR 0012 (claim-by-claim)

Build the ADR-0012 claim table: extract every security-relevant claim,
map to code, verdict each (confirmed / contradicted / partially
implemented — quoting ADR text and code, no paraphrase drift). Seeded
claims:

| ADR 0012 claim | Code to check |
|---|---|
| Unix socket chmod `0600` after bind; pre-chmod window accepted & documented | `server.rs harden()` + bind sequence; whether the window is as brief as claimed (bind → harden adjacency), failure logged not fatal |
| OS object permissions are the *whole* auth story; no tokens/handshake; no network listeners | server bind surface; no other listener anywhere (`interprocess` local-socket kinds only) |
| Ceremony verbs (`connect`/`logout`/`config print`) refused before dispatch, usage class code 2 — secrets never cross the wire | lane table + `server.rs:424-491`, `protocol.rs:291,358` |
| Attach payload *structurally* cannot carry a secret (refused-secret invariant) | `protocol.rs:291` — the payload type's fields |
| Framing caps 64 KiB / 16 MiB enforced as typed transport failures | `codec.rs:10-13,44-45` + read path |
| Versioned envelope; mismatch → typed `VersionMismatch`, never misparse | protocol decode arms |
| `--config` bound by canonicalized path; different file → usage refusal | `server.rs` `--config` handling |
| Stale recovery: probe → remove → rebind once; live answerer surfaces as typed bind error | `bind_with_recovery` — also the TOCTOU question: what can a *second local user* plant/remove in that directory (depends on dir perms, see next row) |
| Graceful shutdown removes the socket file | server shutdown path |
| Serial execution, concurrent accept | dispatcher structure (structure only; concurrency *verdicts* are chunk 9's — cross-ref) |
| Windows: session-local namespace, no filesystem artifact | `cfg(not(unix))` paths — code-reading only (D6) |

Then the **kiosk/multi-user analysis** the severity calibration leans
on: given ADR 0012's trust statement ("exactly as trusted as the
`taskboard.toml`, db, and lock files beside it"), one bounded pass over
the sibling artifacts' *creation* permissions (db file, lock sidecar,
socket, REPL history file — decision D5): if any sibling is
other-readable while carrying K5, the OS-perms auth story degrades by
exactly that much. Deployment sink perms (journald, systemd) are out
of scope.

### 4.4 S4 — `--json`/status output shaping

1. Field-by-field walk of every view struct in `output.rs` (§2.1 list)
   + the status payloads (`boards.rs:367,434`) + receipts
   (connect/logout/select) against the §3 inventory: no K1/K2 field
   may exist anywhere in the serialization closure (including nested
   error objects).
2. `config print` (`commands/config.rs:42`): verify the
   "secret-free by construction" claim end-to-end — what `ConfigView`
   actually serializes (expect K4 at most) and that unknown-key
   rejection really blocks a `token =` key (serde evidence from
   `config.rs`).
3. Error output: how `CommandError`/`DeckError` render in human and
   `--json` modes (do error chains embed URLs — K4, or worse?);
   clap's own error rendering of argv (the wire carries raw argv —
   is argv ever echoed where a secret could appear? Conclusion of S2
   governs whether any argv can carry K1 at all).
4. `holder_pid`/`connector_attached` fields: confirm K6-only content.

### 4.5 S5 — remote-path construction (decision D1 scope)

1. Trace the full URL assembly: `DeckClient::new` normalization
   (scheme/host validation, query/fragment strip, trailing slash) →
   `path_prefix` → resource `format!`s → however the request URL is
   finally built (Url join / request builder) — verify each step's
   encoding behavior for the segment values actually used.
2. Segment provenance: prove by enumeration that every dynamic path
   segment is a numeric id (serde-rendered) or `&'static str`; user
   content (titles) travels only in JSON *bodies* — check the
   attachments endpoints are metadata-listing only (origin §1 known
   fact — verify, don't re-derive) and that any query-string
   construction (stack filters, `model.rs:69` family) encodes
   user-controlled values or contains none.
3. Scheme policy: `http://` is accepted (`client.rs:330`) — the basic-
   auth header (K2) then crosses the LAN in cleartext; record as a
   finding with a proposed action (e.g. opt-in flag or documented
   warning), severity per §5 (config-controlled, kiosk-LAN reality).
4. Path traversal: since segments are ids/statics, the traversal
   question reduces to "can a malicious *title* from the server reach
   a path?" — answer from the body-vs-path split; also check any
   place server *responses* are written to filesystem paths.

## 5. Severity calibration (kiosk context)

Origin §3 defines P0–P3; this chunk calibrates against the kiosk
deployment (audit plan §1: single-user-by-design netbook kiosks,
offline-resilient) with **multi-user local exposure as the escalation
axis** (a shared machine where second local accounts exist):

- **P0** — a K1/K2 secret disclosed beyond the owner's control in the
  default configuration: default log level, `--json`/stdout, the wire,
  or an other-user-readable artifact.
- **P1** — (a) K1/K2 disclosure under a plausible ops configuration
  (`RUST_LOG=trace`, tokio-console enabled, crash/panic reports);
  (b) an authentication/trust boundary a second local user or
  non-owner process can cross (socket-permission window exploitable
  in practice, world-readable sibling artifacts carrying K5, stale-
  recovery race usable to squat/replace the socket); (c) request-path
  injection letting server-controlled data alter request targets.
- **P2** — hardening debt where code matches a documented accepted
  risk only in degree; disclosure of K4/K5 to same-user-readable
  local artifacts; missing leak-floor regression guards for a
  secret-carrier; cleartext-http credential transport that is
  config-selected.
- **P3** — observations, drift cross-refs (§4.6), accepted risks
  confirmed implemented *and* documented (e.g. the pre-chmod window
  exactly as ADR 0012 describes it).

## 6. Decisions (open questions resolved at planning time)

- **D1 — "WebDAV path construction" scope**: v0.1.0 ships no WebDAV
  code; the axis's intent (path construction incl. encoding of
  user-controlled segments) is executed against the real surface —
  the Deck REST client (§4.5). The WebDAV naming drift is recorded as
  a P3 cross-ref for chunk 15 (and chunk 6's crate audit), not a
  chunk-12 finding.
- **D2 — tokio-console is in scope** as part of "secrets in
  tracing/log output": it is a second, opt-in tracing consumer with
  an unauthenticated local TCP listener; its defaults are verified
  from the pinned `Cargo.lock` version at the tag. Opt-in status
  weighs severity (P1 ceiling), it does not waive the check.
- **D3 — severity rubric** fixed as §5 (kiosk single-user baseline,
  multi-user local exposure as the escalation axis; network-reaching
  or other-user-readable secret disclosure is the P0 line).
- **D4 — leak-check semantics for output surfaces**: stdout of the
  requesting client is the product surface; the requesting client is
  the owner under the OS-perms auth story. Secrets (K1/K2) must never
  appear anywhere; K4 in output is at most a P3 note; K5 (task
  content) is a leak only via surfaces with a *different* reader
  (logs, other-readable artifacts, unintended wire emission).
- **D5 — sibling-artifact permissions** (db, lock sidecar, socket,
  REPL history) get one bounded creation-perms pass under S3, because
  ADR 0012's auth story is explicitly anchored on their trust level.
  Deployment sink perms (journald etc.) stay out of scope.
- **D6 — Windows named-pipe side** is audited by code reading only
  (cfg paths + ADR claims); no Windows runtime exists on the dev
  host. Recorded as a method caveat; binary verification would be a
  remediation-wave item if the code reading raises doubt.
- **D7 — test evidence**: existing leak-floor tests are located and
  run read-only (conv 6's carve-out: running read-only tests to
  answer an axis question is allowed). No new tests are authored —
  a missing guard is a finding with a proposed action for the
  remediation plan.
- **D8 — dependency/CVE auditing stays out** (dispatch non-goal);
  `cargo-deny` coverage gaps surface as P3 cross-refs only.
- **D9 — log-census time-box**: the ~207-site census is classified
  mechanically first (static-string sites bulk-clear); hand review
  targets only value-formatting sites and the fmt-impl closure of
  §4.1.3. If the hand-review set exceeds ~60 sites, sample the rest
  by type-formatted and record the sampling as a method note — the
  fmt-impl inventory is the safety net that makes sampling sound.

## 8. Effort & risks

  lookup-heavy, judgment-light).
- **Risks**: (1) trace-level exposure claims depend on third-party

  named surfaces (dispatch non-goal).
