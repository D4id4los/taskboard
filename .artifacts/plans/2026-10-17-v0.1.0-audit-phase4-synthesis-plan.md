## 3. Deliverable A — findings report (the merge)

File: `.artifacts/reports/<execution-date>-v0.1.0-audit-findings-report.md`
(conv 3; `<execution-date>` = stage-2's date, `2026-10-17` expected).
House `[Report]` style. Structure: header/provenance → findings
table (severity-sorted) → axis rollup A–Q → contradiction log (if
any) → decision agenda (§6). The report is an **index + agenda**, not
a re-statement: full evidence stays in the chunk reports, cited by
path + §.

### 3.1 Extraction (per report)

A declared finding = the chunk's own `F<c>-NN` ID in its findings
section/table. Cross-references to other chunks' IDs are pointers,
never declarations. Three format families exist (stage 2 uses the
right parser per family; all 16 are read **in full** first):

- **Bullet family** `- **F<c>-NN · P<s> · axis X · evidence**: …` —
  chunks 1, 2, 4, 5, 10, 11, 12, 13.
- **Table family** `| F<c>-NN | P<s> | axis | evidence | action |
  effort |` — chunks 3, 6, 7, 8, 16.
- **Embedded family** (findings declared in a dedicated findings
  section, referenced from analysis tables) — chunks 9, 14, 15:
  extract only from the findings section; pointer rows in analysis
  tables (e.g. chunk 14's risk-map rows naming F6-01…03) are the
  *owning* chunk's findings.

Per chunk, stage 2 records in §provenance: declared IDs, severity
counts, and any extraction ambiguity (a report whose declared count
disagrees with its coverage table is itself a merge note, resolved in
favour of the findings section, both numbers recorded).

### 3.2 Merge line format (conv 4, one line per finding)

`F<c>-NN[+F<d>-MM] · P<s> · axis <ID> · <short title> · evidence
anchor (chunk report §x / file:line @ v0.1.0 / baseline §anchor) ·
<proposed action, compressed> · effort S/M/L`

IDs are stable; **no renumbering** (conv 4). Evidence anchor must
point at the owning chunk report's section so the session can drill
in.

### 3.3 Dedupe rule

Two findings merge into one line **iff same axis AND same evidence**
(same `file:line` at the tag, same ADR claim, or same workflow path)
— both IDs kept (`+`-joined), and the merge is logged in a small
reconciliation table (IDs → merged line, reason). Merging requires
the actions to be compatible (one is a refinement of the other);
**same evidence but conflicting verdicts is NOT a dedupe — it is a
contradiction** (§4). Expected non-dupes to leave alone: chunk 14's
consumed crate findings (cross-references), chunk 16's F-axis
findings that restate chunk 3/4 friction *for decision framing*
(keep both; they serve different axes/audiences unless evidence AND
axis coincide).

### 3.4 Severity sort & sections

P0 block first — expected **zero**; if zero, the report states "no
P0 findings were declared by any chunk" as an explicit line (no
invented justification). Then P1, P2, P3; within a block order by
axis A→Q, then ID. Every P0/P1 line carries a proposed action —
acceptance requires it (origin §8); stage 2 verifies all expected 9
P1s do, and flags any that doesn't as a review finding against this
merge.

### 3.5 Axis rollup (the coverage proof)

Table over dispatch §1.1's map — per axis A–Q: owning chunks, N
findings (IDs), or an explicit **clean** / **accepted-risk** verdict,
aggregated from the sixteen coverage tables (conv 5). No silent
skips; every axis that another chunk left "→ chunk 17" (the
StateCommand naming facts, D9 caveat) appears here with its merged
verdict (PD-7). Cross-check each axis's owners against §1.1; a
mismatch is a merge defect.

### 3.6 Arithmetic acceptance

Findings-line count = Σ declared (173) − merged duplicates, with the
reconciliation table reconciling the difference exactly. Severity
counts sum to the line count. Stage 3 re-derives all counts
independently from the sixteen reports (prompt 17.3).

## 4. Contradiction-resolution rule

If two chunk reports disagree on a fact or severity for the same
evidence: re-read **only the cited evidence at the tag** (`git show
v0.1.0:<path>`; conv 2 for the reports themselves) — never re-audit,
never run new probes or baselines (conv 6). Record the reconciliation
in a contradiction log (IDs, the evidence read, the chosen verdict,
one-line rationale). Severity conflicts resolve to the **more severe**
value unless the evidence read settles it explicitly. If the evidence
read does not settle it: **keep both findings verbatim**, flag both
lines `⚠ session`, and add one decision-agenda row so the user
adjudicates. No contradiction may be resolved by weakening either
chunk's evidence claim.

### 5.4 Folding audit findings via the entry template

backlog now** (P2's §3 definition *is* "backlog entry with severity,

that entry (severity verify + context addendum), never create a
sibling. Expected fold volume: large (~100+ P3s) — group trivially
