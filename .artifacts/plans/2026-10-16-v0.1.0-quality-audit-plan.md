# [Plan] v0.1.0 Architecture & Quality Audit (post-M2)

- **Date**: 2026-10-16
- **Target**: whole workspace, audited at the `v0.1.0` tag (read-only; remediation
  is planned separately after acceptance of the findings)
- **Goal**: a structured, evidence-based review of the codebase as shipped at
  v0.1.0 — architecture fit against the project's future goals, test-suite
  quality and determinism, module/crate factoring, data & control flow, naming
  accuracy, duplication/complexity, safety of concurrency designs, and
  performance-budget coverage — producing prioritized findings, a reconciled
  improvements backlog, and (optionally) remediation dispatch plan(s).
- **Status**: ACCEPTED (user review 2026-10-16; kiosk target hardware
  decided in the same session — §1)
- **Outputs**: reports under `.artifacts/reports/` (see §4), reconciled
  `.artifacts/taskboard-potential-improvements-backlog.md`, optional
  `2026-10-XX-v0.1.0-remediation-dispatch-plan.md`

## 1. Context & Known Facts (do not re-derive)

- **M2 = Phase 7 of the growth roadmap** (Slint UI on the same core), exit =
  tagged v0.1.0 with released Linux + Windows binaries. The audit runs
  *after* the tag, against the tag, not against moving `main`.
- **Kiosk target hardware (decided 2026-10-16)**: Samsung NP-NF310 (Atom
  N550, 2c/4t in-order, 1 GB, 1366×768) as the interactive kiosk and Acer
  Aspire One D250 (Atom N270, 1c/2t in-order, 1 GB, 1024×600) as the pure
  wall display — both Intel-64 netbooks with gen3 Intel graphics, which
  have no hardware GL on modern Mesa, so the kiosk rendering path is
  Slint's software renderer on the existing x86_64 first-class target —
  plus a Lenovo Yoga Tablet 2 1050F as a later web-dashboard client.
  Tracked in the two 2026-10-16 backlog entries; this fixes axis J's
  budget envelope.
- **Scale at time of planning**: ~70k rs-lines total; per-crate src lines
  roughly: app 14.5k, domain 14.7k (incl. tests ~27.5k/14.7k totals),
  ui-slint 7.7k, state 4.7k, storage-sqlite 3.5k, sync-nextcloud 12k.
  `taskboard-app` is co-largest with domain — a factoring-review signal,
  not yet a finding.
- **Existing quality machinery to build on, not duplicate**:
  - CI: fmt/clippy `-D warnings`, MSRV, `cargo-deny`, nextest, doc-tests,
    llvm-cov → Codecov, SonarCloud analysis, performance benchmarking job.
  - Weekly `cargo-mutants` sweep over `taskboard-domain` + `taskboard-state`
    (survivors collected as artifacts, triaged into reports/backlog).
  - Weekly capped Miri on `taskboard-domain` (core + pipeline gates).
  - Criterion benches: storage-sqlite persistence hot path only.
- **Known-debt ledger**: the improvements backlog has ~80 entries (2.9k lines),
  including a Flaky Test Watchlist with three live entries (actor_wiremock
  under llvm-cov, coverage profraw corruption ×3, repl_history EACCES) and
  several entries marked DONE but kept for history.
- **All 29 `#[ignore]`d tests are environment-gated by design** (dockerized
  Nextcloud tier, live tier, Secret Service). The audit must verify they
  actually execute in `nextcloud-integration.yml` — a gated test that no CI
  job ever runs is a hole, not coverage.
- **Future-goals anchor**: `.artifacts/reports/2026-10-14-future-directions-analysis-report.md`
  §4 defines the cross-cutting decisions D1–D6 (field-carrying strategy,
  multi-board + hierarchy, recurrence semantics, undo architecture, app-data

- **Docs baseline**: 14 ADRs (numbering skips 0013 — verify whether that is
  a withdrawn ADR or an accident), `architecture.org`, `testing_strategy.org`,
  `coding_guidelines.org`.
- **Concrete drift example already spotted**: both `StateCommand`
  (domain/messages.rs) and `EngineCommand` (state/actor.rs) exist and both

## 2. Audit Axes

Each axis lists the question and the method. Axes are assessment lenses; the
phases in §4 schedule them.

### A. Architecture fit vs future goals (user brainstorm #1, #5)
- Question: does the current crate/module topology let D1–D6 and the near-term
  waves land without structural rework?
- Method: for each of D1–D6 + reminders + multi-board + kiosk/IPC, a short
  *dry-run walkthrough*: which crates/files change, which contracts
  (Port traits, message enums, schema) must move, where the change ripples.
  Record friction points as findings.

### B. Test quality: coverage & strength (user #2)
- Question: do the tests cover what we want covered, and would they catch
  real regressions (not just execute code)?
- Method: (1) build a *risk map* — per crate, the behaviors whose breakage
  would be worst (conflict policy, outbox crash-safety, reminder firing,
  IPC protocol, config precedence) — and check each has a test at the right
  layer per `testing_strategy.org`; (2) triage the latest cargo-mutants
  survivor report against the risk map (survivors in high-risk areas are
  findings; consider a one-off mutants run on storage-sqlite and
  sync-nextcloud, currently unswept); (3) coverage per crate as a *negative*
  signal only (uncovered risk areas), never a percentage target.

### C. Test determinism & suite hygiene (user #2)
- Question: has sloppiness crawled in?
- Method: grep-level sweep for `sleep`, wall-clock `now()`/`Utc::now()` in
  non-seam code paths used by tests, unbounded channels, network/fs touches
  in unit tiers; verify each Flaky-Watchlist entry is fixed or still live;
  verify the 29 gated tests actually run in the nextcloud-integration
  workflow; measure suite wall-time and list the slowest tests; check
  snapshot hygiene (16 snapshots — any over-broad AppState dumps that should
  be focused assertions); confirm the AGENTS.md §5 layering rules (no
  duplicated tests across unit/engine/E2E tiers).

### D. Data & control flow diagram (user #3)
- Question: can a reader understand actors, channels, state ownership, and
  entanglements from one artifact?
- Method: derive (not imagine) the diagram from `bootstrap.rs`'s channel
  graph + actor spawn sites: every actor, every channel with its type
  (mpsc/broadcast/oneshot) and boundedness, `ArcSwap` read paths, IPC, UI
  read path. Each edge carries a code reference (`file:line`). Deliver as
  mermaid inside the report; recommend promoting to `docs/` afterwards as a
  maintained release-anchored artifact.

### E. Crate & module factoring (user #4)
- Question: are responsibilities in the right crates; should anything split?
- Method: per-crate responsibility inventory vs AGENTS.md §2 boundaries;
  evaluate concrete extraction candidates with pros/cons, at minimum:
  IPC (server/client/protocol ~1.5k lines) out of app if kiosk management
  grows; the Deck client vs sync-actor split inside sync-nextcloud (12k
  lines, two roles); `completion.rs` (1.6k) placement; whether
  commands/output.rs (`--json` shaping) leaks presentation into app logic.
  Also: is any logic in app that the "UI is a dumb client" rule should
  forbid?

### F. Data-model fit (user #6, reframed)
- Question: not "optimal" in the abstract, but: which structs/enums will
  *force* awkward data flow for D1–D6?
- Method: part of the A-axis walkthroughs; additionally review merge-policy
  field granularity vs the D1 field-carrying decision, `SyncStatus` vs
  multi-board, task identity/timestamps vs recurrence and undo.

### G. Naming & taxonomic drift (user #7)
- Question: do names still say what things do?
- Method: enumerate pub items per crate; check doc-comment vs behavior,
  enum-variant names vs produced semantics, module names vs contents;
  adjudicate known suspects (`StateCommand` vs `EngineCommand`, storage
  `sync_metadata` vs validator naming — existing backlog entry); check
  docs/ADR terminology vs code terms.

### H. Duplication & simplification (user #8, #9)
- Question: repeated logic that wants a helper/generic; overcomplicated
  spots that want a simplification pass.
- Method: mine SonarCloud duplications + manual pass over cross-crate seams
  (DTO mapping, error conversion, config/output shaping); complexity
  hotspots from Sonar/coverage + reviewer judgement; each candidate gets a
  concrete simplification sketch, not just "this is complex".

### I. Error-prone designs (user #10)
- Question: where do current control/data-flow designs invite bugs?
- Method: targeted reviews of (1) `select!` cancellation-safety in every
  actor loop, (2) channel-close semantics on shutdown (who notices, who
  flushes), (3) unwrap/expect/panic paths reachable in the daemon (grep +
  triage), (4) error taxonomy layering (does UI/app stringify errors that
  should be typed; is `color-eyre` confined to app), (5) implicit contracts
  between actor pairs that only hold by convention.

### J. Performance budgets & bench coverage (user #11, reframed; device envelope fixed 2026-10-16)
- Question: define the budgets from the established kiosk hardware, then
  check bench coverage against them.
- Method: the budget envelope comes from the §1 devices — in-order Atom
  cores, 1 GB RAM, software rendering (gen3 graphics have no hardware GL
  on modern Mesa; GPU-dependent budgets would be fiction). Budgets to fix
  in Phase 0: app RSS ceiling (target ≤ ~200 MB to keep headroom on the
  1 GB boxes), idle CPU between events ≈ 0, full-frame repaint time on a
  1.5 GHz in-order core with partial-redraw expectations, daemon cold
  start, sync-cycle wall time and poll-idle cost, binary size. Map
  existing benches (storage hot path) against budget-relevant paths; gap
  candidates: engine transition latency, DTO↔domain mapping, UI
  (software-renderer) repaint cost, sync poll cycle. On-device
  validation happens through the kiosk bring-up spike (backlog entry of
  2026-10-16) once hardware is set up — until then the budgets are
  analytic targets derived from the device class. Decide whether the
  Bencher continuous-tracking backlog entry graduates into the
  remediation plan.

### K. Concurrency, lifecycle & backpressure *(addition)*
- Question: shutdown ordering, bounded channels, broadcast lag, blocking-in-
  async.
- Method: from the Phase-1 diagram: audit every mpsc for boundedness and
  full-channel behavior; broadcast lag handling (`RecvError::Lagged`) for
  long-uptime kiosk listeners; graceful-shutdown order (UI → sync flush →
  outbox durability → storage close) vs implementation; any blocking calls
  (keyring, rpassword, std::fs) on runtime threads.

### L. Time, clocks & DST *(addition)*
- Question: reminder correctness across timezones/DST; consistent clock
  seams.
- Method: inventory every time source (chrono usage, injected clock seams);
  verify reminders scheduling survives DST transitions and timezone change;
  check sync timestamp comparisons vs the clock-skew backlog entry.

### M. Sync & persistence semantics *(addition)*
- Question: does the implementation match ADR 0004/0005/0007, and are the
  known crash windows understood?
- Method: code review of conflict policy vs ADR 0004; outbox
  crash-safety/duplicate-create window (existing backlog entry — verify
  severity); tombstone lifecycle; migration idempotency; the standalone↔
  nextcloud connector switch (ADR 0010) edge cases.

### N. Security pass *(addition)*
- Question: credential handling, IPC surface, logging hygiene.
- Method: secrets in tracing/log output; keyring interaction points; IPC
  socket permissions & authentication model (ADR 0012) for kiosk use;
  `--json`/status output leaking sensitive data; WebDAV path construction.

### O. `unsafe` & boundary enforcement *(addition)*
- Question: ui-slint is the one crate without `#![forbid(unsafe_code)]` —
  how much unsafe exists and is it warranted? And can the architecture
  rules become machine-checked?
- Method: audit unsafe blocks in ui-slint; propose (and, in remediation,
  add) CI-enforceable boundary checks — e.g. cargo-deny bans keeping
  domain free of async/net/UI deps — so "domain is pure" stops being a
  convention.

### P. Docs & ADR drift *(addition)*
- Question: do architecture.org/testing_strategy.org/ADRs describe the
  system that actually shipped?
- Method: section-by-section diff of claims vs code (channel inventory,
  crate roles, test tiers); resolve the missing ADR 0013; check CHANGELOG
  vs actual v0.1.0 contents.

### Q. Backlog reconciliation *(addition, deliverable not just axis)*
- Question: "no known technical debt remaining" is achieved by making every
  debt item fixed, scheduled, or explicitly accepted — the backlog must be
  an accurate ledger.
- Method: walk all ~80 entries; mark done-and-prunable / still-open /
  obsolete-at-v0.1.0; attach severity; fold audit findings in with
  consistent entry format.

## 3. Findings Format & Severity

Every finding is recorded as: **ID · severity · axis · evidence (`file:line`
or workflow path) · proposed action · effort guess (S/M/L)**.

- **P0** — would block or embarrass the v0.1.x line (correctness in sync/
  reminders, security, data loss). Fix in the first remediation wave.
- **P1** — will make the next feature wave (D1–D6, reminders polish,
  multi-board) measurably harder. Fix soon; schedule explicitly.
- **P2** — quality-of-life/determinism/docs debt. Backlog entry with
  severity, no commitment.
- **P3** — observation/accepted risk; recorded so it is *known* debt.

## 4. Phases & Deliverables

Execution is chunked by a dispatch plan generated from the §9 handoff
prompt; the phase boundaries below are the chunking seams.

### Phase 0 — Freeze & baseline (mechanical, ~½ day)
Tag v0.1.0 (release pipeline does this). On the tag, collect:
llvm-cov per crate; latest mutants survivor report (plus optional one-off
runs for storage-sqlite & sync-nextcloud); one-off `clippy --workspace --
-W clippy::pedantic` inventory (report-only); cargo-machete unused-dep
scan; SonarCloud duplication/complexity dump; git churn heatmap (files by
commit count — refactor-risk signal); test-suite wall-time and slowest-20
list; snapshot inventory.
→ `.artifacts/reports/2026-10-XX-v0.1.0-audit-baseline-metrics-report.md`

### Phase 1 — Flow model (~½ day)
Build the D-axis data & control flow diagram from `bootstrap.rs` and actor
spawn sites; every edge typed and referenced to code.
→ diagram + edge table (inside the baseline report or its own report);
recommend promotion into `docs/` post-audit.

### Phase 2 — Per-crate deep audits (parallelizable, ~½–1 day/crate agent-assisted)
Six chunks — domain, state, storage-sqlite, sync-nextcloud, ui-slint, app —
each running the fixed checklist: boundaries (E), naming (G), data-model
fit (F), error taxonomy (I.4), duplication/complexity hotspots (H), test
structure per testing-strategy layers (B/C). Chunk tasks are self-contained
and read-only, matching the dispatch-plan execution pattern.
→ per-crate sections of the findings report.

### Phase 3 — Cross-cutting audits (parallelizable, ~½–1 day each)
(a) K concurrency/lifecycle/backpressure; (b) M sync & persistence
semantics vs ADRs; (c) L time/DST/reminders; (d) N security; (e) J
performance budgets & bench gaps; (f) B+C test-quality synthesis (risk map,
mutant triage, determinism sweep, gated-test verification, flaky-watchlist
status); (g) P docs/ADR drift.
→ cross-cutting sections of the findings report.

### Phase 4 — Synthesis & decisions (~½ day + user session)
Merge everything into:
→ `.artifacts/reports/2026-10-XX-v0.1.0-audit-findings-report.md`
  (severity-sorted, one line per finding, evidence links);
→ reconciled improvements backlog (axis Q);
→ optional `2026-10-XX-v0.1.0-remediation-dispatch-plan.md` chunking the
  P0/P1 fixes into the three-stage agent protocol;
→ user decision session: accept-as-risk vs schedule for each P1/P2.

## 5. Method Rules

- **Audit the tag.** All phases run against `v0.1.0`, so findings are
  reproducible and not invalidated by post-release work.
- **Read-only discipline.** The audit writes reports and backlog entries
  only. No drive-by code fixes — they would bias the findings and muddy
  the remediation plan. (Reports/backlog land via a `docs/` branch + PR
  per AGENTS.md §8.)
- **Evidence or it isn't a finding.** Every claim cites `file:line`,
  a workflow path, or a Phase-0 metric.
- **No new percentage targets.** Per AGENTS.md §5 spirit: coverage and
  mutants are triage inputs against a risk map, not success ceilings.
- **Findings bias toward decisions.** A finding without a proposed action
  and severity is an observation, and gets marked P3.

## 6. Out of Scope

- Any code change, however small (including fixes for bugs found — they
  become backlog/dispatch items).
- Pre-deciding D1–D6 (the future-directions decisions); the audit only
  reports friction, it does not choose.
- Running the flaky/live tiers beyond what `nextcloud-integration.yml`
  already does; setting up new CI jobs (Bencher etc. stay backlog items
  unless the user promotes them during Phase 4).

## 8. Verification & Acceptance

- Every axis in §2 maps to at least one finding, an explicit "clean"
  verdict, or an accepted-risk entry — no silent skips.
- The findings report's every P0/P1 has a proposed action.
- The backlog, after reconciliation, contains zero entries that are
  secretly done or obsolete.
- The flow diagram's every edge resolves to real code that a reviewer can
  click; spot-checked by the user in the Phase-4 session.
