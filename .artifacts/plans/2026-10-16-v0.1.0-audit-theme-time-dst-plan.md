**Partition rule (D1)**: every hit is classified production vs test —

**Seam-vs-direct rubric (D3)** — one verdict per production hit:

| Verdict | Meaning | Requirement to record |
|---|---|---|
| `SEAM` | Reads time only via injected `dyn Clock` (or *is* `SystemClock`) | The injection path |
| `DIRECT-JUSTIFIED` | Wall read outside the seam that is (i) presentation/ephemeral only — never persisted, never compared against stored instants — and (iii) sits in a component with no injectable seam | Which of (i)/(iii) holds and why the read cannot flow through state |
| `DIRECT-FINDING` | Wall read that (a) feeds anything persisted or compared, (b) sits where the seam exists/imports, or (c) creates a **second time authority** concurrent with the engine clock | Which of (a)/(b)/(c) fired + the observable anomaly it can cause |
| `MONOTONIC-OK` | `Instant`/`sleep_until`/interval for pacing/deadlines | Finding only if mixed with wall-clock arithmetic (wall value derived from a monotonic base or vice versa) |
| `CONVERSION` | Parse/format/localize site (no clock read) | DST semantics judged in §3.3 scenarios |

Census table schema (fixed columns): `# · file:line @ v0.1.0 · class
(W1..W5) · prod/test · reads (wall/mono/derived/none-conversion) · seam

### 3.2 Reminder-scheduling trace (hop by hop)

Walk the full path; each hop answers: *who reads what clock, in which
representation, with what precision* — recorded as a trace-table row.
Any hop where representation changes (text ↔ `DateTime`, offset ↔
seconds, zone conversion) or precision truncates is flagged as a
scenario input for §3.3.

1. **Input**: `--due` (`cli.rs:242-256`) → `DateTime<Utc>`;
   `tasks remind --before` / `[reminders] default_before` →
   `TimeDelta` (integer s|m|h|d grammar — `config::parse_before`).
   Also enumerate *every other writer* of `Task.duedate` (IPC commands?
   sync: does a Deck card carry a due date, and with what timezone
   semantics at `mapping.rs`?).
2. **Rule construction**: command planner → `ReminderRule { offset ≤ 0,
   created_at }` — whose clock stamps `created_at`; can a sub-second
   offset exist through any public surface (CLI grammar says no;
   `ReminderOffset::before` is public API)?
3. **Engine tick arm** (`actor.rs:337-473`): cadence monotonic
   (`sleep_until`), default 30 s, default-off; the clock is read once
   per tick inside `reminder_tick` (`:779`). Bound the max firing
   lateness = tick period + loop delay. (Cancellation-safety of the arm
   is chunk 9's — cross-ref only.)
4. **Evaluation** (`reminders.rs`): `due_firings(now)` — confirm the
   `occurrence ≤ now && !delivered` predicate and catch-up semantics
   from code; `occurrence_of` formula (duedate + offset — pin the exact
   expression); snooze chain walk (`effective_occurrence`); mute.
5. **Delivery & persistence round-trip fidelity**: `RecordReminderDelivery`
   (stamped at the tick's read, `actor.rs:809`) → `reminder_deliveries`
   PK `(reminder, occurrence)` TEXT rfc3339 (`repo.rs`, migration
   0004). Resolve concretely: after a restart/reload, is the proof's
   occurrence key **byte/parse-identical** to the evaluator's
   recomputed occurrence? Two specific hazards to adjudicate, not
   assume: (i) `offset_seconds` truncation toward zero on persist
   (`repo.rs:980-987`) vs an in-memory sub-second offset — recomputed
   occurrence shifts, proof no longer matches exact-equality
   (`reminders.rs:231-234`) → re-arm/double-fire; (ii) rfc3339
   sub-second round-trip through `to_rfc3339`/`parse_from_rfc3339`
   (`reminders.rs:160-183`). State which hazard is *reachable through
   v0.1.0 surfaces* (CLI grammar constrains offsets to whole seconds)
   vs only through public API — severity differs accordingly.
6. **Notification fan-out**: engine `Notification` (occurrence rfc3339)
   → notifier channel (capacity 64, `notifications.rs:14`) → `LogSink`
   (`:48-60`). Time fact only: the sink logs `occurrence.to_rfc3339()`.
7. **Display paths** (the second-authority question): CLI
   `DueContext::compute(state, Utc::now())` (`output.rs:554`), UI
   overdue/wall-minute computations (`ui-slint/lib.rs:211`, `:921`,
   `presentation.rs:330/389`) — each reads the wall clock *outside* the
   engine's clock; judge ordering/staleness anomalies (a task shown
   overdue in the UI before/after the engine's own tick judges it).
8. **Config surfaces**: `[reminders] enabled/tick`, `[sync]
   poll_interval_secs` (`bootstrap.rs:545`) — pacing only (monotonic).

### 3.3 DST & timezone scenarios (fixed verdict template)

Template per scenario — every field mandatory, the code-path field
carries `file:line`:

> **Precondition** (stored data + zone) → **Transition event** → **Code
> path walked** (file:line) → **Representation at each step**
> (instant/wall/naive/text) → **Outcome** (holds / breaks /
> holds-by-representation) → if breaks: severity + proposed action
> (conv 4).

- **S1 — spring-forward gap**: a due/occurrence inside a nonexistent
  local hour. Expected verdict path: all comparisons are UTC instants
  (`due_firings` predicate, `DateTime<Utc>` end-to-end) and no local
  wall construction exists (W2 negative grep) → *holds by
  representation*; the verdict must cite both the predicate and the
  negative grep, not chrono's docs (D4).
- **S2 — fall-back overlap**: an ambiguous local wall time maps to one
  instant; same proof shape as S1 (no wall→instant resolution exists to
  be ambiguous).
- **S3 — timezone change while scheduled**: host zone changes after a
  rule is stored. Firing instants are UTC-anchored → unchanged; the
  user-visible semantics ("9:00 stays the *old* zone's 9:00, never
  re-anchors") is recorded as the product fact. Includes **catch-up**:
  occurrences that passed while the daemon was down fire on the first
  tick (`actor.rs:337-341` immediate first tick + `due_firings` ≤-now
  predicate) — verify from code that no "too stale to fire" cutoff
  exists.
- **S4 — wall-clock vs instant storage** (the product-semantics
  scenario): (a) bare `YYYY-MM-DD` → midnight **UTC** (`cli.rs:253`) —
  a user at UTC+2 setting a due date gets a 02:00-local occurrence;
  (b) RFC-3339 *without* offset is rejected (`parse_from_rfc3339`
  requires one — verify the error path); (c) display zone: enumerate
  where due dates are rendered (CLI `task_row`/`DueContext`
  `output.rs:527/554`, UI presentation) and which zone the rendering
  uses. Verdict is decision-grade: either "intended UTC-only product —
  document it" or "local-wall intent silently lost" with options,
  trade-offs, one recommendation.
- **S5 — host clock step vs monotonic tick** (added; D5): the tick arm
  schedules on tokio monotonic time (`sleep_until`, `actor.rs:463`)
  while occurrence comparison reads the *wall* clock — a backward NTP
  step re-arms ticks without re-firing delivered proofs (proofs key on
  occurrence, not on tick time — verify), a forward step fires
  catch-up on the next tick. Reason the mono/wall pairing explicitly;
  it is the one place two time authorities are *composed*, not merely
  co-existing.

### 3.4 Sync clock-skew verification (backlog-entry severity)

1. **Enumerate comparison sites**: every ordering over `DateTime<Utc>`
   that compares *different machines'* clocks. Seeded from orientation:
   `merge.rs:75` (`max_ts`), `:170` (`merge_task`), `:265-272`
   (tombstone `observed_at`), `:287-321` (echo normalization +
   seconds-resolution comment), `:754`/`:769` (board/stack tombstones);
   extend through `pipeline.rs`, `outbox.rs`, storage write clocks
   (`BoardClocks`, migration 0002) — exhaustive like the census.
2. **Determine each operand's origin**: local `Clock` read (which
   component, taken when) vs server-derived (Deck `lastModified`
   seconds, `mapping.rs:296`, server clock, seconds resolution) vs
   mixed. This is what makes a comparison "cross-machine wall clock".
3. **Construct the misordering interleavings concretely** (event order →
   wrong outcome), at minimum: (i) local edit at T, remote echo carries
   server lm = T+δ → echo normalization shadows/reverts the local
   field; (ii) local delete observed at T vs remote write stamped
   T+δ → resurrect-vs-keep flips; (iii) seconds-resolution tie
   ("ties keep local", `merge.rs:70`) vs sub-second local stamps.
4. **Judge the backlog entry**: verified severity recommendation
   (P0–P3, origin §3) + whether the remote-age-bias sketch remains the
   right fix shape + whether the entry's condition ("if real-server use
   shows symptoms") still stands given what the code now does (e.g. the
   echo-normalization comment `merge.rs:287`). Output as the
   **clock-skew severity note for chunk 17** (D8); the backlog file is
   never touched.
