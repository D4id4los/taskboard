## 3. Per-axis checklist (the stage-2 procedure)

### 3.1 E — crate & module factoring (the headline axis)

1. **Responsibility inventory**: classify each of the 30 modules as
   (i) app's legitimate job (process glue, config, secrets,
   lockfile, bootstrap, dispatch, exit codes — ADR 0008/0009),
   (ii) extraction candidate, (iii) logic misplaced per the
   dumb-client rule / state-engine ownership. Every module gets a
   row — the completed table is the no-silent-skips proof for a
   14.5k-line crate (dispatch acceptance; D2).
2. **IPC extraction eval** (measured 1 795 lines across five modules;
   origin §2 E says "~1.5k" — D1): options at minimum {keep in app;
   new `taskboard-ipc` crate carrying protocol+codec only; full
   crate carrying all five modules}; trade-offs must include who
   else consumes it (kiosk-management wave — origin §1 near-term),
   the socket-sidecar/lockfile naming coupling, and test-tier moves;
   ONE recommendation + consequences for the kiosk/IPC wave.
3. **`completion.rs` extraction eval** (1 593 lines): module doc
   claims a pure-function core (`tokenize_prefix` / `plan` /
   `candidates` / `complete`; "no I/O, no channels, no runtime, no
   rustyline types"). Options {stay; move to domain; own
   frontend-support crate; fold into a future repl/frontend crate}.
   The selector-parity invariant (completion must mirror the domain
   `resolve_*` semantics — completion.rs doc "Parity with the
   selectors") is the coupling to weigh: where should that coupling
   live?
4. **`commands/output.rs` eval** (565 lines): the origin §2 E
   question "does `--json` shaping leak presentation into app
   logic?" — adjudicated against ADR 0009 §output (typed serde
   projections, never the domain's serde shapes, `{"error":{"kind":…
   }}` on stderr). A "correctly placed" verdict is acceptable if
   evidenced (D5).
5. **Co-largest adjudication** (dispatch acceptance: a verdict, not
   a deferral): synthesise 1–4 into split / don't-split /
   split-later-with-trigger; the trigger to evaluate is the
   kiosk/IPC-management wave and any second frontend.
6. **Dumb-client violation scan**: AGENTS §2 — the UI layer is a dumb
   presentation client; app's own frontends (commands/*, repl.rs,
   ui.rs) equally must not own business/state logic. Named suspects
   to verify (not presume): the due-banner derivation in
   `commands/output.rs` (`DueMarker` — banner truth derived from the
   task's own due date: domain logic?); completion parity rules
   duplicating domain selection semantics; `commands/reminders.rs`
   (435 lines — domain owns the model, what is app's share?);
   `commands/connect.rs` (719) + `session_ceremonies.rs` (308) — the
   connect session state machine; repl editing semantics. A
   violation is a finding with a proposed home, never a fix.

### 3.2 G — naming & taxonomic drift

Enumerate pub items per module (the `pub mod`/`pub use` surface from
`src/lib.rs:32–44` plus each module's own). Check: module name vs
contents (`session_ceremonies.rs` is the local suspect;
`notifications.rs` vs the GUI notify path; `commands/mod.rs` is the
dispatcher, not "commands"); doc-comment claims vs behavior (the
lib.rs role map; `ipc/mod.rs:1–17`; completion.rs invariants;
output.rs stability note "internal-but-scriptable"); variant names
vs produced semantics (`CommandError::error_kind` strings are also a
G surface — do the kind strings say what the variants do?); AppMode
vocabulary vs the mode-gate reality (§2). Cross-crate verdicts →
facts + cross-ref chunk 17.

### 3.3 F — data-model fit (app-owned shapes only)

Domain structs are chunk 3's, UI models chunk 7's. App-owned shapes
to review for D1–D6 friction: `AppConfig` sections (`[app]` mode,
`[nextcloud]`, `[ui]`, `[reminders]` — serde `deny_unknown_fields`)
vs multi-board (D2) and kiosk configurations; `CommandError` +
`error_kind` taxonomy (extensible where the D-waves add outcomes?);
IPC `Request`/`Response` envelopes (versioned — how do new verbs and
kiosk-management messages land? single-board assumptions?);
`repl_history` persistence format; lockfile/socket-sidecar naming
contracts. For each: does it force awkward flow for a **named**
D-decision or wave? Friction findings only — the audit does not
pre-decide D1–D6 (origin §6).

### 3.4 I.4 — error taxonomy

1. **color-eyre confinement**: exhaustive grep over `src/` (seed
   sites §2); rule per AGENTS §4 — dynamic errors at the binary top
   level. Adjudicate each site: main.rs paths are binary glue;
   `ui.rs:157 run_desktop` sits in the lib — the yardstick reading
   is recorded as a rule (D4), not per-site special-pleading.
2. **Typed-error layer map**: the 9+ thiserror enums, what each
   covers, the conversion seams (`BootstrapError`→`CommandError`,
   IPC client errors → `CommandError`, sync errors → ?), and where
   typed errors are stringified crossing tiers (REPL display, IPC
   error rendering, `report()`) — stringification at a presentation
   boundary is fine; mid-layer stringification is a finding.
3. `unwrap`/`expect`/panic reachability in lib/daemon paths → facts
   + cross-ref chunk 9 (I.3 owns daemon-reachable verdicts).

### 3.5 H — duplication & complexity

Inputs: `§sonar` (app duplication is **test-only**: the
`cli_standalone`/`cli_lock`/`cli_*`/`it_cli` clusters; `src` has no
Sonar clusters — the manual pass is the instrument, D6); `§churn`
(`commands/mod.rs` 36 = the workspace's hottest file; `main.rs` 17,
`output.rs` 16, `tasks.rs` 15, `cli.rs` 15). Manual pass:
(a) the verb-handler shape across `commands/*.rs` (parse → resolve →
dispatch → render — shared or copy-paste?); (b) completion.rs vs
domain `resolve_*` parity (duplication by design? a shared
selection-rules seam?); (c) `config.rs` at 1 152 lines — structure
review (how much is inline tests vs logic?); (d) `repl.rs` 1 122 and
its overlap with `cli_tty`/`cli_editing` tests; (e) the test harness
(`tests/common/mod.rs`, 470) — would a richer harness collapse the
Sonar test clusters? Each candidate gets a concrete simplification
sketch, not "this is complex" (origin §2 H).

### 3.6 B/C — test quality & determinism (crate-scoped; suite-wide is chunk 14's)

1. **Test-tier map** (the dispatch prompt's "E2E/REPL test-tier
   map"): for each of the 22 files — layer per testing_strategy.org,
   hermetic vs gated, what it actually covers. The 11 gated fns and
   their CI wiring (mcp_smoke ↔ `ui-mcp-smoke` job) recorded as
   facts; gated-test verification verdicts are chunk 14's
   (cross-ref).
2. **Risk map** (the B instrument — mutant evidence is absent, D9):
   the app behaviors whose breakage would be worst — IPC
   byte-identical relay contract (ADR 0012), config precedence +
   secret-free-by-construction, dispatch routing/exit codes (ADR
   0009), daemon lifecycle/lockfile, REPL editing/history,
   completion parity, secrets redaction — and whether each has a
   test at the right layer.
3. **§cov gap**: locate the 606 uncovered lines (which modules;
   `src` inline tests vs `tests/`); negative signal only, no
   percentage targets (origin §5; D8 for the method).
4. **§timing explanations**: read the 9 app rows' sources — real
   timeout waits vs paused clocks (`cli_verbs::v6` "sync failure and
   timeout" at 10.05 s suggests a real timeout burn; AGENTS §5
   forbids sleeps — does the timeout path use a seam?); cite
   `§timing`, don't re-run (D7).
5. **Determinism greps, crate-scoped**: `sleep`, wall-clock `now()`
   in non-seam paths, unbounded channels, fs/env touches in unit
   tiers; the repl_history EACCES flaky-watchlist entry is app-owned
   — verify its status locally (fixed/live), cross-ref chunk 14.
6. **Layering per AGENTS §5** ("one behavior, one test, lowest
   layer"): app tests should test routing/glue, not re-test
   domain/state behavior; wiremock-in-app-tests (`cli_connect`,
   `dispatch_routing`, …) — is app re-testing sync-crate contract
   behavior? Cross-tier duplication is a finding.
