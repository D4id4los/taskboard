## 3. Client/actor split evaluation (axis E deliverable — the headline)

Produce the decision-grade evaluation the dispatch acceptance demands:
options, trade-offs, **exactly one recommendation**, and consequences
for the kiosk/IPC wave. Protocol:

1. **Role & dependency inventory** (table, `file:line` evidence):
   module → role (client-side / actor-side / bridge), pub-item count,
   imports (who-depends-on-whom inside the crate). Seeds in §1.1 —
   stage 2 verifies and completes the matrix (incl. test-file
   dependencies: contract.rs needs only the client half;
   actor_wiremock/e2e_hermetic need both).
2. **Coupling-point inventory**: every place the actor half touches the
   client half beyond the plain pub API — `Fetch<T>`, `Validators`,
   `RetrySleep`, `NewCard`/`*Changes` shapes (mapping.rs builds them),
   `DeckClient` construction (`SyncActorConfig`) — and every place
   domain types flow in either direction. This is the evidence a
   reviewer can click (dispatch prompt 6.3 checks "not vibes").
3. **Options to evaluate** (all four, pros/cons each):
   - **O0 — status quo**: one crate, module boundary as the seam.
   - **O1 — extract a `taskboard-deck-client` crate** (client, model,
     color, ocs, backoff, error ± mapping), leaving actor/push_exec/
     poll in sync-nextcloud (renamed or not).
   - **O2 — trait seam only**: introduce a connector-facing port trait
     (domain or crate-local) so the actor depends on an abstraction —
     the ADR 0010 "engine stays connector-blind, connector is a
     translator" stance (file-sync report) without moving code.
   - **O3 — further split of the actor half** (push_exec as its own
     module tree/crate) — evaluate primarily as the push_exec-2 678-
     lines pressure valve against O1's scope.
4. **Fixed evaluation criteria** (score each option against each):
   (a) compile-firewall value at the existing seams (how much of the
   145-touch churn, §churn, is client-half vs actor-half);
   (b) test-suite value (contract tier hermetic per crate; mutants
   one-off scope alignment — the 44 survivors split across both
   halves);
   (c) friction for the named waves — kiosk/IPC wave, D1 sidecar
   (Wave-1 client-surface extension, roundtrip report §4), second
   connector (file-sync report), D5 substrate;
   (d) AGENTS §2 boundary-rule clarity (would the rule text get
   simpler or more conditional?);
   (e) cost — pub-API churn, import rewrites, workspace-crate count
   vs the project's crate-boundary discipline;
   (f) kiosk binary/memory impact (workspace builds one binary —
   crate splits don't change codegen; verify before claiming).
5. **Recommendation**: one option, with consequences for the kiosk/IPC
   wave stated explicitly, and the first concrete step if accepted
   (e.g. "extract crate X, move modules A/B/C, re-point mapping") — a
   recommendation sketch, NOT a migration plan (origin §6: the audit
   does not implement).

Binding inputs (established, do not re-derive): ADR 0010
(standalone-first, pluggable connectors); file-sync connector report's
recommendation shape; deck-roundtrip report's Wave-1 client-surface
consequences; AGENTS §2 crate rules; churn/sonar/mutant baselines.
