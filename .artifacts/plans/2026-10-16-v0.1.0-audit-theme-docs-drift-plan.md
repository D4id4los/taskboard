## 3. Audit procedure (stage 2 executes; strictly read-only on the tag tree)

### 3.0 Claim-extraction method (common to §3.1–§3.5)

A **normative claim** is any doc statement about what the system *is,
does, owns, must, or forbids* — architecture facts, ownership and
protocol descriptions, tool behavior, rules, and structural tables.
Narrative context, rationale, and history ("we chose X because") are
not claims; ADR *Context* sections are historical by design (D8).

Per doc, stage 2 builds a **claim register**: one row per claim with
`claim-ID · doc text (quoted, with line range) · code evidence mapped
(file:line @ v0.1.0) · verdict`. Verdict vocabulary (fixed by the
dispatch acceptance criteria):

- **matches-code** — the claim accurately describes the tag tree;
- **drifted** — the claim describes a different mechanism than shipped
  (report quotes *both sides*: the doc text and the contradicting
  code `file:line`);
- **obsolete** — the claim describes something that no longer exists
  at the tag at all.

Granularity (D9): the report carries **one verdict row per doc
section** (and per ADR), with detailed sub-rows *only* for
drifted/obsolete claims; matching claims are counted per section, not
enumerated. Every claim still gets a register row; the full register
is an appendix table of the report. A claim that cannot be verified
against the tag tree is a planning failure to resolve in the report's
method note — "unverifiable" is not an allowed verdict (D9).

Evidence rules: worktree line numbers are tag line numbers (the
worktree is the tag tree); code claims cite `file:line`; CI/tooling
claims cite workflow paths; tool-behavior claims may cite the tool's
config in-tree. Where checking a claim requires running a read-only
command (e.g. `cargo metadata`, `git grep`, `scripts/changelog.py
self-test` — D6), the exact command is recorded verbatim in the
report's method section.

## 4. Decisions (open questions resolved at planning time)

- **D1 — Scope of "the docs"**: claim-extraction subjects are exactly
  `docs/architecture.org`, `docs/testing_strategy.org`,
  `docs/coding_guidelines.org`, the 14 ADRs, and `CHANGELOG.md`, all
  at the tag. `AGENTS.md` and `README.org` are out of scope (origin
  §2 P names the three guides + ADRs; the dispatch adds the CHANGELOG;
  AGENTS.md is the audit's own normative input, and README drift is
  real but unassigned — if incidentally observed, it becomes a P3
  observation naming it as un-audited surface, per the scope-
  discipline mandate).
- **D2 — Claim unit**: normative claims only (§3.0); narrative and
  ADR Context sections are exempt. Rationale: the axis asks whether
  docs *describe the shipped system*, not whether their history is
  well-written.
- **D3 — Channel ground truth**: chunk 2's edge table alone; zero
  channel re-derivation in this chunk. Any apparent chunk-2 error is
  reported as a *question for chunk 17* (P3 cross-ref), not silently
  re-derived — the dispatch's input contract.
- **D4 — S6 adjudication split**: docs-wording verdicts here;
  identifier-quality verdicts stay with chunks 3/4 (cross-ref). This
  mirrors chunk 2 §2's explicit hand-off.
- **D5 — ADR-0013 verdict taxonomy**: "withdrawn" requires evidence
  of a decision to abandon (none exists at planning time); anything
  else with an empty file history is an "accident". The finding
  targets the *missing formal record for shipped decisions*, not the
  numbering skip itself (the skip is honest bookkeeping, tracked).
- **D6 — Script execution policy**: only `scripts/changelog.py
  self-test` may run, after re-reading confirms it is side-effect
  free; `promote`/`extract` against the repo file are forbidden
  (promote writes; extract is unnecessary — the section is readable
  directly). Read-only discipline (origin §5) overrides convenience.
- **D7 — Sibling-chunk boundary**: chunk 15 checks *doc-vs-reality*;
  quality/correctness/naming verdicts stay with their owning chunks
  (3–8 crates, 9 concurrency, 10 sync, 11 time, 12 security, 13 perf,
  14 tests). Every overlap is resolved by cross-referencing the
  sibling's finding ID via conv 2, never by re-auditing. Where the
  sibling report is not yet merged, the docs verdict stands alone and
  names the pending cross-ref.
- **D8 — ADR depth**: Decision sections fully checked; Consequences
  checked where they assert current behavior; Context exempt.
- **D9 — Register granularity & report size**: full per-claim
  register as a report appendix; per-section verdict rows in the body
  (dispatch acceptance wording). No "unverifiable" verdict —
  everything is checkable against the tag tree or a workflow path;
  a genuinely uncheckable claim means the plan mis-scoped and is
  recorded in the deviations section instead.
- **D10 — Severity calibration**: P1 = drift that would mislead
  near-term architecture/contribution work (wrong channel ownership,
  wrong crate boundary, a mechanism described that does not exist, a
  tool/CI job described that was never wired); P2 = misleading-but-
  survivable docs debt (imprecise attribution, omissions of real
  subsystems); P3 = formatting/style observations (Keep-a-Changelog
  conformance, wording polish). Docs-only chunk: P0 is not expected;
  if a doc claim misdescribes *data-safety* behavior (e.g. conflict
  policy), the P0/P1 call follows origin §3's definitions and the
  correctness adjudication cross-refs the owning chunk.
- **D11 — Baseline inputs**: §env + §cov (dispatch floor) + §snapshots
  (recorded reason in §2.2). Nothing else.
- **D12 — CHANGELOG semantics**: v0.1.0 = first release ⇒ "actual
  contents" = the tag's full user-visible surface (forward + reverse
  checks per §3.7); entries are mapped to code, not to commit
  messages (the changelog is curated prose, commits are not the
  contract).
