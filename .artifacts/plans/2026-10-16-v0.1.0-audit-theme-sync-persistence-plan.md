## 2. Claim-extraction procedure (per ADR)

### 2.1 The procedure

For each ADR (0004, 0005, 0007, 0010), stage 2:

1. **Extract normative claims** section by section. A claim is any
   statement that constrains what the code must do (or must have
   documented as a limitation): Decision-section rules, documented
   limitations and accepted-risk statements, amendments, and behavioral
   Consequences. Context-section wire facts (Deck's behavior) are
   evidence context, not claims. The seeded inventories in §2.2 are a
   **floor, not a ceiling** — re-walk every ADR section and add missed
   claims as new rows (decision §D3; the review gate checks per-section
   coverage).
2. **Assign a stable ID**: `C04-NN` / `C05-NN` / `C07-NN` / `C10-NN`.
3. **Map each claim to code** — grep/read from the seed locations in
   §1.2 outward; every mapping records `file:line @ 925f50e`.
4. **Verdict** (fixed vocabulary, §D2): `confirmed` /
   `partially-implemented` / `contradicted` /
   `confirmed-by-test-reference` (behavior pinned by an existing test —
   cite the test `file:line`; tier-4 docker scenarios are cited, never
   run, origin §6) / `process-claim` (mechanism verified, e.g. sqlx
   checksumming).
5. **Quote rule** (§D4): every `partially-implemented` / `contradicted`
   verdict quotes the ADR line and the code line **verbatim** — no
   paraphrase drift (the review gate re-checks quotes).
6. Claim violations become conv-4 findings (`F10-NN · P0–P3 · axis M ·
   evidence · proposed action · effort S/M/L`); a claim whose breach is
   an explicitly documented ADR limitation is recorded as
   accepted-risk, not a finding.

## 3. Crash-window enumeration method

### 3.1 Method

A **crash window** is an interleaving of a crash/restart with in-flight
work that yields a wrong durable outcome. For each window, stage 2
records, in a fixed template:

1. **Interleaving**: numbered event order (each step `file:line @
   925f50e`), from intent origination to durable landing, with the
   crash point(s) marked.
2. **Crash class** (§D6): *app crash* (process dies; WAL+NORMAL
   preserves committed transactions per ADR 0005) vs *OS crash / power
   loss* (newest commits may drop). A window may differ per class.
3. **Post-crash durable state**: what `load()` returns after reboot.
4. **Next-cycle behavior**: what the sync cycle / engine does with that
   state (re-POST? re-DELETE? tombstone? data loss? duplicate?).
5. **Verdict + severity**: wrong outcome (finding, conv-4) / benign
   (idempotent recovery, accepted-risk with evidence) — severity per
   origin §3 (data loss outranks duplication; duplication outranks
   cosmetic).

The channel hops inside an interleaving are **ordering facts** only —
boundedness/close-semantics verdicts belong to chunk 9 (§D9); cite
chunk 2's edge table where a hop needs identification instead of
re-deriving it.

## 6. Decisions (open questions resolved at planning time)

- **D1 — claim sources**: Decision sections + documented limitations +
  accepted risks + amendments + behavioral Consequences are normative;
  Context-section wire facts are evidence context only.
- **D2 — verdict vocabulary**: `confirmed` / `partially-implemented` /
  `contradicted` / `confirmed-by-test-reference` / `process-claim`;
  fixed, no synonyms, so the review gate can machine-check presence.
- **D3 — completeness guarantee**: §2.2 tables are a floor; stage 2
  re-walks each ADR section and adds missed claims; the report tables
  carry a per-ADR section checklist so silent skips are visible.
- **D4 — quote rule**: partial/contradicted verdicts quote ADR text and
  code verbatim (anti-paraphrase-drift; dispatch review prompt 10.3
  enforces).
- **D5 — baseline scope**: named inputs `§cov`/`§sonar`/`§churn` cited
  by anchor; `§mutants` (b) one-off survivors **may** be cited as
  supplementary risk context (dead-board-guard survivors bear directly
  on ADR 0007 claim pinning). Citation of an already-collected anchor
  is conv-6-compliant; nothing is re-run.
- **D6 — crash classes**: app crash vs OS crash/power loss judged
  separately wherever WAL durability differs (W3 vs W1-class windows).
- **D7 — migration re-run**: judged analytically from the sqlx version
  pinned in `Cargo.lock` at the tag + the migration SQL; optional

## 7. Risks

- **Volume**: ~8.4k lines across the four crates' key files; mitigation

  bounded grep-and-read.

  §D4 + the stage-3 gate re-checking quotes.
- **Test-strength vs claim conflation**: `§mutants` survivors in
  dead-board guards (e.g. `actor.rs` :755) are *test-pinning* signals,
  not automatically ADR violations — keep claim verdicts and
  test-strength findings distinct (a survivor in code that implements a

  removed by §D7.
