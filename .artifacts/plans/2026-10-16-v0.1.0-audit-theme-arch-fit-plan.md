## 2. The walkthrough template (binding, all nine)

Each walkthrough section of the report follows this exact structure
(dispatch §17 "acceptance" requires it):

1. **Change summary** — 2–5 sentences: what the wave/decision lands,
   sourced (future-directions §4/§6 row, deck report section, or
   post-tag design doc per PD-3). No options compared here.
2. **Touched crates/files** — table `crate → files → why`, drawn from
   the seam inventory (§1.1) and the tracing of step 3.
3. **Contracts that must move** — table
   `contract → kind (trait/enum/schema/protocol rule) → current home
   (file:line @ v0.1.0) → required movement`. **Exhaustive at the type
   level**: every named type/rule the walkthrough's change forces to
   change appears; representative call sites may be sampled (PD-6),
   citing the flow model's edge/cluster counts instead of
   re-enumerating.
4. **Ripple assessment** — where the change propagates beyond the
   contracts themselves: channel payload growth (edge IDs from chunk
   2's table), snapshot churn (baseline `§snapshots` counts), test
   tiers touched, churn-hotspot overlap (baseline `§churn` — a change
   landing in `commands/mod.rs`/`pipeline.rs` rides the hottest files),
   and any ADR whose text must be re-opened.
5. **Friction findings** — conv-4 rows `F16-NN · severity · axis A ·
   evidence (file:line @ v0.1.0 | input-report §anchor) · proposed
   action · effort`. Where the walkthrough forks on an undecided
   D-question, record each branch's friction briefly (PD-2) — branch
   rows are labeled `branch:`; no branch is preferred.

Severity calibration (audit §3 mapped to friction): **P1** = the
wave cannot land without structural rework (new contract, schema
migration beyond additive columns, or crate-boundary move) — "will
make the next feature wave measurably harder"; **P2** = localized but
real multi-site friction; **P3** = observation / already-laid
foundations worth recording (positive friction facts like "validators
already per-board" are recorded as P3 observations, not findings
against the design). Effort is the *remediation/prep* effort, never
the wave itself.

  "(post-tag design assumption)". Rejected alternatives: ignoring
  them (audits a stale wave shape the user has already accepted

- **PD-4 — theme reports 9–11 as inputs.** The dispatch's input list
  for chunk 16 names crate reports 3–8 only, but chunks 9–11 are

- **PD-5 — finding IDs and keying.** Findings are `F16-NN` (conv 4),
  keyed to walkthrough IDs `W1…W9`, and to edge IDs (`E-xx`) /
  consumed finding IDs (`F3-04` etc.) wherever applicable, so chunk 17

- **PD-6 — depth rule and time-boxing.** Dispatch size is M
  (~½–1 day). Per-walkthrough soft box ≈ 45–60 min agent-equivalent.

  type level; step 4 (ripple) works from the edge table's counts,
  baseline anchors, and sampled call sites — no full call-site
  enumeration (chunk 2 already owns channel/reader inventories).
  W1 and W8 are the expected densest; W6 the lightest.

  Port traits, message/payload enums, IPC protocol types, state &
  schema types, command surface types, outbox shapes,
  `PersistenceAction`, SQL schema objects, UI model seams, config
  types, merge/protocol rules fixed by an ADR. Anything else a wave
  touches is ordinary code (listed in step 2, not step 3).
- **PD-8 — report assembly.** Nine walkthrough sections (template
  §2), then a **cross-walkthrough synthesis** (friction patterns that
  recur across ≥2 walkthroughs — e.g. a contract named by three crate
  reports; shared prep work two waves could amortize — recorded as
  observations, not new findings unless they stand alone), findings
  index (severity-sorted), axis coverage table (conv 5): axis **A**
  verdict + a note that axis **F**'s cross-cutting half is discharged
  here while its crate halves were discharged in chunks 3–8 (consumed,
  §4).
- **PD-9 — no-pre-deciding rubric (enforced; stage 3 re-checks).**
  Allowed shapes: "branch A costs X sites / branch B costs Y", "the

  "the better option", "D1a wins", any ranking of D-options, and any
  wave-design choice that belongs to the wave's own design round. A
  forbidden sentence is a review finding against the report
  (dispatch 16.3). Proposing *remediation prep* (e.g. "extract the
  status map behind a trait first") is allowed only as a finding's
  proposed action, never as a decision.
- **PD-10 — anchor re-verification.** Stage 2 re-verifies every §1.1
  anchor and every anchor it newly cites before a verdict rests on it
  (worktree = tag tree, so worktree lines are tag lines). A failed
  planning anchor is recorded as a planning error in the method
  section and corrected, not silently kept.

## 4. Consumption discipline (crate-report F/E findings, no
re-adjudication)

Chunk 16 **extends, never re-argues**, the merged chunk verdicts. The
mechanics:

- **Cite-as-fact**: a consumed finding (e.g. F3-05) is quoted by ID +
  its evidence anchor; the walkthrough adds only what the crate report
  explicitly deferred ("chunk 16 owns…", "cross-ref chunk 16"):
  cross-layer movement rows, ceremony ripple, and wave-level severity
  calibration.
- **Split/extraction verdicts are standing**: chunk 6's Deck-client vs
  sync-actor split verdict and chunk 8's three extraction verdicts
  (F8-01 split-later-with-trigger, §2.1–§2.3) are consumed as decided
  context. W9 *uses* F8-01's trigger definition ("kiosk management /
  a second wire consumer ⇒ IPC extraction") to state when the
  extraction fires; it does not re-evaluate whether IPC should
  extract.
- **Contradiction rule**: if a walkthrough's tracing appears to
  contradict a consumed finding, chunk 16 records a cross-ref
  contradiction row (both sides, file:line) for chunk 17's
  contradiction-resolution procedure (re-read evidence; never
  re-audit) — it does not silently override.
