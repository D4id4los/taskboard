### 2.1 Pass A — per-channel boundedness, full-channel behavior, close semantics (K + I.2)

For each of the 15 endpoints (§1.2), produce one verdict-table row:

1. **Boundedness** — re-verify capacity constant + constructor line from
   flow §6 (do not re-derive the topology; spot-verify the cited lines).
2. **Full-channel behavior** — classify every production send site:
   `send().await` (sender blocks/parks), `try_send` drop+log,
   `try_send` coalesce (E-06 nudges :593-597), `blocking_send` (EDT
   parks). Judge the *consequence per direction*: on a durability-relevant
   path (E-02/E-03 receipts, E-18 storage commands, E-07 reports) a silent
   drop is a finding; on a coalescing nudge it is the design.
3. **Close semantics** — sender-clone topology (who holds clones:
   E-06 nudge registry fan-out `state/actor.rs:585-604`, E-07 parked twin
   `bootstrap.rs:149/370` + per-attach clones :297, E-30 per-attach
   pairs), which drop closes the channel, which receiver observes
   `None`/`Closed`, and the receiver's reaction (return / linger-drain /
   guard-flag-off / wedge). Every "who notices" claim names the observer's
   line — the dispatch acceptance demands traceability per edge.

Oneshot families: one collective row each for E-19/E-24/E-28 + engine
receipts — dropped-receiver and dropped-sender tolerance (e.g. storage
actor tolerates dropped reply `storage-sqlite/actor.rs:95-96`; engine
`reply:None` fire-and-forget E-01) — capacity n/a by construction.

### 2.2 Pass B — broadcast lag for long-uptime listeners (K)

Per hub × subscriber (SYS: ENG/SYN/SYSLOG/UI; SIG: UI/boot-pull):
what the `Lagged` handler does, whether **`SystemEvent::Shutdown` can be
missed** (a skipped Shutdown must still be caught by channel-close or the
drain flip — trace the fallback), and whether a kiosk-realistic burst can
outpace the UI's 100 ms `try_recv` cadence (`ui-slint/lib.rs:183-209`,
SIG cap 64) leaving a stale-but-marked-dirty render. The SYSLOG
exit-on-Lagged semantic gets an explicit severity verdict against the
daemon's "no live system-event logger afterwards" consequence (D9: judged,
not preset). Correctness only — render *performance* is chunk 13's (D12).

### 2.3 Pass C — shutdown-order trace (K)

Three layers, per process mode (flow §10 matrix: daemon / desktop / REPL
/ one-shot CLI):

1. **Ownership**: spawn sites → join-handle owners (flow §3 rows; abort
   budgets in §1.5 above).
2. **Sequence comparison**: map the audit plan's desired order (UI → sync
   flush → outbox durability → storage close, D6) onto flow §5.2's
   implemented steps (1)-(8). Each desired stage maps to an implemented
   mechanism or is a **gap finding**. Questions stage 2 must answer with
   evidence: does anything stop the frontend before core teardown
   (desktop aborts UIF/EXITW at `ui.rs:202-203` *after* loop return;
   daemon IPC clients simply lose the socket; RPL exits first)? Does a
   mid-flight SYN `cycle`'s final `SyncReport` reach the engine before
   the reports twin drops (linger-drain `state/actor.rs:403` +
   `bootstrap.rs:365-370`)? Is outbox durability *ordered* before storage
   close by `engine.flush()` (`bootstrap.rs:348`, receipt semantics
   `state/actor.rs:115/158`) — crash *windows* are chunk 10's, ordering
   is ours? Can any `StorageCommand` sender outlive the storage actor
   close (`bootstrap.rs:381-382`) in any mode?
3. **Exit-point enumeration**: every `std::process::exit` / panic-on-
   shutdown path (orientation: `main.rs:329`) and what it bypasses.

Deliverable sub-table: **channel → closing mechanism → observer →
reaction** (this also discharges the I.2 half of the acceptance).

### 2.4 Pass D — blocking-call hunt (K)

Grep recipe (validated at orientation; recorded verbatim in the report):
`git grep -n -E 'blocking_send|blocking_recv|block_on|thread::sleep|spawn_blocking' v0.1.0 -- crates`
plus targeted `rpassword|keyring` and `fs::|std::fs` runs over

### 2.5 Pass E — select!-safety rubric (I.1) — the rubric, applied per site

Full rubric for the six select sites (§1.1); reduced rubric (Q3, Q4-lite,
close behavior) for the seven plain loops (D3). Per site, answer **all**
of:

- **Q1 arm inventory** — each arm, its future, its precondition guard
  (the `if` preconditions like `commands_open`).
- **Q2 head cancellation** — which polled futures can be cancelled when
  another arm wins; classify each primitive against tokio's documented
  cancel-safety (`mpsc::Receiver::recv`, `Sender::send`,
  `broadcast::*::recv/send`, `watch`, `oneshot::recv`,
  `sleep`/`sleep_until`, `signal::ctrl_c`, `signal::recv`,
  `TcpListener/local-socket accept` — all documented-safe; anything else
  found gets named and classified individually).
- **Q3 body-await abort exposure** — awaits *inside* arm bodies are not
  select-cancelled but **are** interrupted by task abort (D11: every
  abort site from Pass C layer 1): SYN's `cycle(...).await` inside the
  command and timer arms (`sync/actor.rs:205/217-220` area), ENG's
  `execute_command` → storage apply round-trip inside the Execute arm,
  IPCA's per-connection tasks in the JoinSet (aborted at
  `server.join`'s budget). For each: what state does a mid-await abort
  leave (half-applied command? un-sent oneshot reply → who observes the
  dropped receiver? un-flushed cycle?), and does any join budget make
  that reachable in a normal shutdown?
- **Q4 re-arming** — after an arm wins, is every stateful arm re-armed
  next iteration: SYN `deadline = reschedule(&st, &cfg)` (missed/dup-fire
  analysis), ENG `next_tick` fixed cadence + `timer_armed` when reminders
  disabled (:338-348), guard flags flipped on `None` (`*_open = false`),
  `sys_open = false` on Closed (`sync/actor.rs:236`).
- **Q5 biased starvation** — can sustained pressure on a high-priority
  arm starve a lower one (ENG: commands before reports before system
  before timer — bounded by inbox caps + try_send drops upstream?; SYN:
  commands always beat the poll timer, but nudges coalesce post-cycle so
  the absorber bounds it — verify). Reason the bound explicitly.
- **Q6 body-await drain delay** — wall-time an arm body can hold the loop
  away from other arms (SYN cycle = full HTTP wall time including
  retries; ENG execute = storage I/O) and the shutdown-latency
  consequence (ties into Pass C; bounded by which join budget?).

**Verdict vocabulary (mandatory)**: `clean` / `clean-because 〈one-line
reason citing the primitive's documented semantics or a code shape〉` /
`finding F9-NN`. A bare `clean` is a review finding (dispatch 9.3: "or
say clean-because").

## 5. Risks (planning agent's honest list)

1. **Cancellation-safety is the hardest axis to judge** (dispatch prompt
   says so too). The select *heads* are documented-safe primitives — the
   real hazards are abort-vs-body-await interleavings (Q3/D11) and
   proving starvation bounds (Q5), neither of which is visible from a
   loop alone. Mitigation: the mandatory `clean-because` vocabulary, the
   abort-site enumeration *before* verdicts, and rate-bounds reasoned
   from caps (inbox capacities) rather than asserted.
2. **Exclusion mistakes in Pass F** (a misread cfg gate silently drops a
   daemon-reachable panic, or vice versa bloats the table). Mitigation:
   D2's gating-line evidence per excluded cluster — the same discipline
   the flow-model chunk used.
3. **Desired-order forcing**: the §2 K order is prose; a strict mapping
   may invent gaps the architecture never promised. Mitigation: D6 —
   step-wise comparison, non-mappings named as gaps *with severity* and
   left for chunk 17's synthesis rather than pre-judged here.
4. **Deadlock reasoning on the cap-1 REPL handshake** is subtle
   (blocking_send ↔ blocking_recv across a std thread). Mitigation: D5's
   targeted-test escape hatch, used only if reading is inconclusive.
5. **Scope bleed into chunks 10/11/12/13/14** — the boundary ledger (D13)
   exists precisely for this; cross-refs, no duplicated adjudication.
