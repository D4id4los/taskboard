## 2. Derivation procedure (stage 2, binding)

Six passes, each leaving a reproducible command trail in the report's
method section. All greps run in the worktree (= the tag tree) with
`git grep … -- crates`; exclusions per D2.

### 2.1 Pass 1 — channel-constructor enumeration (workspace-wide)

```
git grep -n -E 'mpsc::channel|mpsc::unbounded_channel|broadcast::channel|oneshot::channel|watch::channel' v0.1.0 -- crates
```

Every hit is classified: **production** (loaded in non-test builds) vs
**excluded** (inside `#[cfg(test)] mod tests`, `tests/` dirs, doc
comments `///` or `//!`). For each production hit: record primitive,
payload type, capacity (const name + value, or literal), constructor
`file:line`, and — by following both halves — the sender's and
receiver's owner (pass 3). Constructors found *outside* `bootstrap.rs`
are first-class rows (the dispatch prompt names this risk explicitly);
the report states for each whether bootstrap calls into the creating
function or the channel is created by another module's own logic.
Zero `unbounded_channel` hits is a recorded fact, not an assumption.

### 2.2 Pass 2 — spawn-site & actor inventory

```
git grep -n -E 'tokio::spawn|task::spawn|spawn_blocking|thread::spawn|thread::Builder|run_event_loop' v0.1.0 -- crates
```

Each production hit becomes an actor/task row: identity (short ID,
human name), spawn site, crate, inbox(es) consumed, lifetime, join
handle owner. Non-spawn long-lived executors (Slint event loop on the
main thread, the REPL session loop) are included with their
"execution substrate" noted (tokio task / std thread / main thread).

### 2.3 Pass 3 — wiring trace (handle passing)

From `bootstrap()` (`bootstrap.rs:499`) and `run_desktop`
(`ui.rs:157`) as roots, follow every constructor half to its consumer:
which function receives which `Sender`/`Receiver`/handle, by which
parameter. Produces the from→to pairs of the edge table. Cross-check:
the count of edge-table channel rows equals the count of pass-1
production constructors (every constructor yields ≥1 edge; a
constructor whose halves never leave a function is recorded with both
endpoints in that function — e.g. the orphan pair :184).

### 2.4 Pass 4 — ArcSwap read/write trace

```
git grep -n -E '\.rcu\(|\.store\(' v0.1.0 -- crates   # writers
git grep -n -E '\.load\(' v0.1.0 -- crates            # readers (filter to ArcSwap<AppState> receivers)
```

One write edge (engine → store) and one read edge per distinct reader
call-site cluster, each with `file:line`; AGENTS §2's sole-writer rule
is *checked* by the enumeration (a second writer would be a structural
surprise finding, D8 — recorded, not judged).

### 2.5 Pass 5 — shutdown-route trace

From the anchors in §1.3, trace every route that ends a process mode:
signal wait, `App::shutdown` step order (as implemented — numbered
list, each step `file:line`), `detach_connector`, the IPC stop watch,
the UI exit watcher, REPL EOF/Ctrl-D, editor-thread teardown. Recorded
as implemented order only; chunk 9 compares it against the desired
graceful order.

### 2.6 Pass 6 — process-mode matrix + churn annotation

- Mode matrix: rows = process modes (one-shot CLI in-process, one-shot
  CLI over IPC relay, daemon, daemon+REPL? — `entry_point` decides,
  desktop GUI, kiosk), columns = actors/edges from passes 1–5, cells =
  present/absent, each column header carrying its spawn-site
  `file:line`. Derived from `main.rs`, `ui.rs:79`, `repl.rs:71`,
  `ipc/protocol.rs` lane table.
- Churn annotation: every node/edge whose source file appears in
  baseline §churn's top-30 table carries a `churn:N` marker (N = its
  commit count), legend citing baseline `§churn` by anchor. The
  baseline's headline (app crate ≈ 2.4× any other; `commands/mod.rs`
  36/386) frames the hot-seam callouts.

## 3. Edge-table schema (fixed)

One row per channel edge / ArcSwap edge / transport edge, columns:

| Column | Content |
|---|---|
| ID | `E-NN`, stable, assigned in table order |
| From → To | actor short IDs (resolved by the actor inventory table); external endpoints as `CLI(proc)` / `daemon(proc)` |
| Primitive | `mpsc` / `broadcast` / `oneshot` / `watch` / `ArcSwap` / `local-socket` |
| Payload | message type as named in code (vocabulary as found, D3) |
| Capacity | number, `unbounded`, or `n/a` (oneshot/watch/ArcSwap) |
| Direction | one-way / fan-out (broadcast: list subscribers) / read+write (ArcSwap rows are split into write & read edges) |
| Return path | embedded oneshot pattern if the payload carries one (e.g. `EngineCommand::Execute` receipt), else `—` |
| Constructed at | `file:line` of the `channel()` call (D1) |
| Evidence | `file:line` of the send site and the receive/`select!` arm |
| Notes | lifecycle quirks (dropped receiver, fan-in twin, per-attach pair), churn marker |

## 4. Diagram design (mermaid)

### 4.1 Main runtime graph — `graph LR`

- **Subgraph per actor/task** (engine, storage, sync, notifier, IPC
  accept + dispatcher, UI forwarder, Slint UI loop, REPL session +
  editor thread, system logger); subgraph titles carry the spawn
  `file:line`.
- **Broadcast channels are hub nodes** (`SYS` SystemEvent bus,
  `SIG` EngineSignal bus), fan-out edges to each subscriber — not
  point-to-point arrows through the sender (D6).
- **`ArcSwap<AppState>` is a shared-state node** (mermaid database
  shape) outside actor subgraphs: one solid write edge from the
  engine, dashed read edges to each reader (D7).
- **Edges** labelled `payload · cap=N` (or `cap=64 (SYS_BROADCAST_CAPACITY)`);
  every mermaid node/edge maps to exactly one edge-table row (or its
  reverse listing) — the table is the source of truth, the diagram is
  its projection.
- **External processes in a dashed subgraph** (`CLI(proc)`) joined by
  `local-socket · JSON v1` edges to the IPC server (D9).
- **Shutdown triggers** drawn as dotted red edges (`-.->` + `classDef
  shutdown`) only where they are message flow (Shutdown broadcast,
  stop watch, Detach); the ordered teardown itself lives in §4.2.

### 4.2 Shutdown sequence — separate `sequenceDiagram`

Participants: signal/UI/REPL exit source → `App::shutdown` → engine →
connectors → storage; one numbered message per implemented step with
`file:line` in the label. Keeps the main graph uncluttered (D5).

### 4.3 Rendering validation

Stage 2 checks syntax: `mmdc`/`npx @mermaid-js/mermaid-cli` if
available offline (time-boxed 10 min); otherwise a conservative
label subset (ASCII labels, quoted where needed, no exotic shapes)
plus a structural lint (balanced quotes/brackets, every node
declared before use, no `end` inside labels). The method section
records which validation ran — honestly (conv/§5 spirit).

## 6. Decisions (open questions resolved)

- **D1 — constructor site vs bootstrap-centric model**: the edge table
  records where each channel is *constructed*, and the derivation is
  workspace-wide (pass 1), because orientation already proves channels
  live outside `bootstrap.rs` (engine inbox in the state crate, storage
  inbox in the storage crate, UI-command channel in `app/ui.rs`, IPC
  inbound in `ipc/server.rs`, REPL handshake in `repl.rs`). A
  bootstrap-only reading would silently drop five edges.
- **D2 — production-only graph**: channels/spawns inside `#[cfg(test)]`
  modules, `tests/` dirs, and doc comments are excluded; each excluded
  cluster is named in the method note so the reviewer can reproduce the
  exclusion. Rationale: axis D models the shipped runtime.
- **D3 — vocabulary as found**: names (`StateCommand`, `EngineCommand`,
  `SyncCommand`, …) are recorded exactly as the code spells them, even
  where two names meet on one edge; no renaming, no adjudication
  (chunks 3/4 record local facts, 15 adjudicates docs drift, 17 merges
  the verdict — dispatch non-goals).
- **D4 — doc-claim handling**: architecture.org's comm table and its
  "all channels bootstrap-created" sentence are a *checklist* for the
  reality-vs-docs facts list (§5.11) with chunk-15 cross-refs; this
  chunk records reality only (dispatch non-goal: no drift adjudication).
- **D5 — two diagrams, not one**: main runtime graph + separate
  shutdown sequence diagram; mixing teardown ordering into the runtime
  graph makes both unreadable and invites chunk-9-style judgments.
- **D6 — broadcast as hub nodes**: fan-out semantics (N receivers, one
  bus) are structurally different from point-to-point mpsc; drawing
  them as hubs keeps subscriber counts visible (input chunk 9 needs).
- **D7 — ArcSwap representation**: a shared-state node with one solid
  write edge and dashed read edges; each read/write is also an edge
  table row (primitive `ArcSwap`, direction read/write). Lock-free
  reads are a *fact* of the primitive, not a performance claim.
- **D8 — sole-writer check is in scope as enumeration**: pass 4
  enumerates `.store`/`.rcu` call sites; a second writer would be
  recorded as a structural-surprise finding (axis D) with the evidence,
  and cross-refed to chunk 9 — the *verdict* on safety stays chunk 9's.
- **D9 — external CLI process**: the IPC-relay CLI is a real endpoint
  of the flow model but a different OS process; dashed subgraph, edges
  typed `local-socket · JSON v1`, lanes from `route_for_ipc` listed in
  §5.8. In-process one-shot CLI dispatch shares the daemon graph minus
  IPC server and long-lived loops — captured by the mode matrix (D10).
- **D10 — mode matrix included**: which actors/edges exist per process
  mode is part of "understanding the flow from one artifact" (axis D's
  question); chunks 9 and 16 both consume it.
- **D11 — per-request oneshots**: recurring oneshot *patterns* get
  edge rows (EngineHandle receipts, StorageHandle calls, IPC
  per-connection reply, REPL masked read); the table's "return path"
  column ties them to their carrying mpsc edge. No row per ephemeral
  instance — the table models structure, not executions.
- **D12 — findings discipline**: only structural surprises (a channel
  the docs don't mention, a second ArcSwap writer, an unbounded
  channel, a spawn site with no inbox) plus F2-01 (promotion, P3).
  Concurrency/boundedness *judgments* are chunk 9's — capacities are
  recorded here, evaluated there.
- **D13 — edge IDs/actor IDs**: `E-NN` for edges, short actor IDs
  (`ENG`, `STO`, `SYN`, `NTF`, `IPCA`, `IPCD`, `UIF`, `UI`, `RPL`,
  `EDT`, `SYSLOG`) resolved in the actor inventory; stable IDs because
  chunks 9/15/16 cite them.
- **D14 — mermaid validation fallback**: see §4.3; honesty rule — the
  report states which validation actually ran.

| Risk | Mitigation |
|---|---|
| Channels constructed outside bootstrap missed by a bootstrap-centric read | D1: pass 1 is a workspace-wide constructor grep, not a bootstrap read |
| Test-module constructors polluting the graph | D2 exclusion rule + named excluded clusters in the method note |
| Constructor count ≠ edge count (fan-in twin, orphan pair, per-attach pairs) | Pass-3 cross-check makes the reconciliation explicit rows (orphan pair = edge with dropped receiver; attach pair = one row noted "per attach") |

| Line drift: `file:line` rotting between planning and execution | None expected: the worktree is pinned to the immutable tag (conv 1); stage 2 re-verifies every anchor anyway |

| Slip into concurrency verdicts (chunk 9 scope) | D12; stage-3 review rejects smuggled verdicts |
